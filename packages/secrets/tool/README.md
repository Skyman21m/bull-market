# Key-material boundary gate

Run `make custody-check` from the repository root. The existing JavaScript gate checks access to the keystore and package internals. `key_material_gate.dart` additionally resolves production Dart references with the workspace's pinned analyzer and rejects known private derivation and RecoverBull decryption entry points outside `packages/secrets`, including the raw `Bip32Keys` constructor and the mixed public/private decoder `Bip32Keys.fromBase58`. Production consumers also cannot import or export `secrets/testing.dart`, or reference declarations from its test keystore through aliases and re-exports. Every conditional import/export alternative is checked, including branches inactive on the analyzer host, whose relative URIs are matched on their path. Silent Payments accounts built from words (`SpAccount.createFromMnemonic*`) are private derivation too. The Rust bridge may start only as `BullSdk.init()`: a host `handler` or `api` would receive every call's arguments, the words handed to lwk, boltz and bwk among them, and `BullSdk.initMock` is refused for the same reason.

The gate is a fence on named symbols, on signatures and on places: it says where listed operations may be called, what some classes may declare, and which files may use the vault. It is not a data-flow analysis, and the last section lists what it does not see.

## What is scanned

The gate scans every Dart file under `lib/`, `packages/*/lib/` and `features/*/lib/` except the custody package `packages/secrets` itself, generated files included: no file is left out for its name or its folder (#47). Until #47 it skipped `*.g.dart`, `*.freezed.dart`, `*.gr.dart`, `*.config.dart`, `*.mocks.dart` and `*.steps.dart`, and every file under a folder named `generated`, `vendor` or `build`, matched on the absolute path, so a hand-written file at one of those places escaped every rule, and a checkout inside a folder with one of those names scanned nothing. Measured on `main` with the app's generated outputs present, those exclusions skipped 226 of 2,306 files (125 `*.freezed.dart`, 19 `*.g.dart`, the 2 drift `*.steps.dart`, the 78 localization files of the app, of `features/logs` and of `features/p2p`, and the 2 `flutter_gen` files), and scanning them reports no violation and no resolution error, so none is excluded any more. A file that `analysis_options.yaml` excludes from analysis (the app excludes `lib/**/*.g.dart` and `lib/**/*.freezed.dart`) has no analysis context of its own; it is still compiled, so the gate resolves it in the deepest context that holds it. The scan takes about 80 seconds on 2,306 files in the `bull-tools` container, against 68 seconds on 2,080 before.

These fail the check before any rule is applied:
- a symbolic link under the roots, or one that stands for a root, a package, a feature, or `packages/` or `features/` itself, since the gate does not follow it;
- a `pubspec.yaml`, `analysis_options.yaml`, `package_config.json`, `.packages` or `.dart_tool` under a production root, and a scanned file whose analysis context uses another package configuration than the workspace's: a package configuration of its own would make the gate resolve the files below it against other packages than the build does, and analysis options could lower the severity of an error the gate reports;
- a root without `lib/`, or without any Dart file under the production roots;
- an import, export or part of a scanned file, any alternative of a conditional one included, that names a file of the repository the gate does not scan: a file outside the roots, reached by a relative or `file:` URI, or a file without the `.dart` extension, which Dart compiles all the same. The custody package's own `lib/` is the one exception.

Files outside the repository (the SDK, the pub cache) are dependencies: the rules apply to what production code calls in them, not to their code. `test/`, `integration_test/`, `bin/` and `tool/` are not production code and are not scanned. Paths are compared as POSIX paths (`$root/…`): the gate runs on Linux and macOS, the hosts of CI and of the supported builds, not on Windows.

Resolution errors fail the check; diagnostics print only file names, diagnostic identifiers, declaration identities and the signatures of declarations, never source excerpts or runtime values. Import prefixes, re-exports, type aliases, constructor tear-offs, method tear-offs and dot shorthand keep the identity of their resolved declaration.

## Exceptions

Exceptions identify a file, enclosing function or class method, and individual permitted symbols. `_performDryScan` can derive from pre-import user input. `SwapMasterKeyModel.fromBoltz` and `toBoltz` can translate the deliberately exported swap child key. Neither exception permits deriving a new child from wallet words. `Bip32Derivation.getBip32Xpub` in `lib/core/utils/bip32_derivation.dart` alone may call `Bip32Keys.fromBase58`: this adapter forces the public version bytes before decoding. BIP85 child mnemonic formatting, BIP39 validation and public-key operations are not private derivation and need no exception.

## RoboSats Garage Keys

RoboSats Garage Keys (#28) are key material too: whoever holds one controls every robot derived from it. The gate refuses `GarageKeyMaterial.bytes` (`package:secrets`, the bytes of a stored key) and `GarageKey.revealBytes` and `GarageKey.revealBech32` (`package:robosats`) everywhere except in the table `_garageKeyReaders`: the P2P repository (`features/p2p/lib/src/data/garage_key_repository_impl.dart`, class `GarageKeyRepositoryImpl`) may read the bytes and `revealBytes`, and the display widget (`features/p2p/lib/src/ui/widgets/garage_key_view.dart`, class `GarageKeyView`) may call `revealBech32`. `packages/robosats` itself is not exempt. Constructing a key (`GarageKey.parse`, `GarageKey.fromBytes`) and deriving robots from it remain available. Object patterns (`case GarageKeyMaterial(:final bytes)`) are checked like any other access, and dynamic access to a member named `bytes`, `revealBytes`, `revealBech32`, `garageKeys` or `setupP2p` fails closed.

### The handle and the composition

`Secrets.garageKeys` (`package:secrets`), the handle that creates, imports, reads and deletes Garage Keys, is allowed once, in one shape (#47): in the static `AppLocator.setupP2p` of `lib/locator.dart`, as `withGarageKeys ? <vault>.garageKeys() : null`, whose condition is that method's own `withGarageKeys` parameter, passed as the `garageKeys:` argument of `P2pFeature.setup`, which is the method's body or a statement of it. When `lib/locator.dart` declares `AppLocator`, it must make exactly one such call. `lib/locator.dart` also composes the WorkManager isolate, so the composition decides which isolate holds the handle:
- `main` of `lib/main.dart`, the app's only entry point, is named by no code, `startApp` of `lib/bootstrap.dart` is called only as its body or a statement of it, and `Bull.init` of `lib/init.dart`, the foreground composition, only by `startApp`;
- every call of `AppLocator.setup` passes `withGarageKeys` as a boolean literal, and `true` only as a statement of `Bull.init` itself, not in a closure, a local function or a condition; the background handler passes `false`;
- `AppLocator.setupP2p` is called only as a statement of `AppLocator.setup`, with the flag that method received, and neither flag is ever assigned;
- any other reference to `startApp`, `Bull.init`, `AppLocator.setup` or `AppLocator.setupP2p` fails: a tear-off, which `Function.apply` or a dynamic call needs, since Dart reaches a static or top-level function dynamically only through one;
- no call of `package:get_it` has `GarageKeys` in its type arguments, written or inferred, or in a type literal it is passed (`type: GarageKeys`): the feature keeps the handle in its repository, not in the container that every isolate reads. A `Type` held in a variable is not followed.

`AppLocator` is the class of `lib/locator.dart` and `Bull` the class of `lib/init.dart`: a class of the same name elsewhere is not the composition, and renaming either class, or making a method an instance method, leaves the handle call outside the allowed shape, which fails. `test/locator_test.dart` runs `setupP2p` with each value, and `test/core_test/background_tasks/background_tasks_keystore_test.dart` still reads, from the text of `lib/`, the arguments each composition passes.

### Who uses the vault

No production library re-exports a declaration of `package:secrets`, read from the library the analyzer resolved after its `show` and `hide` lists, through any chain of re-exports, and a conditional export fails closed, since the gate does not resolve the library of an inactive alternative (#47). In `features/*/lib` and `packages/*/lib`, a reference to a declaration of `package:secrets` is refused outside the files of the table `_vaultUsers`, and those files may refer only to the declarations the table gives them: the P2P facade, which receives the handle from the shell, and its locator, which registers it, `GarageKeys`; the repository, which uses it, `GarageKeys`, `GarageKeySlot`, `GarageKeyMaterial` and the vault's failures; the feature's test seam, `package:p2p/testing.dart`, which registers the Garage over a handle a test made (#54), `GarageKeys`. A member counts as its class, and a type alias declared anywhere counts as the declaration it names, so `typedef Vault = Secrets;` in another package hands nothing on. Outside those files, no file of `features/*/lib` or `packages/*/lib` invokes or reads a member of a value whose static type mentions a declaration of the vault, even when it names none of its types (a handle returned by a function of an allowed file, used through an extension declared there). The app's own `lib/` uses the vault and is not concerned. `features/p2p/test/secrets_imports_test.dart` still pins the names these files import. The table covers upstream packages too: an upstream merge whose package or feature starts using the vault fails the gate with `package:secrets#<declaration> outside the files that may use the vault` for each such file, and the table grows only after a review of that use.

No production file imports or exports `package:p2p/testing.dart`, the feature's test seam: the resolved library, the decoded text of the URI and every conditional alternative are read, so an escaped URI does not hide it.

### What a reader declares

A class of `_garageKeyReaders` declares the public surface the table gives it, and nothing more (#47): each public member, constructors, fields, getters, setters, operators and static members included, must be in the table with its exact signature as the analyzer prints it, and each type a signature names must come from the library `_readerTypes` gives it, so that a type of the same name declared elsewhere fails. Its supertypes are named in the table (the repository's interface, `StatelessWidget` for the view), it mixes in nothing, and a supertype from the workspace (outside `dart:` and Flutter) declares abstract members only, no field and no concrete member, so the class inherits nothing the table does not list. No other code reaches into it: its file declares only what the table lists (the repository's file, the class alone; the view's file, the view, its private copy button and that button's state), has no `part` or `part of` directive and no dynamic or unresolved member access, no extension on it exists anywhere, and its private members are named only inside it. The implicit constructor of a class that declares none takes nothing and is not counted. The table is written for the surface of #54.

The table pins the signatures as the analyzer prints them (named parameters in alphabetical order, for one) and the libraries that declare the types they name, internal ones included (`package:flutter/src/foundation/key.dart`, `package:primitives/src/result.dart`). An upgrade of Flutter, of the analyzer or of `primitives`, or an upstream merge, can change either and fail the gate, closed, with a message that names the member and the signature or library it found. To update the table, check that the new signature lets out nothing more, then copy it, or the new library of the type, from the message into `_garageKeyReaders` or `_readerTypes`.

The P2P failures a reader names, constructs or returns carry no data but the reason of an invalid Garage Key (#47): such a failure mixes nothing in, neither it nor any of its supertypes outside the SDK declares a field, static or not, except `GarageKeyInvalidFailure.reason` (a `GarageKeyFailure` of `package:robosats`) and `Failure.logMessage` of `package:primitives`, and the constructors of `P2pFailure` take no parameter, so no failure passes a message to `Failure.logMessage`. A failure that no reader names is not concerned: a failure of an order or a trade may carry a status or an id. A new failure that the repository returns is checked as soon as the repository names it; if it must carry data, its field joins `_failureFields`, with the reason, in the same pull request.

## What the gate does not see

This is a policy over known APIs, not whole-program data-flow analysis. It does not prove that plaintext never leaves the package, infer whether arbitrary inputs are private, or detect a newly introduced cryptographic implementation. Review cryptographic dependency and API changes together with this policy. Unresolved access to the listed sensitive members, including dynamic access, fails closed; other dynamic dispatch remains outside the guarantee. In particular:

- What the values a reader hands out let out. The repository returns a `NetworkGarageKey` that holds the `GarageKey`, and a `GarageKey` derives every robot token of the key (`deriveToken`, the robots' identities and keys); only its two reveal methods are fenced. `GarageKeyView.build()` returns a widget tree that holds the `robo1…` text and hands it to `GarageKeyClipboard`, a class the gate does not check.
- Where a key goes inside a reader's members: a log line, a field of an object passed in, a static field of another class. The table fixes the signatures, not the bodies.
- The fields of the types a reader returns (`NetworkGarageKey`, `NetworkRobot`, `GarageRobot`), a failure that carries data through a getter computed from a top-level variable, and a failure that the reader does not name but receives from code outside it.
- A handle stored in a container under another type (`Object`) and called dynamically, other than through the listed member names; the public members of the private helper classes of a reader's file, reached dynamically from another library.
- An `// ignore:` or `// ignore_for_file:` comment over an error hides it from the gate, as from the analyzer; such code does not compile, so it cannot ship (`AGENTS.md` forbids these comments).
- Which names the P2P feature imports from the vault: the feature's import test pins them; the gate pins the declarations it uses.
- `packages/robosats` derives Garage Keys, robot tokens and robot keys with hand-written code that names no listed symbol (see `AGENTS.md`).
- Code outside the repository, and production code outside `lib/`, `packages/*/lib/` and `features/*/lib/` that no scanned file names.

`test/key_material_gate_test.dart` resolves regression fixtures against the installed dependencies without executing their cryptographic or native APIs.
