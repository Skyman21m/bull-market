# Key-material boundary gate

Run `make custody-check` from the repository root. The existing JavaScript gate checks access to the keystore and package internals. `key_material_gate.dart` additionally resolves production Dart references with the workspace's pinned analyzer and rejects known private derivation and RecoverBull decryption entry points outside `packages/secrets`, including the raw `Bip32Keys` constructor and the mixed public/private decoder `Bip32Keys.fromBase58`. Production consumers also cannot import or export `secrets/testing.dart`, or reference declarations from its test keystore through aliases and re-exports. Every conditional import/export alternative is checked, including branches inactive on the analyzer host, whose relative URIs are matched on their path. Silent Payments accounts built from words (`SpAccount.createFromMnemonic*`) are private derivation too. The Rust bridge may start only as `BullSdk.init()`: a host `handler` or `api` would receive every call's arguments, the words handed to lwk, boltz and bwk among them, and `BullSdk.initMock` is refused for the same reason.

## What is scanned

The gate scans every Dart file under `lib/`, `packages/*/lib/` and `features/*/lib/` except the custody package `packages/secrets` itself, generated files included: no file is left out for its name or its folder (#47). Until #47 it skipped `*.g.dart`, `*.freezed.dart`, `*.gr.dart`, `*.config.dart`, `*.mocks.dart` and `*.steps.dart`, and every file under a folder named `generated`, `vendor` or `build`, matched on the absolute path, so a hand-written file at one of those places escaped every rule, and a checkout inside a folder with one of those names scanned nothing. Measured on `main` with the app's generated outputs present, those exclusions skipped 226 of 2,306 files (125 `*.freezed.dart`, 19 `*.g.dart`, the 2 drift `*.steps.dart`, the 78 localization files of the app, of `features/logs` and of `features/p2p`, and the 2 `flutter_gen` files), and scanning them reports no violation and no resolution error, so none is excluded any more. A file that `analysis_options.yaml` excludes from analysis (the app excludes `lib/**/*.g.dart` and `lib/**/*.freezed.dart`) has no analysis context of its own; it is still compiled, so the gate resolves it in the deepest context that holds it. The scan takes about 80 seconds on 2,306 files in the `bull-tools` container, against 68 seconds on 2,080 before.

A symbolic link under those roots, or one that stands for a whole package or feature, fails the check, since the gate does not follow it. So does an import, export or part of a scanned file, any alternative of a conditional one included, that names a file of the repository the gate does not scan: a file outside those roots, reached by a relative or `file:` URI, or a file without the `.dart` extension, which Dart compiles all the same. The custody package's own `lib/` is the one exception. Files outside the repository (the SDK, the pub cache) are dependencies: the rules above apply to what production code calls in them, not to their code. `test/`, `integration_test/`, `bin/` and `tool/` are not production code and are not scanned.

Resolution errors fail the check; diagnostics print only file names, diagnostic identifiers and declaration identities, never source excerpts or runtime values. Import prefixes, re-exports, type aliases, constructor tear-offs, method tear-offs and dot shorthand keep the identity of their resolved declaration.

## Exceptions

Exceptions identify a file, enclosing function or class method, and individual permitted symbols. `_performDryScan` can derive from pre-import user input. `SwapMasterKeyModel.fromBoltz` and `toBoltz` can translate the deliberately exported swap child key. Neither exception permits deriving a new child from wallet words. `Bip32Derivation.getBip32Xpub` in `lib/core/utils/bip32_derivation.dart` alone may call `Bip32Keys.fromBase58`: this adapter forces the public version bytes before decoding. BIP85 child mnemonic formatting, BIP39 validation and public-key operations are not private derivation and need no exception.

## RoboSats Garage Keys

RoboSats Garage Keys (#28) are key material too: whoever holds one controls every robot derived from it. The gate refuses `GarageKeyMaterial.bytes` (`package:secrets`, the bytes of a stored key) and `GarageKey.revealBytes` and `GarageKey.revealBech32` (`package:robosats`) everywhere except in the table `_garageKeyReaders`: the P2P repository (`features/p2p/lib/src/data/garage_key_repository_impl.dart`, class `GarageKeyRepositoryImpl`) may read the bytes and `revealBytes`, and the display widget (`features/p2p/lib/src/ui/widgets/garage_key_view.dart`, class `GarageKeyView`) may call `revealBech32`. The repository exists (#28); the widget does not yet, so no production file may reveal the `robo1…` text today. `packages/robosats` itself is not exempt. `Secrets.garageKeys` (`package:secrets`), the handle that creates, imports, reads and deletes Garage Keys, is refused everywhere except in the class `AppLocator` of `lib/locator.dart`, the composition root that passes it to the P2P feature; that file also composes the WorkManager isolate, so the rule decides where the handle is obtained, not in which isolate. Constructing a key (`GarageKey.parse`, `GarageKey.fromBytes`) and deriving robots from it remain available. Object patterns (`case GarageKeyMaterial(:final bytes)`) are checked like any other access, and dynamic access to a member named `bytes`, `revealBytes`, `revealBech32`, `garageKeys` or `setupP2p` fails closed.

The isolate is decided by the composition, and the gate resolves it (#47). The handle is taken in `AppLocator.setupP2p`, behind the required `withGarageKeys` flag of `AppLocator.setup`. Every call of `AppLocator.setup` passes `withGarageKeys` as a boolean literal, and `true` only in `Bull.init` of `lib/init.dart`, the foreground composition; the background handler passes `false`. `AppLocator.setupP2p` is called only by `AppLocator.setup` of `lib/locator.dart`, which passes it its own `withGarageKeys` parameter and never assigns that parameter. Any other reference to either method fails: a tear-off, which `Function.apply` or a dynamic call needs, since Dart reaches a static method dynamically only through one. The two methods are matched by the name of their class in any library, so a class named `AppLocator` elsewhere is held to the same rules; renaming the class of `lib/locator.dart` fails the gate already, through the exception for `Secrets.garageKeys`. `test/locator_test.dart` runs `setupP2p` with each value, and `test/core_test/background_tasks/background_tasks_keystore_test.dart` still reads, from the text of `lib/`, the arguments each composition passes.

No production library re-exports a declaration of `package:secrets` (#47), read from the library the analyzer resolved after its `show` and `hide` lists, through any chain of re-exports, and a conditional export fails closed, since the gate does not resolve the library of an inactive alternative. Only the vault's own libraries then make its declarations importable, so `features/p2p/test/secrets_imports_test.dart`, which reads the URIs of the feature's directives, sees every way into the vault by import; that test, not the gate, pins which files of the feature import `package:secrets` and which names each one shows.

A class of `_garageKeyReaders` reads a key for its own use (#47): none of its public members, constructors, methods, getters, setters and fields, static ones included, returns a type that can hold the bytes or the text of a key, or takes a parameter that the class could hand them to. A type can hold them when it is `String`, a type of `dart:typed_data`, an `Iterable<int>`, a `BigInt`, `Object`, `dynamic`, `Function` or a type parameter, or a function, record or generic type with one of those anywhere in it; a parameter can receive them when its type is a function type that can hold them, `Object`, `dynamic`, `Function` or a type parameter, or a record or generic type with one of those in it. Type aliases are seen through. Private members are not checked: the class may keep the bytes in them while it works. `features/p2p/test/garage_key_surface_test.dart` still pins, from the syntax tree, the names and return types of the repository's public members.

## What the gate does not see

This is a policy over known APIs, not whole-program dataflow analysis. It does not prove that plaintext never leaves the package, infer whether arbitrary inputs are private, or detect a newly introduced cryptographic implementation. Review cryptographic dependency and API changes together with this policy. Unresolved access to the listed sensitive members, including dynamic access, fails closed; other dynamic dispatch remains outside the guarantee. In particular:

- Where a key goes once read, inside a reader class: a log line, a field of a failure it returns, an object passed in that it fills (a `List<int>`, a sink), a type that holds text without being one (a `StringBuffer`, a `Uri`, a class of the app with a `String` field). Its signatures are checked, not its body.
- Another declaration of a reader's file, or a part of it, that calls the reader's private members: Dart privacy is per library, and the rule on signatures covers the reader class alone. The feature's surface test pins that the repository's file declares that one class.
- Which files of the P2P feature import the vault, and with which names: the feature's import test pins it. A declaration of another library that hands out a vault type under its own name (a type alias, a wrapper class, a function returning `Secrets`) is not a re-export, and that library would need a dependency on `package:secrets` in its `pubspec.yaml`.
- Who calls `Bull.init`: the foreground composition is pinned to that method, not the method to the foreground.
- Any method of `AppLocator` may ask for `Secrets.garageKeys`, not only `setupP2p`; the rules above pin who calls `setupP2p`, not who calls another method of that class.
- `packages/robosats` derives Garage Keys, robot tokens and robot keys with hand-written code that names no listed symbol (see `AGENTS.md`).
- Code outside the repository, and production code outside `lib/`, `packages/*/lib/` and `features/*/lib/` that no scanned file names.

`test/key_material_gate_test.dart` resolves regression fixtures against the installed dependencies without executing their cryptographic or native APIs.
