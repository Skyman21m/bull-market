# robosats

Pure-Dart RoboSats client primitives for Troc: the robot identity and OpenPGP key (see the library comment of `lib/robosats.dart`), and the client of the coordinators described below: the public reads, and the robot of this device on a coordinator.

## Coordinator client: public reads

- `Federation.robosats` is the federation list embedded from RoboSats `federation.json` (commit e56f9cf7c, 2026-11-08: six coordinators, Gumpellite included): each `Coordinator` has its aliases, description, contact, badges, policies, onion addresses and Lightning node keys per `RobosatsNetwork`. `RobosatsCurrency` maps the RoboSats currency ids to codes (commit ff1998c, the protocol reference). Both are generated by `tool/generate_coordinator_data.dart`, which records the source commit and Git blob id in each generated file, and `Federation.problems` validates a list (in the tests, and asserted by `FederationBookReader` in debug builds). How to refresh them, and the protocol reference, from a newer RoboSats commit: `AGENTS.md`, section "Troc (fork)", "Refreshing the RoboSats reference".
- Where the entry of Gumpellite comes from (checked on 2026-11-11 with the public GitHub API, the worked example of a new coordinator in that procedure). RoboSats pull request #2904 (commits `b2ad3cacb` and `ba25fe093`) was opened on 2026-11-06 and merged on 2026-11-08 by KoalaSat, a public member of the RoboSats organisation, with one review comment, by a contributor, about the missing Nostr key. It links the application issue #2685, opened on 2026-08-27 by a separate account, `GumpCoordinatorGit` (created about six minutes before, no public repository; the issue body was never edited), which gives the same mainnet onion address, mainnet node key and PGP fingerprint, and no testnet address. The Nostr key `84e6c796…c840` has no such trail: the issue leaves it empty, and it appears only in the maintainer's commit `ba25fe093`, after the maintainer asked the applicant to check SimpleX. The PGP key file was checked against its fingerprint only; the copy the issue links, on the applicant's own onion site, was not fetched.
- `CoordinatorTransport` is the port the app implements over Tor in `features/p2p`: one HTTP request in (`CoordinatorRequest`: method, absolute onion URL, headers, body, the largest body accepted, and the robot it is made for, if any), one `CoordinatorResponse` or a `CoordinatorTransportFailure` out. The adapter owns sessions, retries and the `User-Agent`; it must always complete without throwing, enforce a total deadline, stop reading at the body cap, give lowercase header names, not follow redirects, keep the requests of each robot on connections and Tor circuits of their own, and never log headers (see the doc of `CoordinatorTransport`).
- `CoordinatorClient(transport)` reads one coordinator: `fetchInfo` (`/api/info/`, whose `network` and `node_id` are checked against the federation entry by `Coordinator.verifyIdentity`), `fetchBook` (`/api/book/`, optional currency and type filters, received orders outside them dropped, a `404` with `not_found` being an empty book) and `fetchLimits` (`/api/limits/`).
- `FederationBookReader(transport)` asks every coordinator at once: `requestAll` returns one future per coordinator, which screens should prefer; `read` waits for all of them and merges them into a `FederationBook` with one outcome per coordinator and every valid `PublicOrder`, tagged with its coordinator, by coordinator then id.
- Nothing is trusted: a body above `CoordinatorReadBounds`, a non-JSON body, an unexpected status or an invalid `/api/info/` field fails that one request with a `CoordinatorFailure`; an invalid book order or limits entry is dropped alone and counted, with a `DroppedOrderReason` per order (`OrderBook.dropped`) and a count of entries (`droppedEntries`). Only the first `CoordinatorReadBounds.maxOrders` orders of a book are read (`OrderBook.truncated`). Order dates must be valid ISO 8601 dates with a zone, between 2020 and 2100, at most 48 hours apart, and within 7 days of the injectable clock of the client. No failure and no `toString()` carries coordinator text.
- Free text from a coordinator (payment methods, notice, node alias, versions, alternative site and name, price sources) is capped in code points and cleaned when read: C0 and C1 control characters and DEL are removed, except tab, line feed, vertical tab, form feed, carriage return and next line, which become a space like the line and paragraph separators; Unicode bidirectional controls and unpaired surrogates are removed; accented letters and emoji are kept. The rule is exported as `displayText`, so that an app cleans the text it shows from elsewhere, the embedded federation list for instance, the same way. It is still untrusted: show it as plain text, never as markup, and never log it.
- Tests run offline on responses recorded from the live federation (`test/fixtures/coordinator/README.md`), which include non-ASCII payment methods and a location; hostile cases are built by the tests.
- `FiatAmount` and `OrderAmount` share their names with types of `lib/core/exchange/domain/entity/order.dart` in the app, a different package: they are not renamed, so code that needs both imports one with a prefix.

## Coordinator client: the robot of this device

- `GarageKey.firstUsableRobot(fromIndex)` gives the first robot at or after an index that a coordinator can be contacted with, as a `GarageRobot` (index and `RobotIdentity`). It skips an index whose token fails the entropy rule of RoboSats, which the official client never contacts a coordinator with and whose automatic choice of a robot passes over, and an index whose hash id has no nickname; it looks at 100 indexes at most, as the official client.
- `CoordinatorClient.fetchRobot` is `GET /api/robot/` with the first-contact `Authorization` header (`Token <hash> | Public <key> | Private <key> | Nostr <key>`), which is what the official client always sends: a coordinator that does not know the token hash creates the robot with those keys, and one that knows it ignores them and answers with the keys of the first contact. `fetchKnownRobot` sends the short header (`Token <hash>`), which never creates anything and sends no key: a coordinator that does not know the robot gives `RobotUnknown`.
- The answer describes the robot of this device only when its `hash_id` and `nickname` are the ones derived from the token, compared before any key is parsed (`RobotHashIdMismatch`, `RobotNicknameMismatch`). Then `fetchRobot` gives a `CoordinatorRobot` that carries the pair it sent when the coordinator returned that very pair: the `public_key` with the fingerprints of the pair sent, primary key and subkey (a coordinator returns it re-exported by GnuPG, so the text differs), and the `encrypted_private_key` with its packets. Any other pair, and every pair `fetchKnownRobot` reads, which sends none, comes as an `UnprovenCoordinatorRobot`: nothing of the answer can be read from it, and only its `prove()` gives the `CoordinatorRobot`, which then carries the pair the coordinator holds, still locked (`pgpKey`, with `pgpKeyProven` true).
- `prove()` takes the pair only when its private key unlocks with the robot's token and holds the secret values of its public key, the two blocks being one key packet body for packet body, and each of its two secret parts is locked by an iterated and salted S2K (`ProtectedSecret.provesPassphraseWith`, which the parser requires and the proof checks again). That proves a holder of the token made the pair: a coordinator receives the SHA-256 of the token, never the token, and such an S2K is salted and iterated over the token itself; a simple S2K over SHA-256 would derive exactly the token hash, which is why no other S2K counts. « Proven » means that and nothing more: a coordinator can return any genuine pair of the robot it ever received, a different one at each read, and `pgpKeyProven` is its word, like `found`. The robot carries the pair re-encoded from the packets the proof checked (primary key, certified user ID, selected subkey, their signatures without unhashed area): anything else in the blocks is dropped. Any other pair is `RobotPgpKeyNotProven`: another token's pair, two blocks of two keys, a kind of key this package does not read, or a pair whose unlocking would hash more than `PgpLimits.proofHashedBytes`, 62 MiB for both secret parts and every S2K pass, checked before anything is hashed (a key of the official client or of Troc asks for 32 MiB; a pair GnuPG protected at its largest count asks for 124 MiB and is refused). `prove()` is synchronous: call it off the UI isolate. It wipes the passphrase and the secret values it unlocked. The official client adopts whatever pair the coordinator returns; this package never does.
- So a robot needs no stored key pair: a Garage Key restored on a new device, or read again after a restart, reads each robot back with its token, as long as the coordinator holds a pair the token proves. A pair returned as sent is taken without a proof, so send at a first contact only a pair made for that robot by `RobotPgpKey.generate` for that very request.
- A `PgpPublicKey` and a `RobotPgpKey` hold canonical armor only: the packets armored as the official client armors them, whatever armor they were read from. Armor headers such as `Comment` are accepted when reading and dropped, so only base64 and the two fixed lines ever go from a key into the `Authorization` header.
- Refusals are typed and carry no coordinator text: `RobotCredentialsRejected` (errors 7000, 7001 after a first contact, 7003, HTTP 401 and 403), `RobotKeysRefused` with a `RobotKeysRefusal` reason read from the code inside error 7002 (invalid key, key already used, key less than 12 hours old), `RobotNicknameTaken` (7004). Every other status is a `CoordinatorUnexpectedStatus`. After a 7004, `fetchRobot` asks once with the short header, in case the coordinator created the robot for another copy of the same request; that check can miss (the coordinator creates the user before the token) and a coordinator can answer 7004 for ever, so a caller asks again with `fetchKnownRobot` before it gives up an index, and bounds how many indexes one coordinator can make it give up.
- `CoordinatorRobot` holds what the screens need: `found` (the robot is more than five minutes old for the coordinator), the rewards, the stealth preference, the active or last order id, the last login, and the Nostr public key the coordinator holds with the formula it comes from (`nostrKeyDerivation`, `null` for a key that is not one of the robot). The Telegram and webhook fields are not read.
- The coordinator of the reference source stores the Nostr public key the first contact carries and checks no link with the token; it replaces it later only when the stored key is its all-zero placeholder. One testnet coordinator was seen to store either of the two formulas. Only `NostrKeyDerivation.currentFrontend` may be sent for a real robot: the secret key of the other formula is the token hash itself, which the coordinator receives on every request.
- Every authenticated request names its robot (`CoordinatorRequest.robot`, a `RobotSessionKey` that holds no credential and prints nothing), so the adapter can isolate it.
- The same token hash is the whole credential of a robot on every coordinator: a coordinator that receives it can act as the robot on another one in everything that needs the bearer alone, confirming that fiat was received included, which settles the robot's escrow there. This package contacts one coordinator per call and cannot prevent a caller from contacting several: the rule "one robot index, one coordinator" is to be enforced by the caller, in code, before any order (`AGENTS.md`, section Troc). Evidence and what was verified on live testnet coordinators: `docs/spikes/robot-coordinator.md`.

## Coordinator client: an order, the take and the cancel

Nothing in the app calls these yet (#84): they are the protocol calls of phase 2, for the trade use cases to come.

- `CoordinatorClient.fetchOrder` is `GET /api/order/?order_id=` with the robot's short header: a `CoordinatorOrder`, the order as the coordinator describes it to that robot (`OrderView.get`, `api/views.py:226-528`, commit ff1998c). Each field is read with the JSON type the view writes for that robot: the serializer's decimals are strings, but the raw `Decimal`s a view adds are numbers (a participant's coordinates, `premium_now`, the summary's amounts, `routing_budget_sats`), as Django REST framework's encoder writes them and the reference's OpenAPI schema says. Bounds are those of `PublicOrder`. Its status is one of the 19 of `CoordinatorOrderStatus`; the fields sent only in some statuses or to some robots are `null` when absent; the maker's text goes through `displayText`, the coordinator's labels (payout failure, swap refusal) become enums and are not kept, the Nostr keys accept the coordinator's `"None"`, and the hold invoices (`HoldInvoice`) are opaque strings of at most 2,000 visible ASCII characters, to be decoded and checked by the caller. Only this robot's own trade summary is read, without the payout's payment hash and preimage, and an invalid summary is dropped alone (display only), never the order with it.
- The roles of an answer are checked against each other and against the robot that asked: maker and taker never both, `is_participant` agreeing with them, the maker's or the taker's hash id this robot's exactly when the answer says this robot is the maker or the taker, buyer and seller each the one the order's type and the role give, `ur_nick` this robot's nickname, the nicknames the ones the hash ids give, status 3 only for a pre-taker with its bond, a taker named once past a pre-take, a robot that is no participant shown a public order without any participant's field, a bond invoice only at the step that asks for it and an escrow invoice only to a seller at the escrow step. Any contradiction rejects the answer. The amounts and the invoices are not checked here.
- `takeOrder` and `cancelOrder` are `POST /api/order/?order_id=` with the reference client's JSON bodies: `{"action":"take","amount":0}` for a fixed order, the chosen amount as a JSON number for a range, `"password"` as the SHA-256 of the password in hexadecimal. The cancel takes the last read of the order (`lastRead`), and always sends `{"action":"cancel","cancel_status":N}` with the status the coordinator stores, 1 for a pre-take shown as 3: without that guard, a cancel that lands after a taker's bond locked settles the bond (`api/logics.py:1108-1130`); with it, it is refused (1020). The reference's taker sends no guard: a deviation. A last read by another robot is refused before anything is sent.
- A take answered `200` is not always a take: the reference coordinator answers a take on an order that is no longer public with the order as it is (`api/views.py:595-596`). `takeOrder` gives `OrderTakeStarted` (status 3, this robot the pre-taker and not the maker, with its bond invoice), `OrderAlreadyTakenByThisRobot` (this robot was already the taker: do not drop the trade, its bond is at stake), or `OrderNotTaken`. A cancel that ends the order is answered `200` with a short body holding a `bad_request` text: `OrderCancelEnded`, never a refusal; any other accepted cancel gives `OrderCancelAccepted` with the order as it then is.
- Refusals are typed and carry no coordinator text: `CoordinatorOrderFailure`, one type per error code a take, a cancel or the read can get (`RobotHasActiveOrder` for 1000 to 1003, `OrderAmountOutOfRange`, `OrderTakePenalty` with the seconds of 1012 when the message has the reference's exact wording, `OrderStatusChanged`, `OrderNotCancellable`, `CoordinatorNodeUnavailable`, `OrderTakeExpired`, `OrderEscrowExpired`, `OrderNotFound`, `OrderCancelled`, `OrderNotAvailable`, `OrderWrongPassword`, `OrderNotPublic`, `OrderReadElsewhere`), `OrderRequestRefused` with the number for any other code or an empty `400`, and the robot failures of the authentication. Codes are read on a `4xx` answer only.
- A take or a cancel fails with an `OrderActionFailure`: `OrderActionRefused` when the failure is known to come before the action (nothing was done), `OrderActionOutcomeUnknown` otherwise, since the answer is the read that follows the action and may fail after it happened: read the order again. An `Error` the transport throws on such a `POST` is an outcome unknown too, not a crash.
- A `POST` is sent once: the client never sends it again, whatever the outcome, a timeout included, and the transport never retries a request that is not a `GET`.
- Known limit: the short header carries no Nostr key, so a read never replaces the all-zero placeholder key a coordinator may hold for the robot (`robosats/middleware.py:98-107`).

## Coordinator client: the encrypted chat of a trade

Nothing in the app calls these yet (#92): the chat use cases of #93 will. The API chat only; whether Troc also sends to the coordinator's Nostr relay, as the official client does, is an open decision (design note § 3.6).

- `CoordinatorClient.fetchChat({identity, lastRead, offset})` is the reference client's poll, `GET /api/chat/?order_id=&offset=` with the robot's short header and session (`frontend/src/components/TradeBox/EncryptedChat/EncryptedApiChat/index.tsx:133-136`, commit ff1998c), and `postChat({identity, lastRead, message, offset})` its post, `POST /api/chat/` with `{"PGP_message":…,"order_id":…,"offset":…}` (`EncryptedChat/index.tsx:259-267`). Like `cancelOrder`, both take the robot and the last read of the order, which gives the coordinator, the network, the order and the peer.
- Before anything is sent, a request is refused when the last read is another robot's (`OrderReadElsewhere`), does not show this robot as the maker or the taker with a named peer (`ChatRefused(notParticipant)`), or is not at a status where the coordinator takes it (`ChatRefused(notInChat)`: reading at 9, 10, 11 and 16, posting at 9 and 10, `chat/views.py:56-62`, `:136-137`), when the offset is outside 0 to 2,147,483,647 (`offsetOutOfRange`), and, for a post, when the message was encrypted by another robot (`messageOfAnotherRobot`).
- What is posted is never free text: an `OutgoingChatMessage`, which only `UnlockedRobotPgpKey.encryptChatMessageToPost(plaintext, peer:)` makes: the official client's `encryptMessage` (to the robot and the peer, signed by the robot; the robot token refused in the text), its line feeds turned into backslashes, at most 5,000 characters on the wire (`maxWireChars`, the `max_length` of the coordinator's model, `chat/models.py:389`, which the reference coordinator does not enforce): about 3,250 bytes of text. It carries the robot that made it and the fingerprint of the peer key it was encrypted to.
- A page (`ChatPage`) holds `peerConnected`, the peer's key and the messages above the offset, in the coordinator's order. Each `ChatMessage` has its `index`, `time`, `nick`, who sent it by that nick (`ChatSender.self`, `peer`, or `unknown` for a nick that is neither, which no honest coordinator sends), and its content: a `PGP MESSAGE` with its line feeds restored (`armored`), or, without any text, `notPgpMessage` (ignored by the official client) or `tooLong` (over 65,536 characters).
- What only the coordinator chooses and no honest one sends refuses the page (`CoordinatorResponseMalformed`): a field of the wrong type, an index not above the offset or over 2,147,483,647, a time out of range, a nick outside the robots' alphabet (`A-Z`, `a-z`, digits, `-`, at most 18), more than 2,000 messages, a body over 4 MiB. What the reference itself can produce is stated, not refused: its query has no order and it numbers posts `count + 1` without a lock (`chat/views.py:64`, `:158-166`), so pages say whether they are `inIndexOrder`, `repeatsAnIndex` and `isContiguous`, and give `lastIndex`, which counts every message. What a peer chooses, the text of its messages, never refuses a page.
- The peer's key is a `ChatPeerKey`: `ChatPeerKeyOfPeer` (named `RoboSats ID <hash id>` after the peer of the last read), `ChatPeerKeyMisnamed` (any other name: another robot's key, this robot's own, the coordinator's), `ChatPeerKeyMissing` or `ChatPeerKeyUnreadable` (malformed, or over 20,000 characters and unread). The coordinator can replace it: pin the first one for the trade and compare every later one; a key it made in the peer's name from the first page cannot be told, but the peer's real messages do not verify with it.
- Line breaks: `pgpArmorToWire` and `pgpArmorFromWire`, the one place for them, are the official client's `split('\n').join('\\')` and `split('\\').join('\n')` (tested against a reimplementation of both); an outgoing armor holding a backslash or a carriage return, which the one-line form cannot carry back, is refused.
- Refusals are kinds without coordinator text: `ChatRefused` with a `ChatRefusal` (6000 `orderIdMissing`, 6001 `notParticipant`, 6002 `notInChat`, 6003 `invalidRequest`, and the local ones), and the authentication's (`RobotUnknown`, `RobotCredentialsRejected`). For a post, each of them is an `OrderActionRefused`: the reference answers them before storing the message. Every other failure is an `OrderActionOutcomeUnknown` (the reference stores the message before it notifies and answers, and can fail with a `500` after storing): read the chat again from the offset posted with and look for the message with `ChatPage.indexOf(message)` before showing it as failed; sending it again sends the same value, whose duplicate a reader can tell by its text. Sent once, never again.
- Tests: answers derived from the reference code (`test/support/chat_answers.dart`, with a coordinator that behaves as `ChatView`), not recorded (no trade was made); a whole exchange between two test robots of published tokens; hostile pages (a replaced key, a replayed, reordered or relabelled message); every refusal and malformed answer; no coordinator or chat text in any failure or `toString`.
