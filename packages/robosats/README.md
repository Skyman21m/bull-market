# robosats

Pure-Dart RoboSats client primitives for Troc: the robot identity and OpenPGP key (see the library comment of `lib/robosats.dart`), and the read-only client of the coordinators described below.

## Coordinator client (read-only)

- `Federation.robosats` is the federation list embedded from RoboSats `federation.json` (commit ff1998c): each `Coordinator` has its aliases, description, contact, badges, policies, onion addresses and Lightning node keys per `RobosatsNetwork`. `RobosatsCurrency` maps the RoboSats currency ids to codes. Both are generated by `tool/generate_coordinator_data.dart`, and `Federation.problems` validates a list (in the tests, and asserted by `FederationBookReader` in debug builds).
- `CoordinatorTransport` is the port the app implements over Tor in `features/p2p`: one HTTP request in (`CoordinatorRequest`: method, absolute onion URL, headers, body, the largest body accepted), one `CoordinatorResponse` or a `CoordinatorTransportFailure` out. The adapter owns sessions, retries and the `User-Agent`; it must always complete without throwing, enforce a total deadline, stop reading at the body cap, give lowercase header names and not follow redirects (see the doc of `CoordinatorTransport`).
- `CoordinatorClient(transport)` reads one coordinator: `fetchInfo` (`/api/info/`, whose `network` and `node_id` are checked against the federation entry by `Coordinator.verifyIdentity`), `fetchBook` (`/api/book/`, optional currency and type filters, received orders outside them dropped, a `404` with `not_found` being an empty book) and `fetchLimits` (`/api/limits/`).
- `FederationBookReader(transport)` asks every coordinator at once: `requestAll` returns one future per coordinator, which screens should prefer; `read` waits for all of them and merges them into a `FederationBook` with one outcome per coordinator and every valid `PublicOrder`, tagged with its coordinator, by coordinator then id.
- Nothing is trusted: a body above `CoordinatorReadBounds`, a non-JSON body, an unexpected status or an invalid `/api/info/` field fails that one request with a `CoordinatorFailure`; an invalid book order or limits entry is dropped alone and counted, with a `DroppedOrderReason` per order (`OrderBook.dropped`) and a count of entries (`droppedEntries`). Only the first `CoordinatorReadBounds.maxOrders` orders of a book are read (`OrderBook.truncated`). Order dates must be valid ISO 8601 dates with a zone, between 2020 and 2100, at most 48 hours apart, and within 7 days of the injectable clock of the client. No failure and no `toString()` carries coordinator text.
- Free text from a coordinator (payment methods, notice, node alias, versions, alternative site and name, price sources) is capped in code points and cleaned when read: C0 and C1 control characters and DEL are removed, except tab, line feed, vertical tab, form feed, carriage return and next line, which become a space like the line and paragraph separators; Unicode bidirectional controls and unpaired surrogates are removed; accented letters and emoji are kept. It is still untrusted: show it as plain text, never as markup, and never log it.
- Tests run offline on responses recorded from the live federation (`test/fixtures/coordinator/README.md`), which include non-ASCII payment methods and a location; hostile cases are built by the tests.
- `FiatAmount` and `OrderAmount` share their names with types of `lib/core/exchange/domain/entity/order.dart` in the app, a different package: they are not renamed, so code that needs both imports one with a prefix.
