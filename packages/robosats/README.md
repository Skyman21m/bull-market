# robosats

Pure-Dart RoboSats client primitives for Troc: the robot identity and OpenPGP key (see the library comment of `lib/robosats.dart`), and the client of the coordinators described below: the public reads, and the robot of this device on a coordinator.

## Coordinator client: public reads

- `Federation.robosats` is the federation list embedded from RoboSats `federation.json` (commit e56f9cf7c, 2026-11-08: six coordinators, Gumpellite included): each `Coordinator` has its aliases, description, contact, badges, policies, onion addresses and Lightning node keys per `RobosatsNetwork`. `RobosatsCurrency` maps the RoboSats currency ids to codes (commit ff1998c). Both sources are unchanged at the protocol reference, commit babf62e (`babf62e2238f262182d0bf638496aaa53e286853`, 2026-11-15, since #174), which the code of this package was checked against: what it cites as « commit ff1998c » is exact there too, except in the few files `AGENTS.md` lists (« The RoboSats reference »). Both are generated by `tool/generate_coordinator_data.dart`, which records the source commit and Git blob id in each generated file, and `Federation.problems` validates a list (in the tests, and asserted by `FederationBookReader` in debug builds). How to refresh them, and the protocol reference, from a newer RoboSats commit: `AGENTS.md`, section "Troc (fork)", "Refreshing the RoboSats reference".
- Where the entry of Gumpellite comes from (checked on 2026-11-11 with the public GitHub API, the worked example of a new coordinator in that procedure). RoboSats pull request #2904 (commits `b2ad3cacb` and `ba25fe093`) was opened on 2026-11-06 and merged on 2026-11-08 by KoalaSat, a public member of the RoboSats organisation, with one review comment, by a contributor, about the missing Nostr key. It links the application issue #2685, opened on 2026-08-27 by a separate account, `GumpCoordinatorGit` (created about six minutes before, no public repository; the issue body was never edited), which gives the same mainnet onion address, mainnet node key and PGP fingerprint, and no testnet address. The Nostr key `84e6c796…c840` has no such trail: the issue leaves it empty, and it appears only in the maintainer's commit `ba25fe093`, after the maintainer asked the applicant to check SimpleX. The PGP key file was checked against its fingerprint only; the copy the issue links, on the applicant's own onion site, was not fetched.
- `CoordinatorTransport` is the port the app implements over Tor in `features/p2p`: one HTTP request in (`CoordinatorRequest`: method, absolute onion URL, headers, body, the largest body accepted, and the robot it is made for, if any), one `CoordinatorResponse` or a `CoordinatorTransportFailure` out. The adapter owns sessions, retries and the `User-Agent`; it must always complete without throwing, enforce a total deadline, stop reading at the body cap, give lowercase header names, not follow redirects, keep the requests of each robot on connections and Tor circuits of their own, and never log headers (see the doc of `CoordinatorTransport`).
- `CoordinatorClient(transport)` reads one coordinator: `fetchInfo` (`/api/info/`, whose `network` and `node_id` are checked against the federation entry by `Coordinator.verifyIdentity`), `fetchBook` (`/api/book/`, optional currency and type filters, received orders outside them dropped, a `404` with `not_found` being an empty book) and `fetchLimits` (`/api/limits/`).
- `FederationBookReader(transport)` asks every coordinator at once: `requestAll` returns one future per coordinator, which screens should prefer; `read` waits for all of them and merges them into a `FederationBook` with one outcome per coordinator and every valid `PublicOrder`, tagged with its coordinator, by coordinator then id.
- Nothing is trusted: a body above `CoordinatorReadBounds`, a non-JSON body, an unexpected status or an invalid `/api/info/` field fails that one request with a `CoordinatorFailure`; an invalid book order or limits entry is dropped alone and counted, with a `DroppedOrderReason` per order (`OrderBook.dropped`) and a count of entries (`droppedEntries`). Only the first `CoordinatorReadBounds.maxOrders` orders of a book are read (`OrderBook.truncated`). Order dates must be valid ISO 8601 dates with a zone, between 2020 and 2100, at most 48 hours apart, and within 7 days of the injectable clock of the client. No failure and no `toString()` carries coordinator text.
- Free text from a coordinator (payment methods, notice, node alias, versions, alternative site and name, price sources) is capped in code points and cleaned when read: C0 and C1 control characters and DEL are removed, except tab, line feed, vertical tab, form feed, carriage return and next line, which become a space like the line and paragraph separators; Unicode bidirectional controls and unpaired surrogates are removed; accented letters and emoji are kept. The rule is exported as `displayText`, so that an app cleans the text it shows from elsewhere, the embedded federation list for instance, the same way. It is still untrusted: show it as plain text, never as markup, and never log it.
- Tests run offline on responses recorded from the live federation (`test/fixtures/coordinator/README.md`), which include non-ASCII payment methods and a location; hostile cases are built by the tests.
- `FiatAmount` and `OrderAmount` share their names with types of `lib/core/exchange/domain/entity/order.dart` in the app, a different package: they are not renamed, so code that needs both imports one with a prefix.

## Coordinator client: the robot of this device

- `GarageKey.firstUsableRobot(fromIndex)` gives the first robot at or after an index that a coordinator can be contacted with, as a `GarageRobot` (index and `RobotIdentity`). It skips an index whose token fails the entropy rule of RoboSats, which the official client never contacts a coordinator with and whose automatic choice of a robot passes over, and an index whose hash id has no nickname; it looks at 100 indexes at most, as the official client.
- `CoordinatorClient.fetchRobot` is `GET /api/robot/` with the first-contact `Authorization` header (`Token <hash> | Public <key> | Private <key> | Nostr <key>`), which is what the official client always sends: a coordinator that does not know the token hash creates the robot with those keys, and one that knows it ignores them and answers with the keys of the first contact. `fetchKnownRobot` sends the short header (`Token <hash>`), which never creates anything and sends no key: a coordinator that does not know the robot gives `RobotUnknown`.
- The answer describes the robot of this device only when its `hash_id` and `nickname` are the ones derived from the token, compared before any key is parsed (`RobotHashIdMismatch`, `RobotNicknameMismatch`). Then `fetchRobot` gives a `CoordinatorRobot` that carries the pair it sent when the coordinator returned that very pair: the `public_key` with the fingerprints of the pair sent, primary key and subkey (a coordinator returns it re-exported by GnuPG, so the text differs), and the `encrypted_private_key` with its packets. Any other pair, and every pair `fetchKnownRobot` reads, which sends none, comes as an `UnprovenCoordinatorRobot`: nothing of the answer can be read from it, and only its `prove()` gives the `CoordinatorRobot`, which then carries the pair the coordinator holds, still locked (`pgpKey`, with `pgpKeyProven` true).
- `prove()` takes the pair only when its private key unlocks with the robot's token and holds the secret values of its public key, the two blocks being one key packet body for packet body, and each of its two secret parts is locked by an iterated and salted S2K (`ProtectedSecret.provesPassphraseWith`, which the parser requires and the proof checks again). That proves a holder of the token made the pair: a coordinator receives the SHA-256 of the token, never the token, and such an S2K is salted and iterated over the token itself; a simple S2K over SHA-256 would derive exactly the token hash, which is why no other S2K counts. « Proven » means that and nothing more: a coordinator can return any genuine pair of the robot it ever received, a different one at each read, and `pgpKeyProven` is its word, like `found`. The robot carries the pair re-encoded from the packets the proof checked (primary key, certified user ID, selected subkey, their signatures without unhashed area): anything else in the blocks is dropped. Any other pair is `RobotPgpKeyNotProven`: another token's pair, two blocks of two keys, a kind of key this package does not read, or a pair whose unlocking would hash more than `PgpLimits.proofHashedBytes`, 62 MiB for both secret parts and every S2K pass, checked before anything is hashed (a key of the official client or of Troc asks for 32 MiB; a pair GnuPG protected at its largest count asks for 124 MiB and is refused). `prove()` is synchronous: call it off the UI isolate. It wipes the passphrase and the secret values it unlocked. The official client adopts whatever pair the coordinator returns; this package never does.
- So a robot needs no stored key pair: a Garage Key restored on a new device, or read again after a restart, reads each robot back with its token, as long as the coordinator holds a pair the token proves. A pair returned as sent is taken without a proof, so send at a first contact only a pair made for that robot by `RobotPgpKey.generate` for that very request.
- A `PgpPublicKey` and a `RobotPgpKey` hold canonical armor only: the packets armored as the official client armors them, whatever armor they were read from. Armor headers such as `Comment` are accepted when reading and dropped, so only base64 and the two fixed lines ever go from a key into the `Authorization` header.
- Refusals are typed and carry no coordinator text: `RobotCredentialsRejected` (errors 7000, 7001 after a first contact, 7003, HTTP 401 and 403), `RobotKeysRefused` with a `RobotKeysRefusal` reason read from the code inside error 7002 (invalid key, key already used, key less than 12 hours old), `RobotNicknameTaken` (7004). Every other status is a `CoordinatorUnexpectedStatus`. After a 7004, `fetchRobot` asks once with the short header, in case the coordinator created the robot for another copy of the same request; that check can miss (the coordinator creates the user before the token) and a coordinator can answer 7004 for ever, so a caller asks again with `fetchKnownRobot` before it gives up an index, and bounds how many indexes one coordinator can make it give up.
- `CoordinatorRobot` holds what the screens need: `found` (the robot is more than five minutes old for the coordinator), the rewards, the stealth preference, the active or last order id, the last login, and the Nostr public key the coordinator holds with the formula it comes from (`nostrKeyDerivation`, `null` for a key that is not one of the robot). The Telegram and webhook fields are not read.
- The coordinator of the reference source stores the Nostr public key the first contact carries and checks no link with the token; it replaces it later only when the stored key is its all-zero placeholder. One testnet coordinator was seen to store either of the two formulas. Only `NostrKeyDerivation.currentFrontend` may be sent for a real robot: the secret key of the other formula is the token hash itself, which the coordinator receives on every request.
- Every authenticated request names its robot (`CoordinatorRequest.robot`, a `RobotSessionKey` that holds no credential and prints nothing), so the adapter can isolate it.
- The same token hash is the whole credential of a robot on every coordinator: a coordinator that receives it can act as the robot on another one in everything that needs the bearer alone, confirming that fiat was received included, which settles the robot's escrow there. This package contacts one coordinator per call and cannot prevent a caller from contacting several: the rule "one robot index, one coordinator" is to be enforced by the caller, in code, before any order (`AGENTS.md`, section Troc). Evidence and what was verified on live testnet coordinators: `docs/spikes/robot-coordinator.md`.

## Coordinator client: an order, the take and the cancel

Nothing in the app calls these yet (#84): they are the protocol calls of phase 2, for the trade use cases to come.

- `CoordinatorClient.fetchOrder` is `GET /api/order/?order_id=` with the robot's short header: a `CoordinatorOrder`, the order as the coordinator describes it to that robot (`OrderView.get`, `api/views.py:226-528`, commit ff1998c). Each field is read with the JSON type the view writes for that robot: the serializer's decimals are strings, but the raw `Decimal`s a view adds are numbers (a participant's coordinates, `premium_now`, the summary's amounts, `routing_budget_sats`), as Django REST framework's encoder writes them and the reference's OpenAPI schema says. Bounds are those of `PublicOrder`. Its status is one of the 19 of `CoordinatorOrderStatus`; the fields sent only in some statuses or to some robots are `null` when absent; the maker's text goes through `displayText`, the coordinator's labels (payout failure, swap refusal) become enums and are not kept, the Nostr keys accept the coordinator's `"None"`, and the hold invoices (`HoldInvoice`) are opaque strings of at most 2,000 visible ASCII characters, to be decoded and checked by the caller. The trade summary is read whole (`TradeSummary`: this robot's side, the peer's, the contract's figures and `trade_revenue_sats`), with the Lightning payout's payment hash and preimage (64 hexadecimal characters, or « processing ») and the on-chain payout's address and transaction, each bounded; an invalid side of the peer is dropped alone, an invalid own side or contract drops the summary (display only), never the order with it.
- The roles of an answer are checked against each other and against the robot that asked: maker and taker never both, `is_participant` agreeing with them, the maker's or the taker's hash id this robot's exactly when the answer says this robot is the maker or the taker, buyer and seller each the one the order's type and the role give, `ur_nick` this robot's nickname, the nicknames the ones the hash ids give, status 3 only for a pre-taker with its bond, a taker named once past a pre-take, a robot that is no participant shown a public order without any participant's field, a bond invoice only at the step that asks for it and an escrow invoice only to a seller at the escrow step. Any contradiction rejects the answer. The amounts and the invoices are not checked here.
- `takeOrder` and `cancelOrder` are `POST /api/order/?order_id=` with the reference client's JSON bodies: `{"action":"take","amount":0}` for a fixed order, the chosen amount as a JSON number for a range, `"password"` as the SHA-256 of the password in hexadecimal, given by the caller as an `OrderPasswordHash` (`OrderPasswordHash.of`, the same hash a make sends; since #245 the text never reaches the client). `PublicOrder.ofRead` gives the order as the book would list it from a read by a robot that takes no part in it, for an order no book lists, such as a password-protected one (#245). The cancel takes the last read of the order (`lastRead`), and always sends `{"action":"cancel","cancel_status":N}` with the status the coordinator stores, 1 for a pre-take shown as 3: without that guard, a cancel that lands after a taker's bond locked settles the bond (`api/logics.py:1108-1130`); with it, it is refused (1020). The reference's taker sends no guard: a deviation. A last read by another robot is refused before anything is sent.
- A take answered `200` is not always a take: the reference coordinator answers a take on an order that is no longer public with the order as it is (`api/views.py:595-596`). `takeOrder` gives `OrderTakeStarted` (status 3, this robot the pre-taker and not the maker, with its bond invoice), `OrderAlreadyTakenByThisRobot` (this robot was already the taker: do not drop the trade, its bond is at stake), or `OrderNotTaken`. A cancel that ends the order is answered `200` with a short body holding a `bad_request` text: `OrderCancelEnded`, never a refusal; any other accepted cancel gives `OrderCancelAccepted` with the order as it then is.
- Refusals are typed and carry no coordinator text: `CoordinatorOrderFailure`, one type per error code a take, a cancel or the read can get (`RobotHasActiveOrder` for 1000 to 1003, `OrderAmountOutOfRange`, `OrderTakePenalty` with the seconds of 1012 when the message has the reference's exact wording, `OrderStatusChanged`, `OrderNotCancellable`, `CoordinatorNodeUnavailable`, `OrderTakeExpired`, `OrderEscrowExpired`, `OrderNotFound`, `OrderCancelled`, `OrderNotAvailable`, `OrderWrongPassword`, `OrderNotPublic`, `OrderReadElsewhere`), `OrderRequestRefused` with the number for any other code or an empty `400`, and the robot failures of the authentication. Codes are read on a `4xx` answer only.
- A take or a cancel fails with an `OrderActionFailure`: `OrderActionRefused` when the failure is known to come before the action (nothing was done), `OrderActionOutcomeUnknown` otherwise, since the answer is the read that follows the action and may fail after it happened: read the order again. An `Error` the transport throws on such a `POST` is an outcome unknown too, not a crash.
- A `POST` is sent once: the client never sends it again, whatever the outcome, a timeout included, and the transport never retries a request that is not a `GET`.
- Known limit: the short header carries no Nostr key, so a read never replaces the all-zero placeholder key a coordinator may hold for the robot (`robosats/middleware.py:98-107`).

## Coordinator client: the buyer's payout, and the on-chain address checker

Nothing in the app calls these yet (#89): the payout use case of #90 will.

- `CoordinatorClient.submitPayoutInvoice` and `submitPayoutAddress` are `POST /api/order/?order_id=` with the reference client's JSON bodies (`frontend/src/components/TradeBox/index.tsx:276-308`, commit ff1998c): `{"action":"update_invoice","invoice":<signed>,"routing_budget_ppm":N}` and `{"action":"update_address","address":<signed>,"mining_fee_rate":R}`, with the robot's short header and session. Like `cancelOrder`, each takes the robot and the last read of the order (`lastRead`), which gives the coordinator, the network and the order.
- What is sent is never free text: a `SignedPayoutInvoice` or a `SignedPayoutAddress`, which only the robot's unlocked key makes (`UnlockedRobotPgpKey.signPayoutInvoice(invoice, network)`, `signPayoutAddress(address)`), clear-signed with the `Hash: SHA512` armor the coordinator splits on (`api/utils.py:628-648`). Each carries the text signed (`text`), its network and the robot that signed it. The invoice's shape is checked before signing (at most 2,000 printable ASCII characters, BOLT11 bech32 with a valid checksum, `lnbc` on mainnet and `lntb` on testnet, signet's `lntbs`, regtest's `lnbcrt` and any other prefix being another network, and an amount BOLT11 allows in whole sats: no leading zero, a `p` amount ending in 0; an invoice without an amount is `PayoutDestinationNoAmount`, since the coordinator refuses it, `api/lightning/lnd.py:508-512`), not its content, so a payout's text is ASCII by construction: decode, check and show that very string before signing it, and sign only what was shown.
- `BitcoinAddress.check(text, network)` is a pure, bounded pre-check of an on-chain address, and `signPayoutAddress` takes only its result. It accepts Base58Check P2PKH and P2SH (testnet's version bytes are shared by testnet3, testnet4, signet and regtest), segwit version 0 (bech32, 20 or 32 bytes) and taproot (version 1, 32 bytes, bech32m), with `bc` on mainnet and `tb` on testnet, and keeps the text exactly as given. It refuses with a `PayoutDestinationFailure`: `PayoutDestinationMalformed` (not an address of these kinds: whitespace, a URI, a private key, mixed case, a wrong length or padding), `PayoutDestinationBadChecksum` (most likely a typo, or the bech32 and bech32m checksums swapped, BIP-350), `PayoutDestinationWrongNetwork` (the other network, or regtest `bcrt`), `PayoutDestinationUnsupported` (a valid segwit address of version 1 with another length or of versions 2 to 16: BIP-350 makes them valid, but the coordinator's Lightning node wallet that pays the swap may not send to them). The coordinator's own bitcoind is the judge (`validate_onchain_address`, `api/utils.py:106-121`): this check exists to refuse an address of the wrong network or a mistyped one before anything is signed. The bech32 and bech32m checksums are written here (`lib/src/bech32_checksum.dart`, the BIP-350 reference algorithm): the `bech32` dependency checks bech32 only.
- `RoutingBudgetPpm` is 0 to 99,998 ppm, 1,000 by default (`LightningPayout.tsx:67-74`, `:281-286`); `invoiceSats(buyerSats)` gives the amount the invoice must be for, computed as the coordinator computes it (`api/logics.py:868-872`). `MiningFeeRate` is 2 to 500 sat/vB with at most 3 decimals (`api/logics.py:784`, `:794`, `api/serializers.py:687-689`), refused rather than rounded when the number is not exactly such a decimal, always sent; the coordinator's `suggested_mining_fee_rate` can exceed 500 (up to 1,000, `api/logics.py:630-634`), and `MiningFeeRate.of` then returns `null`: the panel (#91) offers at most 500 and says the coordinator suggests more than the client allows; `sentSats` gives what the address receives after the swap fee and 280 vB of mining fee (`api/logics.py:806-813`), which must be at least `minimumSentSats`, 20,000.
- Before anything is sent, a payout is refused (`OrderActionRefused`, with `PayoutRefused.fromLastRead` for the three decided from the last read) when the last read was made by another robot, the payout was signed by another robot's key (`PayoutSignedByAnotherRobot`) or is for another network, the last read does not show this robot as the buyer (`PayoutNotBuyer`) or at a step that takes it (`PayoutNotNow`: an invoice at 6 or 8, or at 15 once the failed invoice expired; an address at 6 or 8), or, for an address, does not offer the swap (`PayoutSwapUnavailable`: the reference coordinator would answer a `500`, `api/logics.py:800-803`). A last read may be stale: after a refusal with `fromLastRead`, read the order again and try once more from the fresh read before telling the user anything. A signed payout is not tied to an order or a step: sign just before submitting, from the fresh read, and never reuse one.
- An accepted payout is `PayoutAccepted` with the order as it then is, still this robot's as buyer. Refusals of the coordinator are kinds, never its text: `PayoutInvoiceRefused` with a `PayoutInvoiceRefusal` (empty, not an invoice, route hints unpayable within the budget, no amount, wrong amount, expired, already submitted, `unspecified`; the reference sends the Lightning node's refusals as bare `bad_invoice` texts without a code, compared with its exact wording and never kept), `PayoutAddressRefused` with a `PayoutAddressRefusal` (empty, invalid, unverifiable when the coordinator cannot reach its bitcoind, `unspecified`), `PayoutMiningFeeTooLow` (with the coordinator's minimum when its message has the reference's wording), `PayoutMiningFeeTooHigh`, `PayoutBelowDustLimit`, `PayoutSignatureRefused` (1048), `PayoutNotBuyer`, `PayoutNotNow`, and `OrderNotParticipant` (1047). Each comes before the coordinator records a payout (before the node's refusals and 3002 it may mark the order's unused `OnchainPayment` cancelled, and `payout_amount` may create one: harmless), so it is an `OrderActionRefused`; everything else (a `5xx`, a code of another action, an error of the read after the action, a malformed answer, a lost connection) is an `OrderActionOutcomeUnknown`: read the order again. Sent once, never again.
- Tests: the BIP-173 and BIP-350 vectors, Base58Check vectors, every one-character change of valid addresses refused on both networks, the network never confused; the signed text split back with a reimplementation of the coordinator's own rule; every refusal code and text from answers derived from the reference code, not recorded (no trade was made).

## Coordinator client: the chat step's actions

The trade use cases call them (`ChatStepActionUsecase` of `features/p2p`, #95 and #96).

- `CoordinatorClient.confirmFiat` (the buyer's « fiat sent », 9 → 10), `undoConfirmFiat` (« Payment failed? », 10 → 9), `openDispute` (9 or 10 → 11) and `ratePlatform` (« Rate your trade experience », a `PlatformRating` of 1 to 5 stars) are `POST /api/order/?order_id=` with the reference client's JSON bodies (`frontend/src/components/TradeBox/index.tsx:256-274`, `:315-317`, commit ff1998c): `{"action":"confirm"}`, `{"action":"undo_confirm"}`, `{"action":"dispute"}` and `{"action":"rate_platform","rating":N}`, with the robot's short header and session. The collaborative cancel is `cancelOrder` at 8 or 9, guarded as every cancel: the first ask raises the asker's flag (`askedToCancel`, `peerAskedToCancel` for the other side), the second side's ask ends the order (12).
- Before anything is sent, each is refused (`OrderActionRefused`, with `TradeActionRefused.fromLastRead`) when the last read was made by another robot (`OrderReadElsewhere`), or does not show what the action needs: the buyer (`TradeActionNotBuyer`) at 9 for `confirmFiat` and at 10 for `undoConfirmFiat` (`TradeActionNotNow`); a participant (`OrderNotParticipant`) at 9 or 10 for `openDispute`, whose `expires_at` minus 18 hours (`CoordinatorClient.disputeWindow`, a constant of the reference's code, `api/logics.py:500-501`) has passed by the client's clock (`DisputeTooEarly`); a participant for `ratePlatform`.
- The answer is `TradeActionAccepted` with the order as it then is, this robot in the same role, at a status the action can lead to (`api/logics.py`: 10 or later after « fiat sent », never 9 or 12; 9, or a dispute and what follows it, after its undo; 11 or later after a dispute); any other status is malformed, an outcome unknown, since the reference never answers `200` without acting. The coordinator's refusals come before it changes anything and are `OrderActionRefused`: 1013, 1027, 1029, 1031 (`TradeActionNotNow`), 1030 (`TradeActionNotBuyer`), 1054 (`DisputeTooEarly`), 1047 (`OrderNotParticipant`), the empty `400` of the form check and the authentication's refusals. Everything else is an `OrderActionOutcomeUnknown`, the codes of the other actions included (a 1043 or 1044 comes from the read that follows the action): read the order again, never send again. A second `confirm` by the buyer at 10 changes nothing on the reference coordinator, but the client never sends one by itself.
- `CoordinatorClient.releaseEscrow` (#96) is the seller's « Confirm {{amount}} {{currencyCode}} received »: the same body, `{"action":"confirm"}`, which the coordinator reads as the seller's because of the robot's role; it settles the escrow and pays the buyer (`Logics.confirm_fiat`, `api/logics.py:1686-1735`), and cannot be taken back. Nothing is sent when the last read does not show this robot as the seller (`TradeActionNotSeller`) or not at 10 with `is_fiat_sent` (`TradeActionNotNow`). The answer is done only at 13, 14 or 15 (`fiatReceivedFollows`): the reference answers `200` at 10 when it could not settle or check the escrow, or queue an on-chain payment (its function falls through to `return True, None`), so a `200` at 10 is an outcome unknown. Its refusals are 1027 and 1029 (`TradeActionNotNow`), 1028 (`EscrowBelowPayout`: the escrow not above the buyer's payout) and 1047, each answered before anything is settled. It is a money member: the trade use cases alone name it.
- Tests: every body, every refusal before sending, every code on every `4xx` status, the outcome unknown for everything that may follow the action; answers derived from the reference code, not recorded (no trade was made).

## Coordinator client: making an order and pausing it (#175)

The calls of a maker, for phase 3 (design note `docs/design/phase-3-making-an-order.md` § 3.1). The app calls each from its own use case: the make from the make use case of #179, the pause from the pause's of #184.

- `CoordinatorClient.makeOrder(coordinator, network, identity:, request:)` is `POST /api/make/` with the robot's short header and session (the reference sends the first-contact header, `frontend/src/models/Robot.model.ts:72-86`: put the robot on the coordinator first; a coordinator that knows the robot takes from that header only its Nostr key, to replace a placeholder key, `robosats/middleware.py:93-107`, which the short header does not carry) and the reference client's body, its 17 keys in its order (`Order.make`, `frontend/src/models/Order.model.ts:196-215`, commit ff1998c): `type`, `currency`, `amount` (`null` for a range), `has_range`, `min_amount`, `max_amount`, `payment_method`, `is_explicit` (false), `premium`, `satoshis` (`null`), `public_duration`, `escrow_duration`, `bond_size`, `latitude`, `longitude` (the meeting point, or `null` for each), `password` (the SHA-256 of the password, or `null`), `description` (or `null`). Numbers are written as JavaScript writes them, an integral value without a fractional part.
- What is sent comes only from a `MakeOrderRequest`, checked when it is made (`tryCreate`, `null` when a field is out of bounds) against what the coordinator stores as sent (`MakeOrderSerializer`, `api/serializers.py:587-627`, and the order model's validators, `api/models/order.py:77-184`), so that its form check, whose empty `400` says nothing of why, never refuses it, and so that its answer can be compared field by field: any currency but bitcoin (1000, the reference's « Swap? ## Coordinator client: the encrypted chat of a trade

The chat use cases of #93 call these. Messages are read from the API only; each message sent is also published over Nostr, as the official client does (#94, next section).

- `CoordinatorClient.fetchChat({identity, lastRead, offset})` is the reference client's poll, `GET /api/chat/?order_id=&offset=` with the robot's short header and session (`frontend/src/components/TradeBox/EncryptedChat/EncryptedApiChat/index.tsx:133-136`, commit ff1998c), and `postChat({identity, lastRead, message, offset})` its post, `POST /api/chat/` with `{"PGP_message":…,"order_id":…,"offset":…}` (`EncryptedChat/index.tsx:259-267`). Like `cancelOrder`, both take the robot and the last read of the order, which gives the coordinator, the network, the order and the peer.
- Before anything is sent, a request is refused when the last read is another robot's (`OrderReadElsewhere`), does not show this robot as the maker or the taker with a named peer (`ChatRefused(notParticipant)`), or is not at a status where the coordinator takes it (`ChatRefused(notInChat)`: reading at 9, 10, 11 and 16, posting at 9 and 10, `chat/views.py:56-62`, `:136-137`), when the offset is outside 0 to 2,147,483,647 (`offsetOutOfRange`), and, for a post, when the message was encrypted by another robot (`messageOfAnotherRobot`). The two decided from the last read carry `ChatRefused.fromLastRead`: the last read may be stale, so read the order again before telling the user.
- What is posted is never free text: an `OutgoingChatMessage`, which only `UnlockedRobotPgpKey.encryptChatMessageToPost(plaintext, peer:)` makes: the official client's `encryptMessage` (to the robot and the peer, signed by the robot; the robot token refused in the text), its line feeds turned into backslashes, at most 5,000 characters on the wire (`maxWireChars`, the `max_length` of the coordinator's model, `chat/models.py:87`, which the reference coordinator does not enforce). The text is checked before anything is encrypted: at most `OutgoingChatMessage.maxTextBytes` (3,250) bytes as `textBytesOf` counts them (UTF-8, a line feed counting two), else `PgpChatTextTooLong`; a screen can show what is left. The message carries the robot that made it and the fingerprint of the peer key it was encrypted to.
- A page (`ChatPage`) holds `peerConnected` (the coordinator's word, from the peer's last login within a minute, which the coordinator refreshes only every 2 minutes: an active peer can show as not connected), the peer's key and the messages above the offset, in the coordinator's order. Each `ChatMessage` has its `index`, `time`, `nick`, who sent it by that nick (`ChatSender.self`, `peer`, or `unknown` for a nick that is neither, which no honest coordinator sends), and its content: a `PGP MESSAGE` in canonical armor (`armored`: its packets decoded and armored again as this package and the official client armor them, so that no armor header the coordinator chose travels in it and the same packets always give the same text), or, without any text, `notPgpMessage` (not a `PGP MESSAGE`, which the official client ignores, or an armor that does not decode) or `tooLong` (over 65,536 characters).
- What only the coordinator chooses and no honest one sends refuses the page (`CoordinatorResponseMalformed`): a field of the wrong type, an index not above the offset or over 2,147,483,647, a time out of range, a nick outside the robots' alphabet (`A-Z`, `a-z`, digits, `-`, at most 18). What the reference itself can produce is stated, not refused: its model has no ordering and its query no `order_by`, and it numbers posts `count + 1` without a lock (`chat/models.py:56-58`, `chat/views.py:64`, `:158-166`), so pages say whether they are `inIndexOrder`, `repeatsAnIndex` and `isContiguous`, and give `lastIndex`, `contiguousIndex`, the highest index reached from the offset without a gap, which is the offset to poll from next (polling from `lastIndex` would let one message at index 2,147,483,647 hide every later one), and `contiguousIndexOverRepeats`, the same carried over the indexes the reference's numbering skips right after a repeated index, the offset to poll from once such a gap has held. A message shown again at a new index leaves the indexes in order and contiguous: `repeatsACiphertext` says that two messages of the page carry the same encrypted message in canonical armor, which catches it under another armor (a header, other line wrapping, trailing spaces, no CRC line); a coordinator that frames the packets again (another length encoding of the same bodies) passes that check, and only the decrypted messages tell it: `DecryptedChatMessage.signatureKey`, a `ChatSignatureKey` (the signer's key, the signature's time and the SHA-256 of the signed text, never the text), is the same for every framing of one validly signed message and differs for a message signed again.
- What a peer chooses, the text and the number of its messages, never refuses a page. Only the size can pass a bound: a page over 4 MiB (`CoordinatorReadBounds.chatBytes`, at least about 800 messages of the largest this package posts) is `ChatPageTooLarge`, since nothing bounds what a peer posts: a `200` answer over the bound, or one the transport stopped reading at the bound without saying its status; an error answer seen whole over the bound is `CoordinatorResponseTooLarge`, as for every other request. The package cannot read part of such a history: the coordinator answers every message above an offset at once, with no upper bound, and the indexes are known only by reading them. A later offset (the order's `chat_last_index` and below left out) reads only the newer messages, and skips those that may hold the payment details.
- The peer's key is a `ChatPeerKey`: `ChatPeerKeyOfPeer` (user ID exactly `RoboSats ID ` and the peer's hash id in lowercase hexadecimal, the only form the official client writes, `frontend/src/pgp/index.ts:26`, and the one the reference's test robots carry), `ChatPeerKeyMisnamed` (any other user ID: another robot's key, this robot's own, the coordinator's, or another spelling), `ChatPeerKeyMissing` or `ChatPeerKeyUnreadable` (malformed, or over 20,000 characters and unread). A key prints its fingerprint only, never the user ID its maker chose.
- **What the key check does not prove.** The name proves only that the coordinator did not hand over a key plainly named as another: the hash id comes from the coordinator too. A coordinator that gives each side, from the first page, a key it made in the other's name can read every message, change it, encrypt it again and sign it again both ways, and every message then verifies: the chat is then read and rewritten by the coordinator, payment details included. Pinning the key for the trade catches only a key replaced later. Only comparing both public keys outside the app, with the peer, catches a key replaced from the start, as the official client's « Don't trust, verify » dialog allows (`frontend/src/components/Dialogs/AuditPGP.tsx:107-151`); the package gives what it needs: the peer's `PgpPublicKey.armored` and `fingerprint` from `ChatPeerKeyOfPeer.key`, this robot's own from `RobotPgpKey.publicKey`.
- Line breaks: `pgpArmorToWire` and `pgpArmorFromWire`, the one place for them, are the official client's `split('\n').join('\\')` and `split('\\').join('\n')` (tested against a reimplementation of both); an outgoing armor holding a backslash or a carriage return, which the one-line form cannot carry back, is refused.
- Refusals are kinds without coordinator text: `ChatRefused` with a `ChatRefusal` (6000 `orderIdMissing`, 6001 `notParticipant`, 6002 `notInChat`, 6003 `invalidRequest`, and the local ones), and the authentication's (`RobotUnknown`, `RobotCredentialsRejected`). For a post, each of them is an `OrderActionRefused`: the reference answers them before storing the message, so it is the coordinator's word that nothing was stored. Every other failure is an `OrderActionOutcomeUnknown` (the reference stores the message before it notifies and answers, and can fail with a `500` after storing): read the chat again from the offset posted with and look for the message with `ChatPage.indexOf(message)`, compared in canonical armor. Found, the coordinator shows it as stored, whatever armor it shows it in; not found, it is not confirmed and may still reach the peer, never « not sent » nor « failed », since a coordinator can keep it out of this robot's pages, give it the peer's nickname, frame its packets again, or change one character of it. Sending it again sends the same value, whose duplicate a reader can tell by its text. Sent once, never again.
- Tests: answers derived from the reference code (`test/support/chat_answers.dart`, with a coordinator that behaves as `ChatView`), not recorded (no trade was made); a whole exchange between two test robots of published tokens; keys of the reference's own test robots, named as expected; hostile pages (a replaced key, a replayed, reordered or relabelled message, a replay under five other armors and with its packets framed again, an index at the largest value, a flood, an error answer over the bound); every refusal and malformed answer; no coordinator or chat text in any failure or `toString`.

## The chat over Nostr (#94)

The official client sends every chat message twice: to the coordinator in OpenPGP (above), and over Nostr (`onSendMessage`, `sendToNostr`, `frontend/src/components/TradeBox/EncryptedChat/index.tsx:201-239`, commit ff1998c). With its default setting (`connection = 'nostr'`, `frontend/src/models/Settings.model.ts:84`) and a Garage Key, it shows only the Nostr messages (`EncryptedNostrChat/index.tsx:102-163`): a message posted to the API alone does not show there. This package builds the Nostr copy; the app publishes it. Messages are still read from the API only: the official client never sends a message over Nostr alone (its `skipCoordinator` option has no caller), so the API has them all.

- `OutgoingNostrChatMessage.compose({identity, order, coordinator, network, text, now, random})` builds what `sendToNostr` builds: one NIP-17 rumor, kind 14, the text as content, `created_at` the current second rounded up, the tags `['order_id', '<shortAlias>/<orderId>']`, `['p', <peer key>, <relay>]`, `['p', <own key>, <relay>]` in that order, wrapped twice with NIP-59 (`nip59.wrapEvent` of `nostr-tools`: 2.25.2, the version the official client locks at commit ff1998c and the one this package was checked against; at commit babf62e it locks 2.26.0, whose `nip44.ts`, `core.ts` and `kinds.ts` are the same files as 2.25.2's, whose `nip59.ts` changes only `wrapManyEvents`, which the official client does not call, and whose `pure.ts` adds only a comment, read on 2026-11-16 for #174 in `nbd-wtf/nostr-tools` at `2027d15a39b7605e28ca22f54509cb767fd13751`, the first commit whose `package.json` says 2.26.0 with the dependencies the lock gives it (2.26.0 has no tag), against the tag `v2.25.2`: the repository was read, not the package the npm registry serves, which may differ): for the peer, then for the robot itself. Each wrap: a seal, kind 13, no tags, the rumor encrypted with NIP-44 v2 from the robot's Nostr key to the recipient and signed by that key; inside a gift wrap, kind 1059, one tag `['p', recipient]`, the seal encrypted with NIP-44 from a throwaway key, new for each wrap, and signed by it; the seal and the wrap each dated at a random moment of the last two days, never in the future. `relayMessages` are the two `["EVENT", <wrap>]` to send, `eventIds` the ids a relay's `OK` names.
- Nothing is built when the order lacks the maker's or the taker's Nostr key, or gives one that is no curve point such as the all-zero placeholder (`NostrChatKeyMissing`), when the key it gives for this robot is not the robot's own (`NostrChatKeyNotOurs`: the official client filters on the order's keys, so the peer would not see the message), when the coordinator has no onion address on the network (`NostrChatNoRelay`), or when a wrap would exceed a relay's `maxEventSize` of 65,536 bytes (`NostrChatMessageTooLarge`, out of reach with a text the chat accepts).
- The relay is `ws://<onion>/relay/`, as `getRelayUrl` writes it (`frontend/src/models/Coordinator.model.ts:374-378`). `nostrRelaysFor` chooses where to publish as `RoboPool.updateRelays` builds its pool (`frontend/src/services/RoboPool/index.ts:116-137`, commit babf62e; `:65-85` at commit ff1998c): the relay of the order's coordinator first, in the place the reference gives to the relay of the coordinator that serves its page, then relays drawn at random among the federation's until there are `min(3, n)`. A peer reads from a pool of its own drawn at random, and the coordinators' relays copy the gift wraps between them (`docker/strfry/sync.sh`, kinds 38383, 31986 and 1059, every minute).
- Since commit babf62e (RoboSats #2919, « Nostr relay auto-recovery »), the official client keeps its pool alive (`frontend/src/services/AGENTS.md`, « Connection resilience »): it reconnects for ever, sends its subscriptions again to a relay at each reconnection (`resubscribeAll`, `RoboPool/index.ts:375-385`), so that a peer whose connection dropped reads again the gift wraps addressed to it from 48 hours before its subscription was made (its `since`, computed once, `:535`), probes a relay silent for 10 minutes, and replaces a relay of its pool other than its page's coordinator's that stays down more than 10 minutes with one the draw left out (`maybeFailover`, `failoverRelay`, `:286-309`). Two limits: it holds on the web and desktop clients only, since on Android the bridge's socket has no `onOpen` and always says it is open (`Websocket/WebsocketAndroidClient/index.ts:38-40`, `:50`), so nothing is sent again there and the watchdog sees no dead socket (upstream `frontend/src/services/AGENTS.md`, « Android relay resilience is weaker than web »); and no release has it yet (`v0.8.8-alpha` is `e56f9cf7c`), so a peer on a published version behaves as at ff1998c. The pool is still drawn as above, and an event is still sent to every socket of the pool, a socket not yet connected being tried again every 500 ms (`sendMessage`, `:387-403`), with no `OK` awaited (`sendEvent`, `:622-626`); the messages and the relays' protocol are unchanged. None of it applies here: each publication opens its own connections to the relays `nostrRelaysFor` draws for it, and is not kept open.
- `CoordinatorClient.postChat(onSending:)` tells the caller when the post really leaves: `CoordinatorRequest.onSending`, which the adapter calls once when it starts writing the request's body on a connection it obtained to the coordinator, never when nothing is written (a refusal before sending, no place in the transport, no session, a connection that fails before the body; a request without a body never calls it). It must return at once; the app's adapter keeps whatever it throws from the request. The app starts the Nostr copy there, so that a message the coordinator never received is not published; one the coordinator receives and then refuses has its copy out already, as in the reference.
- `OutgoingNostrChatMessage.composeFor(sender, …)` composes from the robot's Nostr key pair alone, for an isolate that must not receive the robot's token (the app composes apart: four signatures, two ECDH and a throwaway key take about 160 ms on a desktop).
- `NostrRelayTransport` is the port the app implements over Tor in `features/p2p` (`TorCoordinatorTransport.publish`): one relay, one `NostrRelayPublication` (the events of a chat message, or of a rating of the coordinator, next section), a `NostrRelayOutcome` that is only a word for a log (`NostrRelayOk` reads a relay's `OK`). The official client neither waits for an `OK` nor tells the user anything.
- Primitives, in `lib/src/nostr/`, none of them exported: `Nip44` (NIP-44 v2 on `pointycastle`: ECDH on secp256k1, HKDF-SHA256, ChaCha20 RFC 8439, HMAC-SHA256, the padding), `NostrEvent` (NIP-01 ids and JSON written byte for byte as `JSON.stringify` writes them, the fields in `nostr-tools`' order), `NostrGiftWrap` (NIP-59), `Bip340` (BIP-340 signatures through the `bip340` package, each signature verified before it is returned). The robot's secret key stays in `NostrKeyPair`, which signs and computes conversation keys itself; the `bip340` package takes keys as hexadecimal strings, which cannot be wiped.
- Every random byte comes from the `Random` the caller passes (`Random.secure()` in the app): NIP-44 nonces, the signatures' aux, the throwaway keys, the dates.
- Dependency: `bip340` 0.3.0 (MIT, by fiatjaf, the author of Nostr; its own tests replay the official BIP-340 vectors), pinned exactly. Not 0.3.1: it requires `pointycastle` ^4, and the workspace is on `pointycastle` ^3 (`bip85_entropy`, `dart_pg`); the code of `lib/` is identical in both versions. Move to 0.3.1 when the workspace moves to `pointycastle` 4.
- Tests: the whole official NIP-44 vector file (`test/fixtures/nostr/nip44.vectors.json`, its checksum the one NIP-44 publishes) and the official BIP-340 vectors through `Bip340` (`test/fixtures/nostr/README.md` for their sources and licences); the message checked against the reference's fields and against what the official client requires to show it, opened by a reader that makes the checks of `nip59.unwrapEvent` (`test/support/nip59.dart`). Checked once against `nostr-tools` 2.25.2 itself on 2026-11-15, outside the repository (PR of #94): wraps built here verified and opened by `nostr-tools`, and wraps built by `nostr-tools` opened here.

## The rating of the coordinator over Nostr (#95, « Rate your host »)

At the end of a trade the official client rates the trade's coordinator on Nostr only (`rateHostPlatform`, `frontend/src/components/TradeBox/Prompts/Successful.tsx:54-105`, commit ff1998c).

- `CoordinatorClient.fetchReviewToken` is `POST /api/review/` with the body `{"pubkey": <the robot's Nostr key>}` and the robot's short header, as `Robot.loadReviewToken` sends it (`frontend/src/models/Robot.model.ts:220-245`). The coordinator answers `200 {"pubkey", "token"}` only when the robot's last order is at 14, 17 or 18 and the key is the one it holds for the robot, which it records when it holds none; otherwise a `400` (1052, « Robot has no finished order », `api/views.py:1236-1269`), read as `CoordinatorUnexpectedStatus`. Bounded at `CoordinatorReadBounds.reviewBytes`; sent once.
- `HostReviewToken` is the token: the coordinator's BIP-340 signature of the text `<robot's Nostr key><id of the robot's last order>` in lowercase hexadecimal (`Nostr.sign_message`, `api/nostr.py:164-175`). Only that form is accepted (128 characters of `0-9a-f`), so that nothing else reaches a public event; a `200` with anything else (the reference's `""` when its signature failed) is `CoordinatorResponseMalformed`. Readers check it with the coordinator's key (`verifyCoordinatorToken`, `frontend/src/utils/nostr.ts:131-149`); this package does not, as the official client does not before publishing.
- `OutgoingHostRating.compose(sender, {token, coordinator, orderId, rating, now, random})` builds the reference's event field for field: kind 31986, empty content, `created_at` the current second rounded down (`Math.floor(Date.now() / 1000)`), the tags `['sig', <token>]`, `['d', '<shortAlias>:<orderId>']`, `['p', <coordinator's Nostr key>]`, `['rating', <stars / 5>]` in that order, signed by the robot's Nostr key pair, its JSON in the order of the reference's template (`kind`, `created_at`, `tags`, `content`, `pubkey`, `id`, `sig`, which `finalizeEvent` fills in place; `NostrEvent.fullTemplateOrder`). `HostRating.tagValue` writes `String(stars / 5)` as JavaScript does: `0.2`, `0.4`, `0.6`, `0.8`, `1`. The kind is addressable (NIP-01, 30000 to 39999): a relay keeps the latest event of a key for one `d`, so a new rating of the same order replaces the earlier one.
- What it makes public: anyone reading the relays learns that this robot's Nostr key rated this coordinator for this order, with these stars.
- Tests: the event's fields, its signature checked as `verifyEvent` checks it, and its id for each number of stars, as `finalizeEvent` of `nostr-tools` 2.25.2 gave it outside the repository on 2026-11-16 for the robot of the fixtures and a token signed by a test key as `api/nostr.py` signs (`test/coordinator/host_rating_test.dart`); the request and each answer of `/api/review/`. Checked once against `nostr-tools` itself the same day: events signed here pass `verifyEvent`, and their JSON is byte for byte what `finalizeEvent` gives for the reference's template, the signature aside (its aux is random).

What a published rating makes public, for whoever reads the relays: the robot's Nostr key, the coordinator, the order id and the stars, with the time of the rating; that this robot completed a trade; through the order id, the public details of that order in the coordinator's book; and, since the event carries the coordinator's signature over the robot's key and the order id, a link that anyone can check. It is what the official client publishes, no more and no less.

## The recovery note of a Garage Key (#81)

When a Garage Key is entered, the official client reads on its relays a small encrypted note that says the index of the robot that key last moved to, and starts there (`recoverAccount`, `frontend/src/models/GarageKey.model.ts:89-119`; `subscribeAccountRecovery`, `frontend/src/services/RoboPool/index.ts:628-728`; `frontend/src/utils/accountRecovery.ts`, commit babf62e). This package writes and reads that note as the official client does, so that a key pasted there finds the robot this app left, and the other way round. The app writes and reads it on every coordinator relay of a network (`nostrRelaysOfNetwork`) through an `OwnSessionNostrRelayTransport` (below).

- The note is a NIP-59 gift wrap from the key's recovery identity to itself: `GarageKey.recoveryNostrKeyPair`, whose secret key is `sha256(sha512(key bytes))` (`getNostrSecKeyFromGarageKey`, `frontend/src/utils/garageKey.ts:120-122`). Its rumor is of kind 30078, with the tags `['d', 'robosats-garage-account']` and `['account', <index in decimal>]`, an empty content, and `created_at` the current second rounded down (`createAccountRecoveryEvent`, `accountRecovery.ts:12-30`). The official client also reads the notes of the legacy identity, `GarageKey.legacyRecoveryNostrKeyPair`, which hashed the hexadecimal text of the key (`getLegacyNostrSecKeyFromGarageKey`, `garageKey.ts:124-128`), and never writes with it.
- `GarageRecoveryNote.compose(key, {accountIndex, now, random})` gives an `OutgoingGarageRecoveryNote`, a `NostrRelayPublication` of one `["EVENT", <gift wrap>]` built by `NostrGiftWrap`, or `AccountIndexOutOfRange` for an index outside 0 to 2,147,483,647, where the reference throws. `composeFor(identity, …)` does the same from the recovery identity alone, for an isolate.
- `GarageRecoveryNote.filters(key)` gives the two requests of the official client, the recovery identity's then the legacy one's: `{"kinds":[1059],"#p":[<identity>]}` each, with no `limit` and no `since` (`RoboPool/index.ts:663-670`), as `GarageRecoveryFilter.toJson()`, to send in a `REQ`.
- `GarageRecoveryNote.latestNote(key, events)` reads the JSON texts of the events **one relay** answered to the two filters, in any order, duplicates included, and gives the latest note as a `GarageRecoveryReading`: its robot index and its rumor's `created_at`, or `null` (`latestNoteFor(identities, events)` for an isolate). `GarageRecoveryNote.latestOf(readings)` chooses among the readings of several relays with the same rule. The official client reads each relay apart and keeps one choice across them; reading each relay apart here too, each under its own bound, keeps one relay's events from hiding another's.
- A note counts for an identity when its wrap has a `p` tag naming that identity; it unwraps with that identity's key as `unwrapEvent` of `nostr-tools` does (`NostrGiftUnwrap`: wrap of kind 1059, seal of kind 13 whose id and BIP-340 signature verify as `verifyEvent` checks them, rumor of the seal's author); its rumor is that identity's (`RoboPool/index.ts:684-685`); and the rumor reads as `parseAccountRecoveryEvent` reads it (`accountRecovery.ts:32-53`): kind 30078, the first `d` tag `robosats-garage-account`, the first `account` tag a canonical decimal (`/^(0|[1-9]\d*)$/`, ASCII digits only) of a robot index. The content is not read, and a second `d` or `account` tag is ignored, as in the reference. A seal whose `pubkey` is not the identity is dropped before its signature is checked, which changes nothing to what counts. The choice is the reference's (`GarageKey.model.ts:103-109`): the latest rumor `created_at`, the larger index on a tie, whichever of the two identities wrote it; a note dated in the future is not set apart.
- Case, as `verifyEvent` reads it: the seal's `pubkey` must be lowercase hexadecimal (`validateEvent`), its `id` must equal the lowercase hash, its `sig` may be in either case (`hexToBytes` of `@noble/hashes`). A NIP-44 payload is read only in the canonical standard base64 with its padding, as `@scure/base` reads it, the decoder of `nip44.ts` (`Nip44.decrypt` refuses the URL-safe alphabet, which Dart's own decoder takes; both refuse a missing padding and non-zero padding bits). Before a signature is checked, the key must lift to a curve point and `r` and `s` be in `1..p-1` and `1..n-1`, the checks `schnorrVerify` of `@noble/curves` makes first; then nothing reaches the `bip340` package on which it could throw, but for a challenge of zero, which takes a SHA-256 preimage.
- Four points are stricter than the reference, each about a note only a holder of the key can make, and none about a note the official client writes (every one of its notes goes through `validateEvent` of `nostr-tools`, which throws on what these points refuse): the wrap must have the identity in a `p` tag, as every answer to the filter has; every tag of the rumor must be a list of strings (the reference would read `['account', 7]` as 7); the rumor's `created_at` must be an integer of at least 0 (the reference compares anything, and keeps a note dated -1 when its index is above the index it starts from); the seal's `kind` and `created_at` must be integers. Like `unwrapEvent`, the wrap's signature and the rumor's id are not checked.
- What the number read is worth. A note counts only when its seal is signed by one of the two identities, which needs the Garage Key: no relay and no third party who only knows the identity, which every relay sees in the `p` tag, can make up a number, raise it or date it in the future. What they can do: withhold notes, so that the number is older than the latest one, or missing; send old genuine notes again (harmless when the latest one also arrives, since only the rumor's date counts, never the wrap's); and flood the identity's `p` tag. **Older means smaller**: the official client writes the note only when it moves forward, so an older note names a robot below the last one, a robot that may already have served; taking it again is the money risk of this number, open to any relay, here as in the official client. Any holder of the key, on the other hand (another device, the official client, whoever has the key or the words it is derived from), can write any index dated at any time: a note dated far in the future wins over every later honest note, here as in the official client, and a device whose clock runs a few minutes ahead can win with a smaller index without any malice.
- Bounds against a hostile batch: one call of `latestNote` looks at the first `GarageRecoveryNote.maxEvents` (1,000) events of its list, every one counted, duplicates and refused ones included, and ignores the rest: what one coordinator's relay of the reference gives at most for the two filters (500 each, `maxFilterLimit`, `docker/strfry/strfry.conf:81-82`). The bound is meant for one relay's answer: a list that mixes several relays lets one relay, or a third party who floods one relay, push the others' notes past it. An event longer than `maxEventLength` (65,536 UTF-16 code units, the largest event a coordinator's relay of the reference takes) is skipped before it is decoded. The costliest event a third party can send now is encrypted to the identity, names both identities in its `p` tags and holds a seal that says it is the identity's, with a well-formed false signature: two key agreements and one signature check. A full batch of 1,000 such events took about 23 seconds in the project's tools container (about 6 to 10 ms per key agreement, 12 ms per signature check, on `pointycastle`), and 1,000 events whose seals are a third party's, now dropped on their author before any signature check, about 12 seconds; on a phone, count several times as much. Nothing read is thrown, logged or kept.
- Nothing prints the identity: `OutgoingGarageRecoveryNote` and `GarageRecoveryFilter` print their type only, since the identity is a fixed label of the Garage Key on every relay.
- Tests (`test/garage_recovery_note_test.dart`): the identities, the rumor (byte for byte, its id included), the size of the wrap (1,701 bytes for any index) and two notes, one built by `nostr-tools`' `nip59.wrapEvent` and one built by an independent Python implementation and read by `nostr-tools`' `unwrapEvent`, all from the design study of #81 (`test/fixtures/nostr/garage-recovery-note.json`, public test data of the BIP-39 test phrase « abandon … about »); every refusal of the reference and of `unwrapEvent`, the four stricter points, the case of each field, the readings and the choice among relays, and the bounds. `test/nostr/nip44_test.dart` checks the canonical base64.

### The relays of the note

- `OwnSessionNostrRelayTransport` is the port the app implements over Tor (`TorCoordinatorTransport` in `features/p2p`) for what belongs to no robot: `publishOnOwnSession(relay, publication)` and `readOnOwnSession(relay, filters)`, each on a Tor session of its own, opened for the call and closed after it, so that a relay ties a call to no robot, to no read of the books and to no other call; both always complete, never throw, within a bound of time, and a read is bounded in events, in bytes and in the length of a message.
- A read sends one `REQ` per `NostrRelayFilter`, each under its own subscription id (the filter's `subscriptionLabel`, `accountRecovery` for the note as in the official client, then `_` and a few random characters), keeps the events of those subscriptions until each has its `EOSE` or `CLOSED`, then sends a `CLOSE` for each. It gives a `NostrRelayRead`: the events' JSON texts as received, and whether the relay's answer was whole (`complete`: an `EOSE` for every subscription within the bounds). A relay that never ends, floods, cuts the connection or closes a subscription gives what it sent, incomplete.
- `nostrRelaysOfNetwork(federation, network)` gives every coordinator relay of a network, where the note is written and read; the official client's pool takes `min(3, n)` of them (`nostrRelaysFor`).

### What a caller must do

A caller of the relays must do what each point says; `RecoveryNoteSync` of `features/p2p` (#81, design note `docs/design/garage-key-from-the-words.md` § 3, « As PR 3 built it ») does it as the end of each point says.

- read off the UI isolate (`latestNoteFor` with the two identities), under one deadline for the whole reading, and call `latestNote` once per relay, then `latestOf` on the relays' readings, never one call on a list that mixes relays. The app reads every coordinator relay of the network at once, once per run, each on a Tor session of its own, its events in an isolate killed past its time (96 s for the whole reading), a relay whose reading fails counting as not answered; it records the floor relay by relay, the highest index read, at or above what `latestOf` would give. The official client gives up after 5 seconds over sockets already open; a new trade of the app, for a key never read for good on the device, waits at most 40 seconds, until a strict majority of the relays gave their whole answer (review of #302), the relays being reached through new Tor sessions;
- send the two filters without `limit`, and never use a wrap's date for anything. Done as written;
- never go below the robot index this device already knows for the key: the number read may be older, so smaller, than the last one (withheld note, drowned note, a clock running ahead on another device); for a pasted key with no history on this device, take it as « at least », never « exactly ». The app keeps the index read as a floor that only goes up, and takes for a new trade the first free index strictly above it and above every index in use;
- decide what to do with a note dated in the future (it wins for ever, as in the official client): at least never go below what the device knows. The app does not set it apart, as the official client, and never goes below what it knows;
- decide what to do with an enormous index, up to 2,147,483,647, before moving there: at the last index there is no next robot. The app takes it as any floor: at the last index the key has no robot for a new trade;
- decide when to write the note, and never write it with the legacy identity. The official client writes it when it moves to a new robot (`Garage.model.ts:287-294`) and after a make (`:547-569`); the app writes it, with the recovery identity only, after each make and take the coordinator confirmed and again at the first showing of the P2P tab in each run, with the highest index it knows for the key (robots in use and floor read), and only after a reading of that run that reached a majority of the relays, with the highest of what it knows and what that reading gave (review of #302). That does not cover two devices that read at the same moment, then write each, nor four relays of six that serve an old note while the two others are unreachable;
- treat the recovery key pair given to an isolate as a secret: it is enough to write notes that count. The app gives the isolate the identities only, never the Garage Key;
- log neither `GarageRecoveryFilter.publicKeyHex`, nor the identity, nor the events' text. The app logs fixed words only.
