# A robot on a coordinator (issue #28, first half)

Branch `feat/p2p-robot-coordinator`, 2026-11-11, revised the same day after the independent review of the pull request. Updated on 2026-11-12 by the first pull request of #29, which takes the key pair a coordinator returns once the robot's token has proved it: see "Taking the key pair back from a coordinator". Follow-up to [robot-identity.md](robot-identity.md), [pgp.md](pgp.md) and [tor-transport.md](tor-transport.md). Reference: RoboSats at commit `ff1998c` (v0.8.8) of 2026-11-06, so after the per-coordinator token of 2026-10-06 and its revert of 2026-10-15 described below.

This half makes a robot known to a coordinator and reads it back. It stores no key, shows no screen and moves no money: the Garage Key and the robots of the live runs were random, lived in memory only, and are gone.

## Summary

1. **A robot made by Troc exists on a real coordinator.** On 2026-11-11, temple on testnet (RoboSats 0.8.6) created robots from a first contact sent by this code over the embedded Tor, and returned the hash id and the nickname this device had computed, the OpenPGP key pair it had generated, and the Nostr key it had sent. Six runs, twelve throwaway robots, every step with the expected outcome.
2. **The coordinator accepts our OpenPGP key.** It returns the public key re-exported by GnuPG, with the same fingerprints, and the encrypted private key byte for byte. This closes the "Real coordinator" line of [pgp.md](pgp.md) for the creation of a robot, not for signatures and chat.
3. **The Nostr key question is settled.** The coordinator of the 0.8.8 source checks no link between the Nostr key and the token, and the one coordinator reached, which runs 0.8.6, stored the key of either formula as sent and kept the first one when the other came later. Two keys on one coordinator: no other key and no other coordinator was tried. Troc sends the formula of the official client since July 2025, `sha256(sha512(token))`. The other one, `sha256(token)`, must never be sent: that secret key is the token hash itself, which the coordinator receives on every request.
4. **A coordinator keeps the first keys it received, for good**, and the official client adopts whatever comes back. This package checks instead: another hash id or nickname is a typed failure, and a key pair other than the one just sent is taken only once the robot's token has proved it, `RobotPgpKeyNotProven` otherwise (#29, see "Taking the key pair back from a coordinator"). Seen live: a first contact with a second key pair for the same token gets the first key pair back; in these runs, before the proof existed, that was reported as `RobotPgpKeyMismatch`, the failure the proof replaced.
5. **Each robot has its own Tor session per coordinator**, apart from the anonymous sessions of the book. At most 32 robot sessions exist at a time, all coordinators together, at most two of them for one robot on one coordinator, and they are closed with the others or robot by robot.
6. **A Garage Key index whose token fails the entropy rule is skipped.** The official client has no such rule: the robot stays loading and its automatic choice moves on. The effect is the same.
7. **Not verified**: a second coordinator (lake on testnet never answered), mainnet (out of bounds), anything that needs an order (invoice, chat, reward), a phone, and the errors 7000, 7002 and 7004 on a live coordinator.
8. **A rule to enforce before any robot goes to a second coordinator, and before any order: one robot, one coordinator.** The token hash is the same credential on every coordinator, and the official client sends it to all of them at once. A coordinator that holds it can act as the robot on another coordinator in everything that needs the bearer alone, which includes confirming that fiat was received: that settles the robot's escrow there. It is a loss of funds, not a privacy nuisance. RoboSats changed that on 2026-10-06, in commits named after a security advisory, and reverted the change on 2026-10-15; the reference `ff1998c`, of 2026-11-06, comes after both, has no such code, and still describes the scheme in its notes for agents. See "The shared token hash".

## What was built

- **`packages/robosats`**: `CoordinatorClient.fetchRobot` (first-contact header, creates or reads) and `fetchKnownRobot` (short header, never creates), the `CoordinatorRobot` they return, the `CoordinatorRobotFailure` family, `GarageKey.firstUsableRobot` with `GarageRobot`, and `RobotSessionKey`, which every authenticated `CoordinatorRequest` carries.
- **`features/p2p`**: `TorCoordinatorTransport` keeps one Tor session per coordinator for the anonymous reads and one per coordinator and robot for the requests of a robot; `FetchRobotUsecase` and `CloseRobotSessionsUsecase` are registered inside the feature, for its coming Garage screens. No screen calls them, and the app-facing library `package:p2p/p2p.dart` has no robot method and exports no type that makes, holds or reveals a robot: shell code cannot generate or reveal a Garage Key through it.
- **Tests**: offline in both packages, and the opt-in live test `integration_test/p2p_robot_tor_test.dart`.

## The exchange

One endpoint, `GET /api/robot/`, and two forms of the `Authorization` header. Their structure, never their values:

| Form | Header value | Sent by |
|---|---|---|
| First contact | `Token <A> \| Public <B> \| Private <C> \| Nostr <D>` | `fetchRobot` |
| Short | `Token <A>` | `fetchKnownRobot` |

- `<A>`: the basE91 form of the SHA-256 of the robot token, 39 or 40 characters. It is the credential of the robot on every coordinator.
- `<B>` and `<C>`: the armored OpenPGP public key and the armored private key locked by the token, each on one line, every line break replaced by a backslash.
- `<D>`: the Nostr public key of the robot, 64 lowercase hexadecimal characters.
- The parts are separated by space, pipe, space; a coordinator requires exactly four parts or treats the whole value as the token hash (`robosats/middleware.py:51-59`).
- The other request headers are `Accept: application/json` and the transport's `Accept-Encoding: identity`; no `User-Agent`, no cookie, no body, no query.

What a coordinator does (`robosats/middleware.py:62-178`, `api/views.py:697-743`, `api/utils.py:496-669`):

| Situation | Answer |
|---|---|
| `<A>` is not 39 or 40 basE91 characters | HTTP 400, `{"error_code": 7000, "bad_request": …}` |
| `<A>` is unknown and the header is the short one, or a key is missing | HTTP 400, error 7001: nothing is created |
| `<A>` is unknown and a PGP key is refused | HTTP 400, error 7002, whose message holds the key error: 1034 (GnuPG or the shape check refuses a key), 1055 (public key already used by another robot), 1056 (key less than 12 hours old) |
| `<A>` is unknown, the keys are accepted, the nickname already exists | HTTP 409, error 7004 |
| `<A>` is unknown and everything is accepted | the robot is created with the hash id and nickname the coordinator computes from `<A>`, the public key as GnuPG re-exports it, the private key and the Nostr key as received; then HTTP 200 |
| `<A>` is known | `<B>`, `<C>` and `<D>` are ignored, whichever header is sent; HTTP 200 with the keys of the first contact |

Seen on the live coordinator: the short header on an unknown robot (error 7001), the creation, and a known robot under both headers. The errors 7000, 7002 and 7004 are read from the source and tested offline only.

The `200` body is the same in every case: `nickname`, `hash_id`, `public_key`, `encrypted_private_key`, `earned_rewards`, `wants_stealth`, `nostr_pubkey`, `webhook_url`, `webhook_enabled`, `webhook_api_key`, `last_login`, `tg_enabled`, `tg_token`, `tg_bot_name`, then `active_order_id` or `last_order_id` when the robot has one, and `found: true` once the robot is more than five minutes old. Nothing else tells a robot that was just created from one the coordinator already knew.

What the official client does with it (`frontend/src/models/Robot.model.ts:88-147`, `Slot.model.ts:40-101`): it sends the first-contact form every time, to every coordinator of the federation at once, with the same token hash and the same PGP key pair, and it replaces its local keys with the ones of the answer without any check.

## What this package does differently, on purpose

- **It checks the answer against this device.** The `hash_id` and the `nickname` must be the ones derived from the token (`RobotHashIdMismatch`, `RobotNicknameMismatch`), and they are compared before any key of the answer is parsed. The key pair must be the one this first contact sent (the `public_key` with its fingerprints, primary key and encryption subkey, and the `encrypted_private_key` with its packets, whatever its armor), or a pair the robot's token proves (`RobotPgpKeyNotProven` otherwise). A coordinator that returned a pair of its own would otherwise become the reader of the robot's chat without a sign.
- **It never adopts a key without a proof.** The second device of a restored Garage Key generates its own key pair; the coordinator ignores it and returns the first one, which is taken only once the robot's token has unlocked it: see "Taking the key pair back from a coordinator".
- **It sends canonical armor only.** A key object holds the canonical armor of its packets, base64 between the two fixed lines, as the official client writes it, whatever armor it was read from. An armor header such as `Comment`, which may hold any text, is accepted when reading and never kept, so it cannot add a fifth part to the first-contact header or put in it a character an HTTP header cannot carry. Refusing armor headers was the other option; it would have made the keys GnuPG writes with a `Version` or `Comment` line unreadable.
- **It checks a taken nickname before reporting it.** A coordinator that receives the same first contact twice at once creates the robot for one copy and answers the other with error 7004; the transport can cause that when it retries a request whose connection broke after it was sent. After a 7004, one request with the short header tells whether the coordinator knows this very robot. Tested offline only, and not airtight: see "What the next steps need to know".
- **It reads less.** The Telegram and webhook fields are ignored: Troc uses neither, and `tg_token` and `webhook_api_key` are credentials.
- **It contacts one coordinator per call.** Nothing sends a robot to the whole federation.

## Token entropy rule

The official client has no rule that skips an index (commit `ff1998c`). `Robot.fetch` returns before any request when the token fails `validateTokenEntropy` (`Robot.model.ts:99`) and never resets `loading`, so the robot stays "loading" for ever; `Slot.isReusable()` is `false` while loading, so `Garage.ensureReusableSlot` and `findNextUnusedAccount`, which looks at 100 indexes at most, move on to the next index. `Order.make` has no entropy check of its own.

`GarageKey.firstUsableRobot(fromIndex)` follows the net effect: it skips an index whose token fails the rule, over 100 indexes at most. It also skips an index whose hash id has no nickname (once in 2^54), a robot no coordinator can create; this second skip is Troc's own. A token that fails the rule cannot become a `RobotToken`, so no request of this package can carry one, as in the official client. No Garage Key is known that has such an index: the skip is tested through an injected derivation.

## The robot's Nostr key

**Answer: a coordinator expects neither formula. The coordinator of the 0.8.8 source takes any 64 hexadecimal characters, stores them at the first contact and changes them afterwards in one case only, a stored placeholder made of zeros. The one live coordinator reached, which runs 0.8.6, stored each of the two keys tried. Troc sends `sha256(sha512(utf8(token)))`, `NostrKeyDerivation.currentFrontend`, and must not send the other one.**

What "accepts any key" rests on, exactly: the source of one version, and two keys, the two formulas, on one coordinator of another version. No arbitrary key was sent, and no other coordinator answered.

Evidence, in three layers:

1. **The coordinator's code** (`robosats/middleware.py:29-37`, `:98-107`, `:126-172`): the key is whatever matches `[0-9a-fA-F]{64}` in the fourth part of the header, lowercased, stored when the robot is created. No signature is asked, and nothing relates it to the token hash or to the PGP key. For a known robot the received key is ignored, with one exception: when the stored one is the placeholder `000…0`, which the coordinator uses for a key it lost, the key of a later request replaces it (`:98-107`, at most every two minutes). That exception was not seen live.
2. **The coordinator's answers** (temple, testnet, every run):

   | Robot | Nostr key sent at the first contact | `nostr_pubkey` returned | Read back with the short header |
   |---|---|---|---|
   | A | `currentFrontend` | the same key | the same key |
   | A, already known | `repositoryFixtures` | still the `currentFrontend` key | |
   | B | `repositoryFixtures` | the same key | the same key |

   A coordinator that expected one formula would have refused or replaced one of the two. The only formula it could check is `repositoryFixtures`, whose secret it can compute; this one accepted the other without a word.
3. **The history of the official client** (public GitHub API, read on 2026-11-11): the Nostr key came with commit `e78d86feba` of 2025-04-27 ("nostr pubkey for Robot") as `sha256(token)`; commit `a71173abe3` of 2025-07-09 ("Simplify nostr key generation") changed it to `sha256(sha512(token))`, which is still the code at `ff1998c`. `tests/robots/1/nostr_pubkey` was last changed on 2025-05-31 (`ceead5315d`), before that change, and `development/docs.md:80` was never updated. So the fixtures carry the first formula, which the official client used for about ten weeks.

Why the first formula must not be used. Its secret key is `sha256(utf8(token))`: exactly the 32 bytes whose basE91 form is the `<A>` of every request. Any coordinator the robot contacts can compute that Nostr secret key, sign as the robot and read what is sent to it. The current formula hashes the token again through SHA-512 first, which a coordinator cannot reproduce from `<A>`.

What the choice changes in practice: the coordinator gives the stored key to the trade peer (`maker_nostr_pubkey`, `taker_nostr_pubkey`) and sends its notifications to it, and the robot reads them with the secret key its own client derives. A robot shared between Troc and the official client reads the same messages in both only with `currentFrontend`. `CoordinatorRobot.nostrKeyDerivation` says which key a coordinator holds for a robot, `null` when it is neither: a robot first created by a client of spring 2025, or one whose key the coordinator replaced by the placeholder.

Left in the code: `repositoryFixtures` stays in `NostrKeyDerivation`, to recognise such a key and for the test vectors. `CoordinatorClient.fetchRobot` still takes the formula as a parameter, for the live test; `FetchRobotUsecase`, through which the feature will make its first contacts, does not, so the app can only send `currentFrontend`.

Not verified: the current formula's output was not compared with the official client running. It is computed from the same specification by two independent implementations (the Dart code and the Node script of the vectors), and that is all.

## Does a real coordinator accept our identity and our PGP key?

**Yes, for the creation of a robot.** temple on testnet accepted every first contact this code sent: twelve robots over six runs, each with a key pair made by `RobotPgpKey.generate` minutes earlier and dated 24 hours back.

| What the coordinator checked or returned | Result |
|---|---|
| Token hash: 39 or 40 basE91 characters | accepted |
| Header split into four parts, keys with backslashes for line breaks, about 2 KB, sent by `dart:io` through the SOCKS port of the embedded Tor | accepted: the keys arrived intact |
| Public key: shape check, GnuPG import, age | accepted (the 12-hour rule is in the source at `ff1998c`; whether 0.8.6 already has it is not known) |
| Encrypted private key: GnuPG import without passphrase | accepted |
| `hash_id` computed by the coordinator from the token hash | equal to `RobotIdentity.hashId` |
| `nickname` computed by the coordinator's generator | equal to `RobotIdentity.nickname`, for twelve different robots |
| `public_key` returned | not the text sent: 693 characters for 694 sent, the re-export by GnuPG; same fingerprint of the primary key and of the encryption subkey, and `PgpPublicKey.parse` verified its self-certification and its subkey binding |
| `encrypted_private_key` returned | byte for byte the text sent, 923 characters |
| `nostr_pubkey` returned | the key sent |
| Short header before the first contact | error 7001, read as `RobotUnknown` |
| Short header after the first contact | the same robot |
| First contact again | the same robot |
| First contact with a second key pair for the same token | the first key pair comes back: `RobotPgpKeyMismatch` then; that pair is now proven by the token and taken (#29, not run live) |
| Short header five minutes and twenty seconds after the creation | the same robot, now with `found: true` (runs 2 to 6) |

The answer has 14 fields, in this order: `nickname`, `hash_id`, `public_key`, `encrypted_private_key`, `earned_rewards` (integer), `wants_stealth` (boolean), `nostr_pubkey`, `webhook_url` (empty string), `webhook_enabled` (boolean), `webhook_api_key` (`null`), `last_login` (`YYYY-MM-DDTHH:MM:SS.ffffffZ`), `tg_enabled` (boolean), `tg_token` (15 characters), `tg_bot_name` (24 characters). It weighs about 2.1 KB and comes as `application/json`. The offline tests build their answers on this shape, with the values of the public test robot of the RoboSats repository; no live answer is stored anywhere.

What this does not prove: that a coordinator accepts a clear-signed invoice or a chat message made by this code. Both need an order, which is outside this half.

## Tor sessions

- Anonymous requests keep one session per coordinator origin, as before. A request made for a robot uses a session kept for that robot on that coordinator, with its own HTTP client, so its own connections: no circuit and no connection is shared with another robot, with the same robot on another coordinator, or with the anonymous reads of the book.
- The guarantees of the transport are unchanged and apply to both kinds, since they share the code path: total deadline of 132 s, size cap, `http` to `.onion` hosts only, no redirect followed, no `User-Agent`, `Accept-Encoding: identity`, a `GET` retried at most twice on a new session of the same robot after a connection failure. `GET /api/robot/` creates the robot at most once, so a retry reads it back.
- At most 32 places are given to robot sessions at a time (`maxRobotSessions`), all coordinators together. A robot session holds its place from the moment it starts to open until it is closed, the sessions a connection failure replaced while a request still uses them included, unless it is given up as said below. Beyond the bound, a new session takes the place of one that is closing, or else of the least recently used one that no request is using or about to use, and opens only once that one is closed. The anonymous sessions are neither counted nor closed by this. The bound counts places, not the sessions of the embedded Tor: a session given up after the close timeout, and one whose opening was given up but that opens after all, exist there without a place until they end, with no request on them.
- **One robot has at most two places on one coordinator** (`maxSessionsPerRobotAndCoordinator`, issue #41): the session its requests use, and one more that a connection failure replaced while a request still uses it, or that is closing. A robot that has its two gets a third only in the place of one of its own that is closing; otherwise its request fails. The second review of the pull request showed why: a coordinator that dropped every second connection and held the others made each request of one robot keep a session of its own, took the 32 places with a single robot, and had the idle session of another robot closed to make room. It now takes two places per robot it was sent, and a robot that has two never has the idle session of another robot closed. The cap counts places, not Tor sessions: when the place of a closing session is handed over to a new session, of this robot or of another, it counts for that new session, so the robot can have a third session in the embedded Tor until the closing one has ended.
- **The robots of one coordinator hold at most 24 places together** (`maxRobotSessionsPerCoordinator`, after the independent review of the pull request), so the robots of all the other coordinators together always keep eight, whatever that coordinator does with their connections and however many robots callers send to it. The review showed the gap the cap per robot left: sixteen robots sent to one coordinator that held their connections took every place, two each, and had the idle session of a robot of another coordinator closed. Beyond its 24, a new session of that coordinator takes only the place of one of its own sessions, one that is closing or else its least recently used idle one, and fails with `CoordinatorTransportBusy` when there is none; no session of another coordinator is closed for it, and no session at all is closed while every one of its sessions is in use. Twenty-four is twelve robots with both of their sessions on one coordinator, far more than a person trades with at once, and a user who has more robots there gets their idle sessions recycled there, the least recently used first, as at 32. The first delivery had chosen no share at all, because a share reserved per coordinator (32 divided by the coordinators of a network) would have left four to six places to a user who trades on one coordinator; a ceiling leaves that user 24.
- **When no place can be had, the request fails with `CoordinatorTransportBusy`**, a retry after a connection failure included: every place is in use, the robot has its two places on that coordinator and neither session is closing, the robots of that coordinator have their 24 places and none of those sessions is closing or idle, or the session whose place was taken did not close in time. That failure is given for nothing else, and nothing was sent on that attempt. It does not say that the coordinator works: the places go to the requests in flight, so a coordinator that holds the connections of its robots, or drops them so that they are made again, uses up their places, up to the limits above. The rule for callers is an exponential backoff, a cap on the attempts of each request and on the attempts made to each coordinator, and busy answers that repeat on one coordinator read as a sign about that coordinator (see "What the next steps need to know"). `CoordinatorTransportFailed` stays what a refused URL or header, a request stopped by a close, or an answer that is not HTTP gives.
- **The opening of a Tor session is given the deadline of a request** (`coordinatorRequestDeadline`, 132 s, after the independent review of the pull request). Before, an opening that never completed kept its place for good, closes included: a second one after `closeRobotSessions` left that robot busy on that coordinator, thirty-two of them left every new robot busy until the app restarted, and every request that joined one stayed counted as waiting. Now the opening is given up at that deadline, its place comes back, the requests waiting for it fail with `CoordinatorUnreachable`, and a session that opens after all is closed unused. No new constant: a cold start of Tor, 62 s measured, fits in that deadline, and no request could use a session that opens later. The opening needs nothing from a coordinator (it waits for Tor to be ready, then binds a local SOCKS port), so only a broken embedded Tor makes it hang.
- **The close of a Tor session is given ten seconds** (`torSessionCloseTimeout`). A session that has not closed by then is given up and no longer counts. So a close that never completes fails the requests that waited for its place, every request waiting on the session that took it and not only the first, with `CoordinatorTransportBusy`, and loses no place for good; it no longer keeps `closeSessions` or `closeRobotSessions` waiting for ever. Until it really ends, such a session exists in the embedded Tor beyond the bound, with its HTTP client closed: nothing can be sent on it. Each session given up is counted, and the count is logged as a warning at 1, 2, 4, 8 and so on, without naming a coordinator, a robot or a session. Ten seconds were not measured: closing is local work in the embedded Tor, the end of a SOCKS listener.
- `closeRobotSessions` closes the sessions of one robot to every coordinator, and `closeSessions` closes everything, in both cases the sessions that a connection failure replaced while a request was still on them too. A request that was running fails instead of opening a new session, whichever session it was on, and a session that is still opening is no longer waited for: its place comes back shortly after the close has returned, not before, or once the session whose place it took has closed, and it is closed unused as soon as it opens. A request sent in the very instant a close returns may therefore still be told busy. A request that waited for the session whose place it took fails when a close stopped it, even if that session then did not close in time, and is told busy only when no close ran. The review of the pull request found the gap the first of these closes: a request left on a replaced session survived `closeRobotSessions`, and sent the credential again on a new session after a later connection failure.
- **`closeRobotSessions` is not a lock** (decision of issue #41). A request started after it was called goes through on a new session of that robot, and so does the second request of a `fetchRobot` whose first request had just been answered with error 7004. The transport cannot tell that second request from the next request of the robot, which must go through; closing the gap would take a notion of operation in the port of `packages/robosats`, and a delay after a close would fail honest requests. What can go out is that follow-up, a `GET /api/robot/` to the same coordinator, which already holds the credential: it is retried up to twice after a connection failure, so up to three attempts, each on a new session that nothing else shares and each carrying the short credential (the token hash). The session it leaves is idle but the most recently used, so the bound, which closes the least recently used idle session first, closes it last: it stays until the caller closes the sessions of that robot again. A caller that gives up a robot lets its calls end, or drops them, before it closes its sessions.
- Header names and values are checked before any session opens: an HTTP token for the name, printable ASCII for the value, at most 16 384 characters each (`maxHeaderLength`, issue #41), where the longest header of the API, the first contact, has about 2 000, and at most 32 768 characters for all the names and values of a request together (`maxTotalHeaderLength`, after the independent review). Anything else fails with `CoordinatorTransportFailed`, as does a request `dart:io` refuses to write, without a retry: its exception would quote the header value. Before the length was checked, a value of 200 KB was sent, and one of 2 MB failed as `CoordinatorUnreachable` after three sessions; before the total was checked, a hundred headers of 16 000 characters did the same.
- A request that carries an `Authorization` header without naming its robot is refused before any session opens, and the client of `packages/robosats` cannot build one. The guard looks at that header only: the chat websocket will carry the token hash in a query parameter, and the guard must be extended when it arrives.
- The log line of a retry gives the Tor reason and two counters only. It names neither the coordinator nor the robot, and a test reads what is printed to keep it so.
- **Not verified**: that two Tor sessions of the embedded Tor really use distinct circuits is a property of `bull_tor` and Arti that the tests take as given; the tests prove that the transport asks for distinct sessions and never mixes their connections.

## The shared token hash

**The fact.** `<A>`, the token hash, is the whole credential of a robot, and it is the same on every coordinator. At `ff1998c` (2026-11-06) the official client computes one `tokenSHA256` per robot (`frontend/src/models/Slot.model.ts:32`) and sends it to every coordinator of the federation at once (`Slot.model.ts:40-53` and `:89-101`).

**The consequence.** A coordinator that has received `<A>`, because the robot was sent to it, can present it to any other coordinator where the same robot exists, and is then that robot there for everything that asks for the bearer alone. On an order (`api/views.py:557-690`, all under `TokenAuthentication`) that is every action but the two that carry a PGP-signed text, `update_invoice` and `update_address`:

- `confirm`: when the robot is the seller and the buyer has marked the fiat as sent, it settles the seller's escrow and pays the buyer (`api/logics.py:1686-1736`, "KEY LINE - SETTLES THE TRADE ESCROW"). A dishonest coordinator working with the buyer takes the seller's sats without any fiat being paid.
- `cancel`, which can forfeit the robot's bond or cancel its trade, `dispute`, `submit_statement`, `undo_confirm`, `pause`, `take` and the ratings, and `POST /api/make/` for a new order.
- It also reads the robot (`GET /api/robot/`, the encrypted private key included, which stays locked by the token), its orders and the ciphertexts of its chat.

So this is a loss of funds for a robot that trades on one coordinator and was also sent to another, not a privacy nuisance. It is read from the source; it was not reproduced, and nothing here tests it.

**The evidence that upstream knows.** Read on 2026-11-11, in the clone and through the public GitHub API, the clone being shallow:

- Commits `551e228cc1` and `ec24f301c0` of 2026-10-06, both titled "Fix GHSA-22q8-9ghc-jg3h", made Garage Key robots send a distinct token hash per coordinator, "so that a compromised coordinator cannot replay the token at another one". Commit `51a65ef700` of 2026-10-15, "Revert fix", removed it. The advisory itself is not published.
- The reference clone postdates both: `ff1998c` is of 2026-11-06. Its code has no per-coordinator token (`deriveCoordinatorToken` appears in no source file), but its notes for agents still describe the reverted scheme as if it were in place: `frontend/src/models/AGENTS.md:36-47` gives the bearer as `sha256("robosats-coordinator-token:" + shortAlias + "|" + baseToken)` and states the property, "a malicious/compromised coordinator only ever sees its own `tokenSHA256`", "blocking the bearer-replay / escrow-settlement attack", and `frontend/src/utils/AGENTS.md:22` and `:184` still list `deriveCoordinatorToken` and forbid changing its prefix. Upstream named the attack, wrote the fix, and ships without it.

**What this client cannot fix by itself.** A coordinator cannot tell a replayed bearer from the robot. Troc could apply the reverted scheme on its own, but the hash id and the nickname come from the token hash: a robot made so would be a different robot on each coordinator, and no longer the one the official client derives from the same Garage Key index. That is a product decision, not taken here.

**The rule, to enforce before any robot goes to more than one coordinator and before any order: one robot index is bound to one coordinator.** The coordinator is recorded at the first contact of that index, and every later request for that robot is checked against it in code, not left to the screens. A robot that has no other coordinator has given its bearer to nobody who could replay it. The record needs storage, so the rule comes with the second half of #28, which wrote it: the feature's own database `p2p.sqlite` and the check in `FetchRobotUsecase` (AGENTS.md, « One robot, one coordinator »); still no screen and no app-facing method reaches the robot calls, so nothing in the app makes a first contact yet. The cost is that Troc does not offer what the official client does, one robot visible on the whole federation: an order on another coordinator takes the next index.

## Taking the key pair back from a coordinator (#29)

Added on 2026-11-12 by the first pull request of #29, offline only: the live test was extended (below) and not run.

**The problem.** Reading a robot back with the short header compared the coordinator's answer with a key pair the device had to hold, and the pair is stored nowhere: after a restart every read was `RobotPgpKeyMismatch`, and so was every robot of an imported Garage Key. Storing the pair in `p2p.sqlite` was the other option: its public key names the robot (`RoboSats ID <hash id>`), so the file would identify the robots and not only count them, and the robots of an imported key would still need a recovery path.

**The rule.** `fetchRobot` gives a `CoordinatorRobot` that carries the pair it sent when the coordinator returns that very pair, which it does when it creates the robot with it. Any other pair, and every pair `fetchKnownRobot` reads, since it sends none, gives an `UnprovenCoordinatorRobot`: nothing of the answer can be read from it, and only its `prove()` gives the `CoordinatorRobot`. `prove()` takes the pair when its private key unlocks with the robot's token and holds the secret values of its public key, the two blocks being one key packet body for packet body (`RobotPgpKey.parse` had compared them by fingerprint). Any other pair is `RobotPgpKeyNotProven`, which replaces `RobotPgpKeyMismatch`. The hash id and the nickname are still compared first, before any key of the answer is parsed.

**Why it proves who made the pair.** A coordinator receives `sha256(token)` in every request, never the token. Each secret part of the private key is encrypted under a key derived by an iterated and salted S2K over the token itself (RFC 4880 section 3.7.1.3), and checked by the SHA-1 of the plaintext; the unlocked values must then give the two public points. A coordinator that does not hold the token cannot make a private key the token unlocks, except by guessing that check, one chance in 2^160 per part; it can only return a pair the token holder made. Nor can it find the token from its hash: a token drawn from a Garage Key is 36 base62 characters, about 214 bits. The official client adopts whatever pair a coordinator returns (`Robot.model.ts:122-139`); this package does not.

**The S2K the proof rests on** (added after the independent review of the pull request). The argument above holds for the iterated and salted S2K only. A simple S2K (type 0) over SHA-256 derives exactly `sha256(token)`, the token hash every coordinator holds, so a coordinator could lock a key of its own under it and have it « proven »; a salted S2K (type 1) is a single hash of the token. The parser refuses both (`ProtectedSecret.read` accepts type 3 with its 8-byte salt only), and `RobotPgpKey.proveMadeBy` checks it again for both secret parts (`ProtectedSecret.provesPassphraseWith`: type 3, an 8-byte salt, SHA-1 or SHA-2, a coded count of 0 to 255, AES), so that the proof does not depend on the parser alone: the library that is to replace this OpenPGP layer must keep refusing them for a proof (AGENTS.md). Each of the two parts must unlock with the token: a pair whose primary part is locked by the token and the subkey's by anything else, or the reverse, is refused.

**What « proven » means, and what it does not.** A proven pair was made by a holder of the token, nothing more. A coordinator can return any genuine pair of the robot it ever received, and a different one at each read: the use case makes a new pair for every first contact the user asks for (a request sent again after a busy answer sends the same pair, #29 robot requests), and a coordinator that stores several (against the reference source, which keeps the first) can hand back any of them. So a proven pair is not necessarily the one the coordinator stored first, nor the one it will check signatures with. `CoordinatorRobot.pgpKeyProven` is the coordinator's word, like `found`: a coordinator makes it true after a first contact by returning another genuine pair, or the very pair sent in other packet framing; no screen may rely on it alone to say « this robot already existed ».

**What a proven pair holds.** It is re-encoded from the packets the proof checked: the primary key, the user ID it certifies with that certification, the selected encryption subkey with its binding, each signature without its unhashed area, which nobody signs. Anything else a coordinator put in the two blocks (another user ID, another subkey or a whole second key, a secret key left unprotected, padding up to the 20 000 characters a block may have) is dropped, so what a robot holds is bounded by the key its owner made: under 1 000 characters per block for a key of the official client or of Troc. A pair that comes back equal to the pair sent is taken as this device made it.

**Cost and bound.** Unlocking hashes the S2K count of each part, twice for SHA-1 or SHA-224 with an AES key longer than the digest. A key of the official client or of Troc asks for 32 MiB of SHA-256 in all. A proof hashes at most `PgpLimits.proofHashedBytes`, 62 MiB for both parts and every pass together, computed from the S2K parameters before anything is hashed: without it, a pair a coordinator made up could ask for 124 MiB of SHA-1 for its first part alone, which a proof spends before it can refuse. The bound refuses a pair GnuPG protected at its largest count (62 MiB per part with SHA-1 and AES-128, the case of `pgp_interop_test.dart`), which neither the official client nor Troc makes. The independent review measured, under JIT on the project's PC, 538 ms for the proof of an official pair, and 400 to 700 ms for a hostile pair at the largest count the bound allows, whatever its hash. The feature runs `RobotPgpKey.generate` and `prove()` in `Isolate.run`, through `RobotKeyComputePort`, never on the UI isolate. The answer is parsed before that, on the calling isolate: three parses, which cost up to about 80 Ed25519 verifications for a hostile block of 32 packets, about 300 ms measured by the review; since #69, a key block with more than 8 signature packets, where a robot key has 2, is refused before any is verified, so an answer costs at most 24 (not measured since).

**What stays in memory.** The robot keeps the locked pair only: the public key and the private key as the coordinator holds it, which is only as secret as the token. `prove()` encodes the token as the passphrase and wipes those bytes, and wipes the Ed25519 seed and the X25519 scalar it unlocked as soon as it has compared them with the public points; the S2K key and most of the decrypted buffer are wiped by the unlocking itself. Not wiped, and freed rather than cleared at the next collection: the token itself (a `String`), its bytes in the list `s2kIteratedSalted` builds the salt and the token from and in the hash's own buffers, the 20-byte check at the end of each plaintext, the big-endian copy of the scalar and the list made to reverse it in `x25519ScalarFromSecret`, the key objects of `pinenacl` that compute the public points, and whatever copies the runtime makes. What crosses to the isolate is copied there: to prove, the `UnprovenCoordinatorRobot`, which holds the token, the two blocks of the answer and public facts, and no longer the whole identity; to make a pair, the robot's whole `RobotIdentity`, its token, both forms of its token hash and its two Nostr secret keys included (taking only the token across would need a member that hands the token out of the identity to the feature, which its architecture test forbids). The isolate shares the heap of the app's isolates, so it keeps the screens fluid, it does not keep these apart in memory.

**What a dishonest coordinator can still do.** Return no robot, another robot (refused by the hash id or the nickname), or a pair the token does not prove (refused): the robot is then unusable on that coordinator, which is a denial of service, not a change of key. Return any genuine pair of the robot it holds, a different one at each read, and say through `pgpKeyProven` that the robot existed before (above). Make each read cost up to 62 MiB of hashing in a background isolate, and the parse of a hostile block on the calling isolate. Lie in the other fields of the answer (`found`, orders, rewards, Nostr key), which the proof does not cover. A pair returned equal to the pair sent is taken without a proof, which is sound because the device has just made that pair for that robot; `FetchRobotUsecase` makes it itself, so a caller cannot send another.

**Tests.** Offline, in `packages/robosats/test/coordinator/robot_test.dart` and `test/robot_pgp_key_proof_test.dart`: the three test robots of the RoboSats repository, whose tokens prove their official pairs; their pairs answered for another robot; a pair the coordinator made, locked by anything but the token, by the token hash through an iterated, a simple or a salted S2K; each of the two parts unlocked by the token alone, and genuine secrets moved to the other part; public and private blocks of two keys; a key of a kind this package does not read; secret values that are not those of the public key; a pair at the bound and pairs over it, refused before any hashing; both passes of SHA-1 with AES-256 counted; armor padded to the bound and over it; foreign packets and a second key dropped from a proven pair; a pair returned as sent, taken with no proof, and the same pair re-framed, proven; two genuine pairs handed back in turn; what each type prints; the S2K rule itself. In `features/p2p`: the use case and its order (binding, pair, request), the port replaced by a fake, the real isolate port, which leaves the calling isolate free while it hashes, and the whole path as the feature registers it (`robot_request_wiring_test.dart`: the real vault on an in-memory keystore, the database in memory, the real port). The live test `integration_test/p2p_robot_tor_test.dart` reads robot A back with nothing in memory, the robot derived again from the Garage Key and no pair given, and expects the pair of its first contact back, proven through the real isolate port; and expects the first contact with a second pair to give the first pair, proven. It does not drive `FetchRobotUsecase`, which needs a vault that a test can only make by replacing the keystore of the whole process. It has not been run.

## What the next steps need to know

**Storage (second half of #28)**

- **The coordinator of each robot index.** The rule of "The shared token hash" needs, per Garage Key index, the one coordinator the robot was sent to, written before the first contact leaves and read before every request. It is the first thing the storage must hold, and the check belongs in the use case, so that no screen can skip it. Done in the second half of #28; the PGP key pair below is not stored yet.
- A robot needs, per Garage Key index: the token (derivable from the Garage Key) and its PGP key pair. The key pair is random, not derived from the token: it must be stored, or recovered from a coordinator. A coordinator keeps the first key pair it received for good, so a robot whose key pair is lost can never get a new one on that coordinator. Done in #29: the pair is recovered from the coordinator at each read and not stored.
- The encrypted private key is only as secret as the token, and every coordinator the robot contacted holds a copy.
- Recovery on a new device: done in #29, as prescribed here. The short header, the answer's `encrypted_private_key` proven by unlocking it with the token (the only proof that the key was made by a holder of the token), then that pair taken for that coordinator: see "Taking the key pair back from a coordinator".
- A key pair is dated 24 hours back and a coordinator refuses one younger than 12 hours for its own clock: a device whose clock is more than 12 hours ahead gets `RobotKeysRefused(keyTooRecent)`.
- Generating a key pair hashes 32 MiB of SHA-256, 0.4 to 0.7 s on this PC in debug mode: off the UI isolate. Done in #29: `FetchRobotUsecase` makes and proves pairs through `RobotKeyComputePort`, run in `Isolate.run`.

**Garage screens (#29)**

- One robot, one coordinator: see "The shared token hash". The Garage screens must not offer the official client's robot on every coordinator; an order on another coordinator takes another index.
- `fetchRobot` creates an account on a third-party server that this client cannot delete.
- `found` is the only hint that a robot existed before; `activeOrderId` and `lastOrderId` say whether it can be reused.
- An unusable index is answered by the next robot of the Garage Key, `firstUsableRobot(index + 1)`.
- `RobotNicknameTaken` must not be answered that way at once. The client already asks once with the short header, but the reference coordinator creates the user (`robosats/middleware.py:152`) before the token (`:163`): a follow-up that lands between the two gets error 7001, and the failure is reported although the robot is being created for this device. So, before giving up an index, ask again with the short header a little later (`fetchKnownRobot`): if the robot is there, keep it. And a coordinator can answer 7004 for ever: cap how many indexes one coordinator can make the user give up, or it burns through the Garage Key.
- The failures need their own texts: today `CoordinatorRobotFailure` falls back on the generic book error in `p2p_failure_l10n.dart`.
- Close the sessions of a robot that is no longer used (`CloseRobotSessionsUsecase`), once its calls have ended or been dropped: a call still running may send one more request on a new session after the close, a `GET` up to three times, and the session it leaves is the last the bound closes, so close the sessions of that robot again once that call has ended.
- `CoordinatorTransportBusy` means "the request may be sent again later", and does not mean that the coordinator works: it comes when 32 robot sessions, all coordinators together, are in use at once, when one robot has two sessions in use on one coordinator, when the robots of one coordinator hold their 24 places, or when a Tor session did not close in time, and a coordinator that holds or drops the connections of its robots can cause the first three. The backoff on busy is not the job of the transport: send the request again with an exponential backoff, cap the attempts of each request and the attempts made to each coordinator, and take busy answers that repeat on one coordinator as a sign about that coordinator. Done in the domain since #29 (robot requests): `RobotRequestLimiter`, see AGENTS.md.
- Busy has no text of its own yet and falls back on the generic error in `p2p_failure_l10n.dart`: its text, which asks to try again later, comes with these screens.
- Bound how many robot requests run at once per coordinator, the polling of orders included: `RobotRequestLimiter` does it in the domain since #29 (robot requests), two in flight per coordinator and network. A coordinator that holds its answers keeps one place per request in flight until the deadline, two per robot at most, and up to 24 for all its robots; the transport keeps eight places for the robots of the other coordinators, but nothing smaller for the robots of that coordinator, which a coordinator that holds their answers leaves busy.
- `RobotPgpKey.parse` accepts armored blocks of up to 20 000 characters each, so a key pair padded with packets that parse ignores still parses, and gives a first-contact header of about 40 KB, which the transport refuses before any session since it is above 32 KB in all (measured by the independent review: 40 178 characters, against 1 757 for a key pair made by `RobotPgpKey.generate`). Settled in #29 without a new cap: a pair read from a coordinator is never sent back, since only first contacts carry a pair and `FetchRobotUsecase` makes a new one for each; and a proven pair is re-encoded from the packets its proof checked, so neither armor headers nor extra packets a coordinator pads a block with are kept.
- A coordinator that resets the connection right after accepting it gets most of its dropped requests classified as `CoordinatorTransportFailed`, without retry, rather than as connection failures (`CoordinatorUnreachable` after retries): `dart:io` raises an `HttpException` for most of those resets, which Dio does not report as a connection error, so the transport reads them as an answer that is not HTTP (seen by the independent review: 19 of 21 dropped requests). This is older than issue #41 and costs no session, since nothing is retried; the screens should not read `CoordinatorTransportFailed` as proof that a coordinator answered.
- Creating a robot is always explicit: only a first contact (`RobotContact.firstContact`) sends a key pair to `FetchRobotUsecase.execute`.
