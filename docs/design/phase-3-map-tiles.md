# « Show tiles » on the maps, issue #246: design note

**Status: design**, written on 2026-11-23, before any code of [#246](https://github.com/Skyman21m/bull-market/issues/246), without any request to a tile server, a coordinator or a relay, and without running Tor or the app.
Where the code later differs, the code and its pull requests are right, and this note is updated.
**Updated with the code** of [#263](https://github.com/Skyman21m/bull-market/pull/263): the port is named `MapTilePort` (`AGENTS.md`'s naming of non-repository domain interfaces); the tile zoom is Leaflet's, rounded; the memory holds the tiles' PNG bytes for one session of the switch; the meeting point's map keeps its switch while the create form is open, as the reference's; each change is said where it applies below, marked « (code) ».
The owner asked for the reference's « Show tiles » on both maps, off by default, the pinned point still randomized as today (issue #246, 2026-11-20).
**Decided by the owner on 2026-11-23** (comment on #246), after reading this note and its review: the tiles are fetched **outside Tor**, as the reference's Android app does by its code (option C of § 3), knowing that the provider then sees the phone's IP address and the area looked at, and that the real map undoes much of the point's randomization; options A (a change to `packages/bull_tor`) and D (no tiles) are not taken, and stay described below because they explain the choice.
The owner also decided, the same day, the three other questions of § 9: the name given to the tile server, `TumbleLark`, an anagram of « Bull Market »; tiles not kept beyond the app's life, as the reference; the reference's dialog word for word, with no line added. No question is left open.
Everything else here is a proposal of this note, said as « this note recommends ».
It was reviewed by an independent agent before merging; its findings are folded in.

Reference: RoboSats/robosats at commit babf62e (`babf62e2238f262182d0bf638496aaa53e286853`), the project's reference since #174 (`AGENTS.md:541`), frontend paths relative to `frontend/src/`.
Every line cited from the reference is at commit babf62e; of the files cited, only `components/Map/index.tsx` changed on the tiles since commit ff1998c (the tiles moved to `components/Map/osmTiles.ts`), and the locale files changed elsewhere than the lines cited.
Bull Market: `main` at `9a0d69ec6`. The `onion` package of `bull_sdk` is read at the commit the workspace pins (`1b01dc5e962c4c068fc4934b8125b839e2cd3264`, `pubspec.lock:1469-1477`).

**The decisive fact, in one line:** every SOCKS listener of the embedded Tor is opened onion-only (`packages/bull_tor/lib/src/data/onion_tor_backend.dart:17-31`, `SocksPolicy.onionOnly`, for the default listener at `:129-135` and `:405-419` with Snowflake, and for every session at `:309-313`), so the tiles of `tile.openstreetmap.org` cannot go through Tor without a change to `packages/bull_tor`; that change would be small, since the policy is chosen per listener and the Tor client has no destination filter for public hosts (§ 3), but the owner chose to fetch the tiles outside Tor instead.

(code) But the meeting point's dialog stays mounted in the create form (`<F2fMapDialog … open={openWorldmap}>`, `MakerForm.tsx:651-665`), so its switch and acknowledgment survive closing and opening the map again while that form is shown: opened again, it has its tiles on without the dialog; MUI unmounts the dialog's content while it is closed, so the tiles are loaded anew each time it opens. **The tiles** (Leaflet `^1.9.4`, react-leaflet `^5.0.0`, `frontend/package.json:89`, `:99`):
- the address `OSM_TILE_URL = 'https://tile.openstreetmap.org/{z}/{x}/{y}.png'`, with no subdomain (`components/Map/osmTiles.ts:1`);
- each tile fetched by `loadOsmTileBlob` with the global `fetch`, the header `X-Requested-With: RoboSats` (`OSM_TILE_APP_ID`, `osmTiles.ts:6-12`), `referrerPolicy: 'no-referrer'`, an `AbortController` that drops the tiles leaving the view (`osmTiles.ts:14-34`, `Map/index.tsx:30-76`); any status but `2xx` is a failed tile (`osmTiles.ts:16-18`), so a tile OSM refuses with HTTP 200 and an error picture (§ 4) is shown as it comes;
- the credit « © OpenStreetMap contributors » shown on the map (`OSM_TILE_ATTRIBUTION`, `osmTiles.ts:3-4`, its own `Control.Attribution({ prefix: false })`, `Map/index.tsx:78-93`, the map's default control staying off, `:242`);
- the tiles **in place of** the bundled countries, never under them (`{!useTiles && worldmap && <GeoJSON …>}` then `{useTiles && <OsmTiles />}`, `Map/index.tsx:245-256`);
- `maxZoom={15}` (`:239`); the book's map opens at zoom 1 (`:241`), the meeting point's at 6 on a saved point and at 2 without one (`MakerForm.tsx:664`), an order's place at 6 (`OrderDetails/index.tsx:291`);
- no cache of its own, client by client: on Android the WebView is set to `cacheMode = WebSettings.LOAD_NO_CACHE` (`android/app/src/main/java/com/robosats/MainActivity.kt:492`, in `secureWebViewSettings`, `:481`), set so that nothing is reused from a cache, and its cache is cleared with `clearCache(true)` when the activity is destroyed (`:656-661`); whether `LOAD_NO_CACHE` also stops the WebView from writing its cache is not established, and `onDestroy` is not called when the system kills the process; the desktop app sets nothing for its Electron session's cache (`desktopApp/index.ts`, its only `no-cache` being the page's own load, `:84`), so Chromium's default HTTP cache applies, which is kept on disk (Chromium's default, not read in code here); on the web, whatever the browser keeps, the tile `fetch` setting no cache mode (`osmTiles.ts:8-12`).

**Where the tile requests go, client by client** (the most important fact of this section):
- **Desktop app**: through Tor. `desktopApp/index.ts:110-113` sets `socks://localhost:9050`, the Tor it starts, as the proxy of the whole Electron session, so the tiles leave by a Tor exit relay, with Electron's browser User-Agent.
- **Android app**: **outside Tor, established by the code, not observed on a device.** The frontend runs in a WebView loaded from `file:///android_asset/index.html` (`android/app/src/main/java/com/robosats/MainActivity.kt:445`); Tor is the proxy of the OkHttp client behind the JavaScript bridge only (`HttpClientManager.setDefaultProxy`, `:289`); the WebView has no proxy (no `ProxyController` anywhere in `android/`), and the client installed once Tor is up overrides `shouldOverrideUrlLoading` only, with no `shouldInterceptRequest` (`:361-387`), so the tiles' `fetch` goes through the WebView's own network stack: the name resolved by the phone's DNS in clear, then the request from the phone's IP address, with the User-Agent `AndroidRobosats` (`:435`), `X-Requested-With: RoboSats`, and the cache off (`LOAD_NO_CACHE`, `:492`).
  The app's own agent notes say the opposite (`android/app/src/main/java/com/robosats/AGENTS.md:27-29`: « shouldInterceptRequest: allows file:///android_asset/ only; all other requests blocked »); the code wins, and if the notes were right the tiles would not show at all. The exceptions are outside the app: a system VPN, Orbot as a VPN (the « Use Orbot » option, `settings_use_proxy=false`), or a proxy set for the whole phone.
- **Web, over the onion**: the browser fetches the tiles itself. In Tor Browser they leave by a Tor exit, outside the federation; in an ordinary browser on the self-hosted client (`nodeapp/README.md`: only the API goes through the node's Tor) they leave in clear. This is the « Depending on your setup » of the dialog.

## 2. Today in Bull Market

**What draws the maps.** Both maps are drawn by the app, with no map dependency and no request (`AGENTS.md`, « The Map view of the book (#30) »): `MapChartView` (`features/p2p/lib/src/ui/map_chart_view.dart:30`) for the book, `LocationMapDialog` (`ui/location_map_dialog.dart:21`) for the meeting point, both painting with `MapChartPainter.paintWorld` and `paintPin` (`map_chart_view.dart:911`, `:943`; the dialog's `_LocationPainter`, `location_map_dialog.dart:318`).
The world is Natural Earth's 1:110m countries, about 42 KB, bundled (`features/p2p/assets/map/world_110m.bin`, read by `WorldMap.parse`, `domain/world_map.dart`), in Web Mercator as Leaflet projects it, zooms 0 to 15 (`domain/web_mercator.dart`: `tileSize` 256, `maxZoom` 15).
So the projection, the camera (`MapCamera`, `map_chart_view.dart:541`) and the tile size are already Leaflet's: a tile `z/x/y` maps onto the painter's world square with no new mathematics.

**The pinned point.** `MeetingPoint.randomized` (`domain/meeting_point.dart:17-29`) moves the place tapped by up to 0.05° on each axis (up to about 5.5 km north or south, less east or west away from the equator, so up to about 7.8 km diagonally at the equator), from `Random.secure` (`p2p_locator.dart:152`), then rounds it; the place tapped never leaves the dialog. Nothing reads the device's position; no permission is asked. #246 changes none of this.

**How the feature reaches the network today.** `TorCoordinatorTransport` (`data/tor_coordinator_transport.dart`) sends every coordinator request and every relay publication through the embedded Tor:
- each session comes from `tor().embedded.sessions.open()` (`:180`), a « circuit-isolated SOCKS route » of its own (`packages/bull_tor/lib/src/domain/entities/tor_session.dart`), with its own `HttpClient` built by `TorHttpClientFactory` (`packages/bull_tor/lib/src/data/tor_http_client_factory.dart:23-64`), whose only connection factory is SOCKS5, the host name sent to Tor unresolved, TLS done over the SOCKS socket for `https` (`:46-49`);
- one session per coordinator origin for the anonymous reads, one more per coordinator and robot for a robot's requests, so nothing ties a robot to another robot or to the anonymous reads (doc comment, `:88-91`);
- only `http` to a `.onion` host (`:110`, `_isOnion` `:209`), no `User-Agent` (decision of 2026-11-10, `:128-130`), `Accept-Encoding: identity`; the relay outcome is logged as a fixed label, never a relay, a robot or an event (`:125`).

**What fences it below.** In the `onion` package of `bull_sdk`, the policy belongs to each SOCKS listener: `TorSession::start(…, policy, …)` (`rust/src/api/session.rs:67-91`), checked on every `CONNECT` (`socks.rs:176`, `policy.allows(&addr)`, else `NOT_ALLOWED`); `SocksPolicy::Any` relays any destination and is the package's default, `OnionOnly` only hosts ending in `.onion` (`session.rs:20-54`, the Dart `SocksPolicy.any` and `.onionOnly`, `lib/src/rust/api/session.dart:30`); the Arti client itself is configured with `allow_onion_addrs(true)` and no destination filter for public hosts (`client.rs:141-143`; Arti's own defaults still refuse local and private addresses), and `open_session_with_connect_timeout(socks_port, policy, …)` takes the policy for each new session (`client.rs:198-222`).
`bull_tor` chooses `onionOnly` for every listener it opens (`onion_tor_backend.dart:31`), « refusing non-onion destinations » because a loopback SOCKS port has no authentication and any app on the device that finds it can use it (`:17-30`, the same warning at `session.rs:32-37`).

## 3. Fetching the tiles through Tor, or not

**Not possible through Tor without changing `packages/bull_tor`.** Every Tor session the feature can open is onion-only, and no onion service of OpenStreetMap's tiles was found (§ 4).
A tile request sent through today's path is refused at the SOCKS step (`NOT_ALLOWED`), so nothing leaks, and nothing shows.

**The options**, as this note set them before the decision:
- **C. Outside Tor, as the reference's Android app does by its code: decided by the owner on 2026-11-23.** For it: no change to Bull's code, faster, exactly what the reference's Android app does. Against it: the provider sees the phone's IP address, and the phone's DNS asks the name in clear.
- **A. A narrow change to `bull_tor`, feasible on paper, not tried; not taken**: a second way to open a session, with `SocksPolicy.any`, used only for tiles, every other listener staying onion-only. It would touch `bull_tor` alone (`OnionTorBackend.openSession`, `onion_tor_backend.dart:298-325`, and the `TorSessions` facade, `tor_controller.dart:60-66`), not `bull_sdk`, which already takes the policy per session (§ 2). Its cost: a change to Bull's own package, to carry across every update from Bull's releases, which this fork follows; and, while such a session is open, its loopback port would let any app of the phone that finds it reach any website through Tor, from a Tor exit, without seeing anything of the tiles: the exposure `onion_tor_backend.dart:17-30` narrows.
- **B. A second Tor client started by the feature itself** through `bull_sdk`, with `any`: no change to `bull_tor`, but a second bootstrap (Tor took 62 s on 2026-11-10, `tor_coordinator_transport.dart:27`), twice the memory and battery, the same loopback exposure, and a feature reaching past `tor.dart`, which the package forbids (`packages/bull_tor/lib/tor.dart`, header). Not recommended, not taken.
- **D. No tiles yet**: the switch not offered, as today. Not taken.
- Not an option for everyone: the user's own Tor, such as Orbot, which Bull can verify for its Electrum servers (`ExternalTor`, `tor_controller.dart:68-75`) and which filters nothing; the P2P feature uses only the embedded Tor (`tor_coordinator_transport.dart:180`). A user who runs Orbot as a system VPN gets the tiles through it anyway, as with the reference.

**What « outside Tor » means for the code (option C):**
- **Its own client**: a plain `dart:io` HTTPS client, direct, created for the tiles only and used for nothing else; never the coordinator transport's client nor either of the wallet's clients outside Tor, the one that reads the Bull price (`AGENTS.md:427`, `features/p2p/lib/public/p2p_wallet_port.dart:79`) and the one that talks to Bull's swap service (`AGENTS.md:382`, `p2p_wallet_port.dart:24`, `:34`, `:64`); nothing shared with the coordinator transport: no client, no header, no cookie (the client keeps none), no identifier, no robot or order data.
- **When it asks**: no request before the switch is on and « Acknowledged » pressed on that map; none while the switch is off, coming back to the screen included (every map opened starts with the switch off, as the reference; code: but for the meeting point's map opened again from the same create form, on without the dialog when it was left on, as the reference's dialog stays mounted in its form, § 1); only the tiles in view, nothing fetched ahead; the tile client is not even created before the switch is on and « Acknowledged » pressed on that map, and it is closed when the map closes or the switch goes off.
- **The DNS**: the name `tile.openstreetmap.org` is resolved by the phone's resolver, in clear, as the reference's Android app does: the network the phone is on sees it.
- **What stays from the rules written for Tor**: the tile source accepts only `https://tile.openstreetmap.org/{z}/{x}/{y}.png` with whole `z` from 0 to 15 and `x`, `y` within the zoom; no redirect followed; a response bounded in size (a tile is a few tens of KB) and decoded only as PNG; the headers set by the app, not by `dart:io`'s defaults (§ 9, question 2); kept in memory only (§ 7); nothing of the device's position read, no permission asked.
- **Transport**: HTTPS only, the certificate always checked (no `badCertificateCallback`), never a fallback to HTTP; bounded timeouts for the connection and for each wait for data; at most a few requests at once (6, as a browser's connections to one host), the others queued, so the use stays fair.
- **The picture**: before decoding, its PNG header (`IHDR`) is checked to be 256 × 256 pixels, since a small PNG can decompress into a huge picture and a bound in bytes is not enough.
- **The headers, exactly**: `User-Agent: TumbleLark`, `X-Requested-With: TumbleLark`, `If-None-Match` for an expired tile kept in memory, and a fixed `Accept-Encoding` (not `dart:io`'s default, which marks a Dart client), plus the `Host` that HTTP requires; nothing else, a test pinning the list.
- **The `ETag`**: the validator the provider sends with a tile and that a conditional request sends back could link, during the app's life, two successive IP addresses of the phone (Wi-Fi then mobile data) if it were particular to a client; whether OSM's `ETag`s are is not established. This note retains clearing the tile cache, `ETag`s included, when the device's network changes, or, if the code cannot see that change, when each map closes; the code's pull request says which. (code) The code cannot see it: tiles and `ETag`s last one session, from the switch turned on to the switch turned off or the map closed.
- **Screenshots**: the code's pull request decides whether `LocationMapDialog` is protected from capture while tiles show (§ 7).
- **Never logged**: no log line holds a tile's URL, its `z`, `x`, `y` or the view's bounds; only a fixed outcome label (loaded, refused, failed), as the relay outcome (`tor_coordinator_transport.dart:125`); a test pins it.
- **When a tile does not come**: a tile not there yet, failed or refused (HTTP 200 with `x-blocked`, § 4) leaves the countries drawn in its square; when tiles fail, one short line « Map tiles unavailable » (the app's text, the reference having none), and the next pan or zoom tries again; tiles do not need Tor, so they do not wait for it. (code) « The next pan or zoom » is one that changes the set of tiles in view, never a redraw of the same tiles; a refusal (`x-blocked`, or « Too Many Requests », 429) stops every request until the switch is turned off and on again, the map opened again included.
- **Speed**: not measured; faster than through Tor. A phone screen at one zoom needs about 6 to 20 tiles.

## 4. The tile provider

Pages read on 2026-11-23:
- the tile usage policy, <https://operations.osmfoundation.org/policies/tiles/> (no date shown);
- « Blocked tiles », <https://wiki.openstreetmap.org/wiki/Blocked_tiles> (last edited 2026-11-12);
- « Technical updates to the tile.openstreetmap.org service », community.openstreetmap.org, topic 133421 (2025-07-30);
- the OSMF privacy policy, <https://osmfoundation.org/wiki/Privacy_Policy> (last edited 2026-01-25).

What the policy asks of an app:
- the exact URL `https://tile.openstreetmap.org/{z}/{x}/{y}.png`, as the reference uses at commit babf62e; other hosts « may be slower or withdrawn without notice »;
- « a distinct, stable User-Agent naming your app », which « optionally includes a contact URL or email » (§ 3.1, example `MyTownMaps/1.4 (+https://example.org; contact: maps@example.org)`), the version not required; an app ID that the platform puts in `X-Requested-With` by itself is acceptable, a proper User-Agent still recommended (§ 3.1); a library's default (Dart's own, or flutter_map's `flutter_map (unknown)`) « will be blocked », and never another app's or a browser's (« never impersonate another app or a browser »); OSMF « may try to contact you (for example, via your User-Agent or public contact details) » before a block, which « may not always be possible » (§ 7);
- a `Referer` from websites; « Native apps usually do not have a referer, this is ok »;
- honour `Cache-Control`, `Expires` and `ETag`, « If your cache cannot read them, cache each tile for at least 7 days », « Use Conditional Requests using `If-None-Match` and `If-Modified-Since` when requesting tiles that have expired », « Keep a sufficient local cache to ensure that repeat views do not unneccessarily re-download tiles », never send `no-cache`;
- no bulk download, no prefetch of tiles not in view, no offline use;
- the attribution « clearly on the map », not hidden;
- under « You must not »: « tunnel all clients behind a single, anonymous identity » (said of proxies); caching proxies « generally » not recommended;
- best effort, « no SLA », and blocks without notice when use degrades the service; since 2025-07-30, a refused tile comes back as an error picture with HTTP 200 and an `x-blocked` header;
- OSMF « publish[es] anonymised, aggregated usage data for research and operations, including summary data on tiles accessed and websites/apps using the service ».

What it says of Tor: nothing; Tor, VPNs and exit relays are not mentioned.
What is known publicly: the wiki says Tor Browser sends no `Referer` from onion sites and suggests `X-Requested-With`, the header the reference sends, or another provider; the Tor blocks found (captchas, a Cloudflare challenge) concern the website and the editing API, not the tiles, which a community thread says Fastly serves.
**Not established** (no request was made): whether `tile.openstreetmap.org` serves requests from Tor exits today, at what speed, whether its automatic `Referer` block applies to a native app with its own User-Agent, and how long tile logs are kept (the privacy policy does not say).
No official onion service of the tiles was found.

## 5. What the provider learns

**In the option decided (C, outside Tor)**, for each tile request:
- **the provider** (OSMF and its CDN): the phone's IP address, so its network and a rough place, and whoever can tie that address to a subscriber can tie it to a person; the tile's zoom, `x` and `y`, so the area looked at, down to one tile of zoom 15 (about 1.2 km wide at the equator, less towards the poles), so a neighbourhood, at street level; the time; the headers sent, the name `TumbleLark` among them (§ 9, question 2), no `Referer`, no cookie;
- **a network observer near the phone** (the Wi-Fi, the operator): the DNS query for `tile.openstreetmap.org`, the HTTPS connection to OSM's CDN and the size and timing of each response, not the tiles' content; tiles differ in size, so an observer who compares those sizes with the public tiles could guess some of the tiles loaded, a known attack on maps over HTTPS that needs effort; and that the same phone uses Tor at the same time.

**What it reveals of a meeting point.** The coordinator publishes the point moved by up to 0.05° on each axis (§ 2), but the tiles the maker loads to aim show the true neighbourhood, at up to zoom 15, a few minutes before an order whose point lies within about 5.5 km on each axis appears in the public book. Whoever holds the provider's logs and reads the book can match the two by time and place, and so undo much of the randomization, down to about the width of a tile; outside Tor, the same logs hold the phone's IP address, which the coordinator itself never sees.
On the book's map, the areas looked at say where the user looks for a trade, with the phone's IP address.

**What reduces it**: no `Referer`, no cookie, and a fixed name, `TumbleLark`, shared by every user of the app (it groups them, it does not hide them in a crowd, § 9); the zoom capped at 15, as the reference; only the tiles in view, no neighbouring tiles fetched ahead; the cache in memory (§ 7), so a tile seen again is not asked again; nothing before the switch and the dialog.

**Had option A been taken** (through Tor): the provider would have seen a Tor exit's address instead of the phone's, the rest being the same; the exit relay, the host name and the response sizes; a network observer near the phone, Tor traffic only.

**Compared with the reference** at commit babf62e: its Android app, by its code, gives the provider the phone's IP address, `AndroidRobosats` and `RoboSats` with every area looked at, and the phone's DNS resolver the name, as option C does with its own name, `TumbleLark`; its desktop app gives an exit address, Electron's browser User-Agent and `RoboSats`; Tor Browser, an exit address.

## 6. The library

**flutter_map**, Leaflet's Dart counterpart (fleaflet.dev, BSD-3-Clause, 8.3.2 on pub.dev): not in Bull nor in the workspace's lock; it brings `latlong2`, `proj4dart`, `path_provider`, `uuid` and more; a disk cache on by default since 8.2 (up to 1 GB in the system's cache folder; `DisabledMapCachingProvider` turns it off); `NetworkTileProvider(httpClient: …)` takes a `package:http` client, so an `IOClient` over the Tor `HttpClient` would carry its requests; its weight was not measured.
Adopting it means rebuilding both maps on it: the camera, gestures, pins, groups (a plugin), screen-reader nodes and tests of #30 and #189, all already matching the reference.

**Tiles drawn by the existing painter**: a tile layer in `paintWorld`'s transform, drawn in place of the countries as the reference does: the tiles of the view at the camera's zoom rounded, as Leaflet does (`var tileZoom = Math.round(zoom)`, then `this._clampZoom(tileZoom)`, `src/layer/tile/GridLayer.js:552-557` of Leaflet 1.9.4), within 0 and 15 (code; this note first wrote « the whole zoom below the camera's »), fetched by a `MapTilePort` port of the feature (code; first written `MapTileSource`), decoded with `instantiateImageCodec`, drawn scaled, a repaint as each arrives, the requests for tiles that left the view dropped (the reference's `AbortController`).
No new dependency, the HTTP client fully the feature's own (headers, size bound, no redirect, no disk), the gestures and pins untouched; the cost is a small tile cache and its tests.

**This note recommends the existing painter**: a library is admitted where the reference has one, but here it would replace reviewed work, bring a disk cache to switch off and its own headers to override, and change nothing the user sees; outside Tor, flutter_map's own client would work as it is, which does not change this choice.

## 7. Cache and storage

- **Decided by the owner on 2026-11-23: nothing kept beyond the app's life, as the reference.** The reference's Android app reuses nothing and clears its cache on destroy (`LOAD_NO_CACHE`, `clearCache(true)`, § 1, with the two reserves said there); its desktop app leaves the tiles to Chromium's cache, on disk; this app keeps them in memory only, as the Android app, the deviation being that it reuses a tile while the app runs (below, § 8).
- **Memory only**: (code) the tiles' PNG bytes kept in a bounded cache (256 tiles, a few MB) for one session of the switch on one map, the decoded pictures only while their tile is in view (256 decoded tiles would take 64 MB), where this note first wrote decoded tiles for the life of the app's process; each with its `ETag` and expiry so that an expired tile is asked again conditionally (`If-None-Match`); nothing written to disk; the cache, `ETag`s included, cleared when the network changes (§ 3); the tile client is closed with the map.
- A disk cache would leave on the phone the list and pictures of every area looked at, the meeting place included, readable by whoever holds the unlocked phone or a backup; this note recommends against it.
- The policy expects tiles kept 7 days or per their headers; a memory cache honours the headers while the app runs and forgets at the next start. The volume is a few dozen tiles a session, far from bulk use. This shortfall is said in the pull request.

## 9. Decisions for the owner

1. **How do the tiles travel?** **Decided by the owner on 2026-11-23: outside Tor (option C), as the reference's Android app**, knowing what the provider sees (§ 5). Not taken: A, a change to `bull_tor` so that a session may leave onion services; D, no tiles for now.
2. **What name does the app give the tile server?** **Decided by the owner on 2026-11-23: `TumbleLark`**, an anagram of « Bull Market », fixed, without version, the same for every user, in `X-Requested-With` and in the User-Agent of tile requests only, where this note had recommended `BullMarket` (the owner: not to say who we are). What it changes: someone reading the provider's logs or its aggregated usage data per app (§ 4) without searching does not see the app's name; it does not hide the app from someone who searches, since this repository is public, this note says the label is an anagram of « Bull Market », and the code will write it. What it does not change: every user of the app stays under the same label, so it hides them in no crowd; with few users, the label still narrows who looks. Taking another app's label, such as `RoboSats`, would be impersonating it, which the policy forbids (« never impersonate another app »), and this note rules it out. **What is sent, as the reference and no more** (the owner's decision of 2026-11-23, « as RoboSats », for a contact or a URL beside the name). At commit babf62e the reference's tile request carries, of its own, only `X-Requested-With: RoboSats` (`osmTiles.ts:6`, `:9`) and `referrerPolicy: 'no-referrer'` (`:10`); its User-Agent is the client's: on Android the WebView's fixed `AndroidRobosats` (`MainActivity.kt:435`), on the desktop Electron's default (nothing set in `desktopApp/index.ts`), on the web the browser's; no contact, no URL, no version set by the code (no other header in `components/Map/`, `desktopApp/index.ts` or `MainActivity.kt`; Electron's default User-Agent usually carries the app's name and version, `RobosatsApp` 0.8.6 in `desktopApp/package.json`, a deduction not checked at run time). So the tile requests carry `X-Requested-With: TumbleLark` and the User-Agent `TumbleLark`, as the Android app's pair with this app's label, no `Referer`, no contact, no URL, no version.
What the policy asks, as written: a distinct, stable User-Agent « naming your app », a contact URL or email optional, no version required; so sending no contact is no deviation from it, only that OSMF then cannot warn before a block (§ 4). It does not say that the name must be the app's public name or brand, so a stable, distinct name with no displayed link to the brand reads as meeting it, a reading of the text and not a confirmation by OSMF. No public app of that name was found (a web search on 2026-11-23).
3. **Where are tiles kept?** **Decided by the owner on 2026-11-23**: not kept beyond the app's life, « if that is what RoboSats does »; it is what the reference's Android app does (§ 1, § 7), so memory only. The cost: below the provider's 7-day expectation, tiles asked again at each start.
4. **The dialog**: **decided by the owner on 2026-11-23**: the reference's text word for word, no line added (§ 8). What the provider learns stays in § 5 and in the trial guide.

Whatever the answers, showing the real map to aim at the meeting point undoes much of the point's randomization for whoever holds the provider's logs (§ 5).
