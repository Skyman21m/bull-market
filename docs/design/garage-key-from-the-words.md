# The Garage Key from the wallet's words: design note, issue #81

**What this note decides.** The RoboSats Garage Key is no longer drawn at random and backed up apart: it is the BIP-85 child of index 0 of the default wallet's words, and « New key » takes the next index. For everything else the app behaves as the official RoboSats client does with a pasted Garage Key: its account-recovery note finds the last robot, otherwise robot 0, and the user moves by hand. One note of our own, built like the RoboSats note, gives the number of the last key in use. Both notes are a help, never a guarantee.

**State.** Decided on 2026-11-26 (#81). PR 1, the derivation in `packages/secrets`, is merged (#289). PR 2 builds the move (§ 2, § 6, § 8: the shell's adapter and its fence, schema 10, the Garage on the keys of the words, the key the vault kept becoming the external key with nothing erased, the key arrows, « New key » and the display; « As PR 2 built it » at the end of § 8). PR 3 reads and writes the RoboSats note of § 3 on the coordinators' relays (« As PR 3 built it » at the end of § 3); the public relays of § 4, the lookups of #79 and our own note of § 4 and § 5 do not exist in the code yet: they describe what the pull requests to come will build, written in the present tense for readability. Where the code later differs, the code and its pull requests are right, and this note is updated.

References to the official client are to RoboSats at commit `babf62e`, relative to `frontend/src/` unless they start with `api/`, `robosats/` or `docker/`. References to this app are to the repository at the time of writing. What is deduced without being read is said to be deduced.

## 1. The derivation

```
Garage Key:  m / 83696968' / 82796679' / 0' / {network}' / {index}'
Note key:    m / 83696968' / 82796679' / 1' / {network}'            (§ 4)
```

- `83696968'`: BIP-85's own branch (BIP-85 2.1.0, § Specification); no wallet key lives there (deduced: BIP-85 does not say it, but no wallet derivation uses that branch).
- `82796679'`: the application number, « ROBO » in ASCII decimal. It names what is derived (a RoboSats Garage Key), survives a rename of the app, and follows BIP-85's advice for semantic numbers. It is not an application listed in BIP-85: another wallet reproduces the keys with a BIP-85 tool that accepts a free application number and a three-step sub-path, and with the vectors below.
- `0'`: purpose « Garage Key, this layout »; `1'` is the key of our note (§ 4). A later layout takes another purpose.
- `{network}'`: `0'` mainnet, `1'` testnet (BIP-44 coin types), from the enum `GarageKeySlot`. A robot's token does not depend on the network, so without this step robot *i* of the testnet key would be the mainnet credential.
- `{index}'`: **0 for the first key**, « New key » = index + 1, up to 2^31−1. The index is a required named argument, so no defaulted integer can choose a key.
- Every step is hardened. The deriver builds the path from the enum and one `int`, checks depth 5, hardening, application, purpose and network, and only then calls `bip85_entropy` (`CustomApplication.fromNumber`, `Bip85Entropy.derive`, as RecoverBull does). The check is necessary: on its own, `bip85_entropy` 1.0.2 accepts an unhardened step, any depth, and, as observed of `bip32_keys` during the design study and pinned since PR 2 (`packages/secrets/test/garage_key_derivation_test.dart`), reads « 2147483648 » without apostrophe as « 0' », so that the path with that unmarked step gives key 0 itself. No caller ever passes a path string.
- **Form of the key**: the first 32 bytes of the 64 bytes of entropy (BIP-85's HEX truncation, as RecoverBull). The official client accepts any 32 bytes: `bech32.encode('robo', …, 90)`, BIP-173 bech32, 63 characters (`utils/garageKey.ts:24-30`, validation `:46-68`); robots `m/44'/88'/{i}'/0` from `sha512(key)` (`:75-118`); recovery identity `sha256(sha512(key))` (`:120-122`). The app reproduces all three (`packages/robosats/lib/src/garage_key.dart`).
- **Seed**: the words of the default Bitcoin wallet of the environment, as the BIP-85 use cases find it, through `Deriver.bip85.root`. On testnet that wallet may have other words than the mainnet one; the testnet Garage then comes from those words. **A BIP-39 passphrase is refused** (`PassphraseUnsupportedFailure`, as for Silent Payments): default wallets are created without one (`lib/core/wallet/domain/usecases/create_default_wallets_usecase.dart`), and a Garage that the words alone do not restore is not this feature. A secret without words is refused too. A keystore that cannot be read never falls back to a random key.
- **Why BIP-85 rather than a home-made path.** Against an attacker, a correct hardened home-made path protects about as well. BIP-85 adds an HMAC that keeps the displayed value one-way from the tree even if a step were unhardened by mistake, keeps it from being a spending key, sits in a reserved branch, and is a reviewed standard already in the wallet.

**Vectors.** Computed by two independent implementations (Python standard library, with self-checks against the BIP-32, BIP-39 and BIP-85 texts, the repository's pinned keys and the RoboSats identity fixture; Node with `@scure/bip32`, `@scure/base`, `@noble/hashes`), recomputed from scratch by an independent reviewer, and pinned through the real library in `packages/secrets/test/garage_key_derivation_test.dart`. Inputs are public test data only: « abandon ×11 about », « legal winner … yellow » and the BIP-85 specification's master key. Main rows (« abandon ×11 about », no passphrase):

## 2. Custody and display

- **Derived on demand, never stored**, held in memory where a `NetworkGarageKey` is held today: nothing new at rest, and no false « delete » since the words recompute the key. What `p2p.sqlite` keeps is not secret: the indexes this device used and their `GarageKeyFingerprint`.
- **One exit in `packages/secrets`**: `secret.derive.garageKey(network:, index:)` returns `Result<GarageKeyMaterial, SecretFailure>`, with an `ArgumentError` outside 0 … 2^31−1 before any keystore read. The custody gate lists it as a sensitive symbol; PR 2 names its one caller, a small adapter in `lib/` (not `lib/core`) built under the same `withGarageKeys` flag as the vault handle, so never in the background isolate. Our note adds a second exit for the note key, in its own pull request. `lib/core/bip85` and `secret.derive.bip85.hex` are not used: the latter is not fenced by the gate and returns 32 bytes shaped like a Garage Key from another path, so PR 2's review checks that the adapter calls `derive.garageKey`, on the default wallet's secret, and nothing else. The derivation logs nothing.
- **Internal and external Garage Keys** (decided on 2026-11-26): an internal Garage Key is a key of the words, backed up by the Bull Wallet; the external Garage Key is the key the vault keeps in the slot of a network, the one drawn at random before #81 or one imported in « Robot recovery », one per network, not backed up by the wallet. It is never derived and never mixed with the internal ones: its fingerprint tells its robots and records apart, and it stays where it is, in the vault, with its robots and its trades. Since the decisions of 2026-11-26 on the mock-up, it trades as any other key, imported or not (§ 3).
- **« Show Garage Key »** (the `robo1…` text) stays behind the wallet's re-authentication, for every key, the current one and the earlier ones, hidden again when the app goes to the background, under screen-capture protection, copied only through `GarageKeyClipboard` (30 s). Moving between keys with the arrows of the Garage Key card (§ 6) asks no re-authentication, as moving between robots; only showing the text does. The line under the key is as short as the official client's « Store your Garage Key safely »: an internal Garage Key is « backed up by the 12 words of your Bull Wallet », the external one « not backed up by your Bull Wallet: keep a copy of it », with an ⓘ that opens the explanation (§ 6). Today's one exception, a key shown without re-authentication right after it is drawn, disappears with the wizard. #56 (clipboard not marked sensitive) should come first: the copy is the main way a key valid everywhere leaks.

## 3. What the official client does with a pasted Garage Key, and what this app does the same

**Entering a key** (`components/Dialogs/Recovery.tsx:60-92`, `basic/GaragePage/GarageKeyOnboarding.tsx:63-97`): `setGarageKey`, then `recoverAccountFromRelays` (`contexts/GarageContext.tsx:84-86`), then `createRobotFromGarageKey`, then `ensureReusableSlot({source: 'auto'})`, with a toast « Switched from Robot #{{fromIndex}} to #{{toIndex}} - previous robot has completed trades » when it moved (`Recovery.tsx:85`).

**Reading the note** (`models/GarageKey.model.ts:89-119`, `services/RoboPool/index.ts:628-728`): for the recovery identity and the legacy one (`utils/garageKey.ts:124-128`), a `REQ {kinds:[1059], '#p':[pubkey]}` with no `limit`, on the pool's relays: the coordinator relay of the host plus random coordinator relays up to min(3, n) (`RoboPool/index.ts:116-137`); done at `EOSE` from every relay or after 5 s. A note counts if it unwraps, its rumor is authored by that identity (`:684-685`) and it parses (`utils/accountRecovery.ts:32-53`: kind 30078, `d` = `robosats-garage-account`, canonical decimal `account`). It takes the latest rumor `created_at`, the larger index on a tie. With no note the index stays at `currentAccountIndex` (`GarageKey.model.ts:90`), which the constructor sets to 0 (`:49`).

**Presenting robots**: `createRobotFromGarageKey` (`models/Garage.model.ts:429-471`) builds a slot for every coordinator of the federation and fetches it on each (`GET /api/robot/` with the PGP keys): the coordinator creates the robot if it does not know it (`robosats/middleware.py:112-170`). `ensureReusableSlot` (`Garage.model.ts:233-298`) keeps a robot with an active order, with no order yet, or whose last order was cancelled or expired (`models/Slot.model.ts:293-309`); otherwise it moves to `findNextUnusedAccount(a+1)` (`:571-601`), the first index with no slot on the device or whose local slot is reusable again, creates it everywhere and publishes the note. It runs at start-up, when the Garage page opens and after a poll of the active order there, unless the user moved by hand.

**Writing the note** (`utils/accountRecovery.ts:12-30`: rumor kind 30078, tags `d` and `account`, content `''`, `nip59.wrapEvent` to itself): after a make the coordinator accepted (`Garage.model.ts:547-569`); at each automatic move; at « Change Robot & Take/Create Order », before the take or make is sent (`components/OrderDetails/TakeButton.tsx:155-163`, `components/MakerForm/MakerForm.tsx:315-323`). Not at a take with a reusable robot, not at the arrows. **The arrows** (`basic/GaragePage/GarageKeyProfile.tsx:50-62`, `Garage.model.ts:473-501`) move the index by one and create the robot on every coordinator.

**Beyond four weeks**: the relay of RoboSats' deployment repository erases every event older than 28 days (RoboSats/robosats-deploy, `compose/relay/sync_federation.sh`, since commit `1f6d1e5`; read during the design study, not part of the reference; what each coordinator runs is not established, § 9). nostr-tools, which the official client uses, dates a wrap up to two days back (as NIP-17 recommends), so a note lives 26 to 28 days on such a relay. After that the official client starts at robot 0. The reference's relay configuration clamps an answer at 500 events (`docker/strfry/strfry.conf:81-82`) and copies kind 1059 between coordinators (`docker/strfry/sync.sh`). No coordinator refuses a robot it already knows: it logs any known token in and creates a robot only for an unknown one (`robosats/middleware.py:78-175`). Coordinators keep indefinitely the robots that had a contract, a reward or an active order, or that turned on Telegram or webhook notifications; the others are deleted by the midnight cleansing (`robosats/celery/__init__.py:35-38`), 6 to 30 hours after their last request (`api/tasks.py:24-46`).

|---|---|---|
| Reads its note when a key is entered | No relay reading; no recovery note | Read the key's note at its first visit after an install, same filter, both identities, same acceptance, on every coordinator relay of the network and on the public relays of § 4 |
| Opens on the note's robot, else robot 0 | Opens on robot 0 or the robot of the records | The same |
| Creates that robot on every coordinator | A robot reaches one coordinator only | Look it up read-only on every coordinator (#79's lookup, short header, nothing created) |
| Moves past a robot that served, publishes the note | Moves the Garage after a trade, sends nothing (#251) | Unchanged |
| Writes the note after a make and at a change of robot | Every make and take reserves a fresh robot | Write it after each confirmed make and take, carrying the highest robot index this device used for that key, so it never goes back when two trades are in progress; written again at each opening of the app |
| Arrows: ± 1, robot created everywhere | Arrows: local, nothing sent | After a restore, a robot reached by the arrows is looked up read-only |
| A found trade is shown and continued | The records can hold a recovered trade and its screens continue it; nothing finds or records one yet | Bind the robot to the coordinator holding its order; the user takes it over |
| `findNextUnusedAccount` | `NextTradeRobot`: lowest index with no binding and no record | After a restore, new robots start above the note's `account` and every robot the lookups found |

**The RoboSats note on public relays.** The note stays written byte for byte on the coordinators' relays, where the official client reads it. An identical copy also goes, from the start, to the public relays of § 4, read only by this app, so that the last robot may be found beyond four weeks if those relays keep it. Its cost: the note is addressed to the key's recovery identity, a fixed `p` tag, which anyone reading a public relay sees with its timing and may drown there by flooding the tag, as on the coordinators' relays. On a device that kept its records, a drowned note costs only the start robot, since new robots stay above everything the device knows. After a restore whose notes were drowned and whose lookups found nothing, the device knows nothing: new robots start low, and the only guard left is this app's own check at the coordinator of the new trade (next paragraph), with its limits.

**The derived key may trade.** Before #81 only a key recorded as drawn on this device traded (`NewTradeStanding.keyDrawnHereOnly`), because a key from elsewhere may have robots anywhere. The derived key is on every device holding the words and may be pasted into the official client, yet it must trade: it is recorded as drawn here. No coordinator protects against a robot used before: RoboSats logs in any token it knows (above). The refusal is this app's: at the first contact of a new trade's robot with that trade's coordinator, a robot the coordinator answers with a key pair this app did not send (the robot was made by another device or client, whose PGP pair is drawn at random), or with an active or last order, is refused, and the next attempt takes the next robot (`features/p2p/lib/src/domain/usecases/trade/make_order_usecase.dart`, `take_order_usecase.dart`, `RobotOnCoordinatorFace.alreadyExisted`, texts `p2pTakeRobotNotNew` and `p2pMakeRobotNotNew`). What replaces the protection is therefore the floor after a restore and that check, nothing on the coordinators' side. The check holds only in this app, only at the coordinator of the new trade, only on that coordinator's word, and only while that coordinator still holds the robot: it misses a robot that coordinator has deleted (no contract, no reward, 6 to 30 hours after its last request) and a robot that served at another coordinator, as § 7 says. The official client has no such refusal: it reads the robot on every coordinator and moves past one that served, and reuses on purpose one whose order expired or was cancelled.

**An imported key trades too** (decided on 2026-11-26, which replaces the rule of 2026-11-13 that kept a key from elsewhere to finishing its trades): the key selected, internal or external, imported or not, is the key of new trades, and `NewTradeStanding.keyDrawnHereOnly` is gone. Where a key comes from is still recorded (`garage_key_histories`), but takes no right away: a reservation for a new trade writes the provenance `generated` for any key, and only such a binding takes a pending take or make, never a robot bound by « Select Host » after « Robots from elsewhere ». What this opens, until the reading of the notes (PR 3) gives a floor: a key that served in the official client starts again from robot 0; each robot of it that the coordinator of the new trade still knows costs one refused attempt (the same check, `alreadyExisted`), the next attempt taking the next robot; a robot that coordinator has forgotten, or that served at another coordinator, passes. « Robots from elsewhere » stays where it was: on « Select Host » for a robot of a key of unknown history, which binds a robot to recover it, not for a new trade.

Besides the rows above, two deviations in what reaches a coordinator: robots are read, never created, on coordinators that do not hold them; and the note is written after the coordinator confirmed, not before, so a failed take writes nothing.

**As PR 3 built it.** The RoboSats recovery note is read and written on the coordinators' relays; the rows of the table above that it builds are « Read the key's note at its first visit », « Opens on the note's robot » and « Write it after each confirmed make and take … written again at each opening of the app », and the floor of « new robots start above the note's `account` ».

- **The relays**: every coordinator relay of the key's network (`nostrRelaysOfNetwork`), the six relays of mainnet, the two of testnet. **Not the public relays of § 4**: the embedded Tor of `bull_tor` refuses every destination that is not an onion service (`SocksPolicy.onionOnly`, for the client and for each session, `packages/bull_tor/lib/src/data/onion_tor_backend.dart`), although the transport could carry a `wss://` websocket through SOCKS (`TorHttpClientFactory` makes the TLS connection itself). Reaching them needs a session that accepts the clearnet in `bull_tor`, a decision of its own (that file says why the listener refuses the clearnet today: any local app that finds its port could use it); the list is embedded (`features/p2p/lib/src/domain/public_note_relays.dart`) and called by nothing. So the four-week limit of the coordinators' relays (above) still holds.
- **Tor sessions**: each read and each write goes through a Tor session of its own, opened for that call and closed after it (`OwnSessionNostrRelayTransport`, implemented by `TorCoordinatorTransport.readOnOwnSession` and `publishOnOwnSession`), never a robot's session nor the anonymous session of the books: a robot's would tie, for that coordinator, the robot to the recovery identity, and so the robots of a key to one another; the anonymous one would tie the books and the keys together. What a relay can tie is what the note carries, the recovery identity in its `p` tag, and the times of the calls (a note written right after a confirmed trade, the notes of every key written at the same opening). The two requests, the recovery identity's and the legacy one's, go on one websocket, as in the official client. At most six such sessions at once, apart from the robots' places.
- **Reading**: once per key and per run of the app while the key is not read, at the first of these: the first showing of the P2P tab of a network, for the key new trades take there, with robots in use or not (`RecoveryNoteSync.opened`, `GarageKeyRepository.forNewTrade`; so that after a reinstall or on a second phone the reading starts well before the first trade, functional review of #302; a key that cannot be had, no default wallet, a passphrase, a wallet locked or words that no longer give the key recorded, is neither read nor written, and nothing is shown); the Garage showing a key, internal or external, imported or not (`GarageCubit` tells `RecoveryNoteSync.visit`); the reservation of a new trade's robot (`InterimTradeRobots`, `RecoveryNoteSync.beforeNewTrade`). Both requests of the reference (`{"kinds":[1059],"#p":[…]}`, under `accountRecovery_<random>` ids), on every relay at once, each relay read apart and its events read apart in an isolate killed past its time (`IsolateGarageNoteCompute`), then `GarageRecoveryNote.latestOf` among the relays. A read is bounded by `relayReadDeadline` (66 s, `torConnectDeadline`, no second attempt), 1,000 events, 8 MiB and 1,064 messages; the whole reading by `noteReadDeadline` (96 s). The key counts as read only when a strict majority of the network's relays (more than half of `nostrRelaysOfNetwork`: 4 of the 6 of mainnet, 2 of the 2 of testnet, 1 of 1) gave their whole answer (an `EOSE` for both requests within the bounds) and their events were read within the reading's deadline, a note found or not; then it is not read again on this installation (`garage_recovery_notes.read_at`, schema 11). The rule comes from the review of #302: with « one relay is enough », one relay answering at once with nothing, or with an old note, while the others were unreachable or late, deprived the key of its floor for good, and the write after the next trade put a newer, lower note in front of the right one, which other devices and the official client would then take. Without a majority the key stays unread: the floor found, if any, is recorded all the same (it only goes up), nothing is written for the key in that run, and it is read again at the next run of the app, never twice in a run. A note found on a minority of the relays raises the floor but does not settle the key: one relay may hold an older, lower note than the others.
- **The floor**: the note's index, at its highest over the readings of both networks, kept in `garage_recovery_notes` (schema 11, by key fingerprint, never the key or its identity; the floor only goes up, a reading recorded stays, nothing is deleted). A new trade's robot is the first free index strictly above it (`NewTradeStanding.noteFloor`, `NextTradeRobot`), and never an index in use, as before. A note never lowers the floor; a lower note read later is ignored. The Garage opens on the note's robot when the device holds no trade of the key and no « Last order » line of it (`GarageOpening`, step 3); elsewhere it opens as before. A note at the last index leaves the key no robot for a new trade.
- **The wait of a new trade**: the reservation waits for the reading of this run still running, or starts it, at most 40 seconds (`newTradeNoteWait`). Where each figure comes from: 34 seconds is the slowest successful first onion contact measured on cold installs, written in the comment of `torConnectBudget` (`packages/bull_tor/lib/src/domain/tor_connect_budget.dart`), whose value is 60 seconds; `torConnectDeadline`, 66 seconds, is that budget plus 10 % and bounds each relay's read; 40 seconds keeps the 34 measured and a relay's answer and its reading a few seconds more; nothing here was measured on a phone. The wait comes again for each new trade of the key as long as the reading of this run has not ended (a reading still waiting for Tor, which it waits for up to 5 minutes): waiting again is the safe side; once the reading of this run ended, read or not, a new trade does not wait. Past it the trade goes on without the floor the reading would give, the check `alreadyExisted` at the coordinator of the trade staying the last guard; no text is added, the button already waits while the robot is prepared. A trade leaves without a floor when no relay answered within that time, when this run's reading already ended with no note found, or when the relays do not hold the note (more than four weeks old, withheld, drowned).
- **Writing**: after each make and take the coordinator confirmed (`TradeReader.tradeConfirmed`, called where `confirmTake` and `confirmMake` succeed, so a take refused or never sent writes nothing), and at the first showing of the P2P tab of each network in a run of the app, for every key with a robot bound or recorded there (`TradeRecordRepository.keysInUse`), the robots used between PR 2 and this one included. The index written is the highest the device knows for the key: its robots in use and the floor read (`NewTradeStanding.highestKnown`), so it never goes back when two trades are in progress, nor below a note read from another device. The note is written only once the key was read for good (a majority of the relays, above): a device that could not read the note from a majority of the relays does not write over a note it may not have seen; such a key is written in a later run, once read. The writes of one key run one after the other, the next after the one before it whatever that one gave. Each publication is on its own session, on every relay of the network; nothing waits for it, and its outcome is logged as a fixed word only.
- **What differs from the table and from the official client**: the public relays, not reached (above); the note written after the coordinator confirmed, never before (as § 3 decided); the highest index known written, where the official client writes the index it moves to; the note written again at each opening only for keys with robots in use, and only once read; the reading at the first showing of the tab or a first visit of a key, until a majority of the relays answered, rather than at each entry of a key, kept across restarts (the official client ends its reading at the `EOSE` of every relay of its pool or after 5 seconds, whatever they answered); a reading's wait of 40 seconds where the official client waits 5 over sockets already open; a note dated in the future not set apart, as in the official client. An `Error` of this path is reported to the zone and never makes a trade fail (a declared exception to rule 11 of `AGENTS.md`).
- **Not built here**: the lookups of #79 (step 4) and our key note (step 5).

## 4. Our one note: the number of the current key

As the RoboSats note gives, from a Garage Key, its last robot, this note gives, from the words, the last Garage Key the user switched to; then that key's RoboSats note gives the robot.

- **Format**, as close to RoboSats as possible: rumor kind 30078, tags `[['d','garage-key-index'],['index','<n>']]`, content `''`, NIP-59 seal and wrap; 1 701 bytes, the size of a RoboSats note, with nostr-tools' compact serialisation and NIP-44 padding, which the Dart code must reproduce byte for byte to keep that size.
- **Its key**: the note key N, `m/83696968'/82796679'/1'/{network}'`, first 32 bytes as a secp256k1 secret (hard failure if 0 or ≥ n), independent of every Garage Key and never displayed. Mainnet, « abandon ×11 about »: `727734121e7914c7ed554b37e15e4f6bb0887c9a7a61f0b01756b066a3e958cd`. BIP-85 2.1.0 now has a Nostr application (`128002'`, the same first 32 bytes as a secp256k1 secret); it is not used because its keys are meant as a user's Nostr identities, which another tool on the same words may derive and use in public, whereas N belongs to this feature and is never shown: under `82796679'` it cannot be one of them.
- **Against drowning**: anyone may write to a public `p` tag, and a relay clamps its answer, so the wrap is signed by W = HMAC-SHA256(N, `garage-key-index/wrap/v1`) and addressed to V = HMAC-SHA256(N, `garage-key-index/recipient/v1`), distinct from W so that the wrap does not stand out as addressed to its own author; W and V, used as secp256k1 secrets, get the same hard failure if 0 or ≥ n; the seal and rumor are authored by N. It is read with `{kinds:[1059], authors:[W]}`: nobody without the words can add events to that answer (a relay can still hide or lose it). Costs: W is one fixed public key per wallet and network, so a relay sees when this wallet refreshes its note; a relay that someday restricts kind 1059 to authenticated readers would need an authentication as W or V (as V only on a relay that applies NIP-17's rule of serving kind 1059 to the p-tagged user alone; strfry's development branch accepts W or V). N is used as the HMAC key of W and V, as the seal's signing key and as its NIP-44 key towards V: signing and NIP-44 on one key is ordinary Nostr, the HMAC use is not; no known danger, but a use that a third HMAC child for the seal would avoid; to settle in the note's pull request, before its format is frozen.
- **Reading rule**: the largest `index` among valid notes, not the latest: keys only go forward, and a device that restored without finding the note must not hide a higher number a slow relay still holds.
- **Written** at each « New key », and written again at each opening of the app, as the RoboSats note is (§ 3). Whether either note gets a cap on these openings (for example once a day, to show relays less) is an implementation detail, settled in each note's pull request. A device writes only an index it switched to itself or read in a note: after a restore that found nothing it writes nothing until the user moves forward. On the coordinators' relays it lives 26 to 28 days after its last write, so about four weeks after the app was last opened.
- **A help, never a guarantee.** Found: the app opens on that key, then reads its RoboSats note. Not found: the app opens on key 0 and the user gets the later keys back by hand with « New key » (§ 6). No blocking, no clock.
- **Relays**: every coordinator relay of the network and four or five public relays, written and read on all. A trial over Tor on 2026-11-26 during the design study, not published in this repository, found seven public relays that accepted and returned such a note, read by `authors`, with no authentication asked; proposed: `nos.lol`, `nostr.bitcoiner.social`, `relay.primal.net`, `nostr.mom`, `nostr.oxtr.dev`; `relay.damus.io` refuses WebSockets from Tor. How long they keep a note is not known yet: re-reads are planned around 2026-11-27, 2026-12-03 and 2026-12-26. So the list is a setting, not a format: an embedded constant in `features/p2p`, like the coordinators' list in `packages/robosats/lib/src/coordinator/federation_data.dart`, changed by a pull request; nothing reads it from the network.
- **Their cost**: each public relay is one more observer of W and of the time and size of each note, and at a restore of the reads made together (the key note, then that key's RoboSats note), which tie these keys together unless each read uses its own Tor session, and even then by timing (deduced). Little diversity: five of the seven candidates run strfry, and two appear to share an operator. A public relay may change its rules or close overnight. If none returns the note, the app opens on key 0.
- **Over Tor only**, one session per relay. A relay that does not answer within its deadline is skipped; the opening of the Garage never waits on a relay read: it opens at once on what the device knows, says it is looking for the last key, and moves when a note arrives. A failed read or write is tried again at the next opening.

## 5. First launch and restore

- **First opening of the Garage with a wallet.** The same path as a restore, since the app cannot tell a first install from a reinstall: the key note is read in the background, key 0 and its robot 0 are shown. No wizard, no backup alert. Nothing reaches a coordinator until a trade.
- **Uninstalled with a trade in progress, reinstalled the next day.** The key note gives key *n* (none: key 0); its RoboSats note gives robot *a*, the highest used; robot *a* is looked up read-only on every coordinator; the one holding its order is found and the user takes the trade over (the coordinator returns the robot's PGP key, encrypted with its token, so chat and payouts work). A trade on a lower robot: « Previous account ». A trade on another internal key: « ‹ » in the Garage Key card back to it, whose note is read and robots looked up the same way.
- **Restore after two months without opening the app.** The coordinators' relays have erased the notes; the public relays may still hold them. If not, the app opens on key 0, robot 0. The user gets the earlier keys back with « New key »: the key 1 it creates is exactly the old key 1, and so on, since a key is only its index. Then the robots, with the robot arrows; each robot reached is looked up; coordinators still hold every robot that had a contract, an active order (a dispute included) or a reward. A user who does not remember the numbers walks forward without knowing where to stop, and each « New key » pressed moves the key note forward for good (§ 4).
- **The same key pasted into the official client.** It reads our RoboSats note (if less than four weeks old) and creates that robot on every coordinator, and moves to the next robot, created everywhere too, if that one served. Pasted while a trade of that key is open, it presents that trade's robot to every coordinator (§ 7). Every robot it creates above what this device knows makes our next trade on that robot refused by this app (« The robot chosen for this take already existed on {coordinator} »), once per such robot, each refusal moving to the next robot; and only while the coordinator of our trade still holds that robot (§ 3).

## 6. The keys

The screen as PR 2 builds it, from the mock-up decided on 2026-11-26 (seven plates, `docs/maquettes/garage-cles-2026-11-26/` in the owner's folder, not in this repository):

- **The Garage screen stays as it is today; only the Garage Key card changes.** There is no row of keys above the row of robots.
- **The internal Garage Keys scroll inside the card**, « ‹ Internal Garage Key #N › », with arrows in the card and no re-authentication, as the robot arrows. « › » goes up to the highest key this device activated and no further: on that key it is greyed and creates nothing; « ‹ » goes down to key 0. The arrows never reach the external Garage Key.
- **Under the field, one short line and an ⓘ**: « Backed up by the 12 words of your Bull Wallet. » on an internal key, « Not backed up by your Bull Wallet: keep a copy of it. » in the warning colour on the external one; the ⓘ, at the right of that line (placement A; placement B, in the title, is one constant of `garage_key_card.dart`), opens the explanation of the key shown, closed by its button.
- **« New internal Garage Key »**, on an internal key only, in place of « Delete All »: « New Garage Key », a plain confirmation, then index + 1 recorded with its fingerprint (and, with PR 5, the key note written); it always makes the key above the highest, whichever internal key is shown, and selects it. Nothing is erased; the official client's « Generate new » replaces its key.
- **The external Garage Key** (§ 2), when the vault keeps one, is reached by « Switch to the external Garage Key », a button of the card of an internal key; its card has the title « External Garage Key » without arrows, « Back to internal Garage Keys », which returns to the last internal key shown (kept across restarts, `selected_garage_keys.last_internal_index`; the highest when none was shown), and « Delete the external Garage Key ». Without one, a discreet link of the card of an internal key, « Import an external Garage Key », opens today's « Robot recovery »; the key imported is shown at once, its robot 0. An internal key of this device pasted there is refused by its number: one key is never both.
- **« Delete the external Garage Key? »**: it is not backed up by the wallet; never refused: a trade in progress of that key adds a line in the warning colour that names it and says it could not be continued, and « Delete » stays enabled; today's PIN rule follows the confirmation (`NeedsPinToDeleteGarageKeyUsecase`). After it, the last internal key shown, and the import link again; the records of the key deleted stay.
- **« Your Garage Keys »**, once on the device, at the first opening of the Garage after the update when the vault kept a key: it says that key is now called « External Garage Key », and how to reach the internal ones; the Garage stays on the external key. Made due by the step to schema 10 (`garage_notices`), so never on a new install, nor after an import.
- **The key selected in the card is the key of new trades**, internal or external, whatever its number or origin; a trade in progress finishes with its own key (the key derived again by its index after comparing fingerprints, or the external key when the fingerprint is its own). A trade in progress of another key than the one shown has a line under the robot navigator, « Trade in progress #N » and, in grey, its key, robot and coordinator, which opens it.
- **The history** covers every key of the network: each order says its key on a line of its own (« Internal Garage Key #2 », « External Garage Key »), then its robot (« Robot #5 · AmberGalleon512 »).
- **Words that cannot give a key** (no default wallet, a passphrase, a secret without words, a keystore that cannot be read) never take the external key away: it stays shown, usable and deletable, and only the internal side says why, with « Retry » and « Switch to the external Garage Key » (review of #292, C-passphrase); without an external key, the Garage says why, as before.
- **After a restore that found nothing**, the app opens on key 0. The user gets the old keys back with « New internal Garage Key »: the key 1 it creates is exactly the old key 1, since a key is only its index; then the robots, with the robot arrows. A second phone that moved ahead is caught up the same way. A « New internal Garage Key » that gives the key already external activates it: the records are kept by fingerprint, so its trades go on, and it is shown as internal from then on.
- **Showing an earlier key** replaces the export of one robot's token: its `robo1…` text, behind re-authentication, pasted into the official client, works as any pasted key and exposes there the robots the official client touches.

## 7. What this design does not guarantee

- **The words hold the whole of P2P.** Whoever obtains them controls every robot of every key and can find the P2P history again, since coordinators keep the robots that had a contract or a reward. Worse than the official client, whose Garage Key is a separate secret: the counterpart of the purpose.
- **A key replaced after a leak, taken again at a restore.** Once the key note has expired, the app opens on key 0 and a user walking forward may stop on the leaked key. Accepted. Worse than the official client, where a replaced random key does not come back.
- **A robot used again.** « A robot serves once » holds for what the device knows. Beyond that, the only guard is this app's check at the coordinator of the new trade (§ 3); no coordinator refuses a robot it knows. Once the notes are gone that guard has holes: coordinators delete robots without contract or reward 6 to 30 hours after their last request, so a robot whose order expired or was cancelled passes again; and a robot that traded at another coordinator passes too, since the check asks only the new trade's coordinator, after which that other coordinator holds the credential of the new trade's robot and could act on it (the bond, or the collateral through a dispute or a false confirmation; never a payout, which needs the robot's PGP key). The check also rests on the coordinator's answer: a coordinator that hides a robot it holds is not caught. Worse than the official client for a robot that traded at another coordinator, which the official client sees since it reads the robot on every coordinator before a trade; not worse for a robot whose order expired or was cancelled, which the official client reuses on purpose; better on exposure, since it hands every robot to every coordinator.
- **A key pasted into the official client during a trade** presents that trade's robot to every coordinator, after which any of them could act on that trade with its credential. Not on the screen; stated here.
- **What coordinators learn at a restore**: each robot looked up gives its credential, hash id and nickname to every coordinator, as #79 accepted. Better than the official client, which creates them everywhere.
- **What relays learn**: the RoboSats recovery identity of the key in use, and the fixed author W with its refresh times. Refreshing both notes at the same opening ties, by timing, W to the key in use, and after « New key » one key to the next: someone holding a leaked key can follow the activity of the next key without reading it. Worse: more observers, for longer, and these links.
- **Two phones with the same words** use the same key and the same lowest free robot. This app's check refuses that robot only at a coordinator the other phone already used it with, and only while that coordinator still holds it; at any other it passes. Worse than the official client, whose second device sees the robot the first one used. One phone at a time.
- **The display is as strong as the wallet's PIN**: without one, « Show Garage Key » asks nothing (`features/p2p/lib/src/ui/garage/garage_reauthentication.dart`), and a copied key lands in a clipboard not marked sensitive (#56), the main way a key valid everywhere leaks (§ 2).

## 8. Moving from what exists

- **Nothing is erased** (decided on 2026-11-26, in place of an emptying first planned here): the version that brings the derived key keeps `p2p.sqlite` whole (bindings, key history, trades and trails, history, payments asked of the wallet, payouts) and the Garage vault slots of both networks. The key a slot holds becomes the external key (§ 2, § 6), with its robots, its trades, its history and its rewards, under its fingerprint. Never touched either: the wallets, their seeds, the wallet database, RecoverBull.
- **At the first opening after the update**, the external key, when the vault keeps one, stays selected: the user finds the Garage as it was, and its trades in progress finish with it. Otherwise key 0 of the words is selected.
- **Removed**: the wizard « Generate Garage Key » and « Generate new », the backup alert, and « Delete All » for an internal key, whose place « New internal Garage Key » takes (§ 6). An internal key has nothing to delete, since the words back it up; and nothing in the Garage empties the device's P2P book any more.
- **An imported key (#79)**: « Robot recovery » stays reachable, from « Import an external Garage Key », for a key from elsewhere, stored in the vault slot as the external Garage Key, shown apart from the internal keys, trading as any other (decided on 2026-11-26), and deletable. One external key at a time: a slot that holds anything refuses an import.

**As PR 2 built it.** Schema 10 adds three tables and erases nothing: `derived_garage_keys` (the indexes of the words this device activated, with their fingerprints, never changed nor deleted), `selected_garage_keys` (the key selected per network: an index of the words, or none for the external key; and the last internal key selected) and `garage_notices` (« Your Garage Keys », due then shown, never deleted). The step from schema 9 copies, changes or deletes no row; the one row it writes is « Your Garage Keys » due, in its own new table. The repository reads the external key from the vault slot of the network at each reading of the keys; at the first reading, with nothing selected yet, it selects the external key when the slot holds one, readable or not, otherwise key 0. A slot that cannot be read keeps its position, so that the user may try again or remove it; it is never taken for an empty one. An external key selected that the vault no longer holds gives way to the highest key of the words. A trade on any key, the external key included, finishes with its own key (`ofSlot`: a key of the words found by fingerprint and derived again, or the external key when the fingerprint is its own). The app never draws a key at random: `GarageKeys.create` stays in `packages/secrets`, with its tests, and nothing in the feature calls it. « Robots from elsewhere » stays as it was, on « Select Host », for a robot of a key from elsewhere.

**The decisions of 2026-11-26 on the mock-up**, written in § 6: the key selected is the key of new trades, whatever its number or origin, kept per network across restarts; the arrows scroll the internal keys, a button leads to the external one and back; « New internal Garage Key » on the internal keys only; the import link while there is no external key; the delete never refused; « Your Garage Keys » once; the line of a trade of another key; the history saying each order's key and robot.

## What was abandoned

A fuller design was studied first: a key number taken from the clock (the minute of the first launch or of a restore) under a two-level path, a check of the time against several coordinators, an encrypted state note listing the trades in progress, per-number and per-robot notes, bridge notes and a search of a pasted key's number. It aimed to guarantee that a restore never reuses a robot or a key replaced after a leak, even after the relays forget, and was judged too heavy for that gain. What this costs: after about four weeks without opening the app (longer if the public relays keep the notes), a restore no longer knows the key or robot in use, and may take again a key replaced after a leak or a robot that served; trades in progress come back by themselves only within that time.
